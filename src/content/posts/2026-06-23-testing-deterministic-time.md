시간은 테스트를 불안정하게 만드는 대표적인 원인입니다. `Date.now()`를 직접 호출하고, 테스트가 실제 시간을 기다리고, 타임존을 환경에 맡기면 로컬에서는 통과하던 테스트가 CI에서 실패합니다. 시간 로직은 현실과 가깝게 만들수록 테스트가 어려워지므로, 코드 안에서는 시간을 주입 가능한 의존성으로 다루는 편이 좋습니다.

## 현재 시간을 직접 읽지 않는다

비즈니스 로직 곳곳에서 `new Date()`나 `Date.now()`를 직접 호출하면 테스트가 원하는 시점을 만들기 어렵습니다. 대신 clock 인터페이스를 두면 테스트가 시간을 통제할 수 있습니다.

```ts
interface Clock {
  now(): Date;
}

class SystemClock implements Clock {
  now() {
    return new Date();
  }
}
```

테스트에서는 고정된 clock을 넣습니다.

```ts
const clock = { now: () => new Date("2026-06-23T00:00:00Z") };
```

이 작은 추상화만으로 만료, 예약, SLA 계산 테스트가 훨씬 단순해집니다.

## 기다리지 말고 시간을 이동한다

재시도나 만료 테스트에서 실제로 1초, 5초, 1분을 기다리면 테스트 스위트가 느려지고 불안정해집니다. 가짜 타이머나 clock 이동을 사용해야 합니다.

```ts
fakeClock.set("2026-06-23T10:00:00Z");
session.refresh();

fakeClock.advance({ minutes: 31 });
expect(session.isExpired()).toBe(true);
```

핵심은 "시간이 흘렀다"는 사실을 테스트가 즉시 만들 수 있어야 한다는 점입니다. 실제 대기는 통합 테스트 한두 개면 충분합니다.

## 타임존을 명시한다

날짜 로직은 타임존을 빼고 테스트하면 언젠가 깨집니다. 특히 "오늘", "월말", "다음 영업일" 같은 표현은 사용자의 지역, 서버의 지역, 데이터 저장 기준이 서로 다를 수 있습니다.

테스트 이름과 입력에 타임존을 드러내는 것이 좋습니다.

```text
Asia/Seoul 기준으로 2026-06-23 00:30은 같은 영업일로 처리한다
UTC 기준 월말 배치는 2026-06-30T15:00:00Z 이후 실행된다
```

서버 저장 값은 UTC로 통일하더라도, 제품 규칙은 지역 시간을 기준으로 할 수 있습니다. 둘을 섞어 쓰면 장애가 생깁니다.

## 경계값을 먼저 테스트한다

시간 로직은 대부분 경계에서 깨집니다. 만료 시간 바로 전, 바로 후, 일광 절약 시간 변경, 월말, 윤년, 주말과 공휴일이 대표적입니다.

테스트 케이스는 정상 중간값보다 경계값을 먼저 잡아야 합니다.

- 만료 1밀리초 전
- 만료 시각과 정확히 같은 순간
- 만료 1밀리초 후
- 월말 23:59:59
- 윤년 2월 29일
- 타임존이 다른 사용자

이 케이스들은 많아 보이지만, 한 번 표로 만들면 반복해서 재사용할 수 있습니다.

## 스케줄러와 작업 본문을 분리한다

크론이나 배치 테스트가 어려운 이유는 스케줄 판단과 실제 작업이 섞여 있기 때문입니다. 스케줄러는 "언제 실행할지"만 판단하고, 작업 본문은 일반 함수로 분리해야 합니다.

```ts
if (shouldRunDailyJob(clock.now(), lastRunAt)) {
  await runDailyJob({ targetDate });
}
```

이렇게 나누면 스케줄 판단은 고정된 시간 입력으로 테스트하고, 작업 본문은 데이터 입력과 결과만 테스트할 수 있습니다.

## 체크리스트

- 현재 시간을 직접 호출하지 않고 clock으로 주입한다.
- 테스트에서 실제 대기 대신 시간을 이동한다.
- UTC와 제품 타임존 기준을 명시한다.
- 만료 직전과 직후 같은 경계값을 테스트한다.
- 스케줄 판단과 작업 본문을 분리한다.

시간 테스트의 목표는 현실 시간을 흉내 내는 것이 아닙니다. 중요한 시점을 마음대로 만들고, 그 시점에서 코드가 같은 답을 내게 하는 것입니다.
