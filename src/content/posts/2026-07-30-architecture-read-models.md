도메인 모델이 깔끔해도 화면 조회가 복잡해지면 API는 점점 무거워집니다. 여러 aggregate를 조합하고, 권한을 적용하고, 통계를 계산하다 보면 쓰기 모델 하나로 모든 읽기를 감당하기 어렵습니다.

이때 읽기 모델을 분리할 수 있습니다. 다만 분리는 공짜가 아닙니다.

## 화면 요구를 먼저 고정한다

Read model은 추상적인 성능 개선책이 아니라 특정 조회 요구를 빠르고 단순하게 만들기 위한 모델입니다. 어떤 화면을 위해 만드는지 명확해야 합니다.

먼저 다음을 정리합니다.

- 화면에서 필요한 필드
- 정렬과 필터 조건
- 권한에 따라 달라지는 값
- 허용 가능한 데이터 지연
- 페이지네이션 방식

이 정보 없이 read model을 만들면 결국 또 다른 범용 테이블이 생깁니다.

## 최신성이 얼마나 필요한지 정한다

읽기 모델은 보통 이벤트, CDC, 배치 작업으로 갱신됩니다. 따라서 원본 데이터와 약간의 지연이 생길 수 있습니다.

모든 화면이 즉시 일관성을 필요로 하지는 않습니다.

- 결제 완료 여부: 거의 즉시 필요
- 관리자 통계: 몇 분 지연 허용 가능
- 추천 목록: 더 긴 지연도 가능
- 권한 상태: 지연 허용이 어려움

허용 지연을 정해야 갱신 방식과 알림 기준을 정할 수 있습니다.

## 재빌드 경로를 만든다

Read model은 언젠가 틀어집니다. 이벤트 처리 실패, 스키마 버그, 누락된 backfill 때문에 원본과 차이가 날 수 있습니다.

따라서 처음부터 재빌드 경로가 필요합니다.

- 전체 재생성 스크립트
- 특정 tenant 또는 기간만 재생성하는 옵션
- 진행률과 실패 로그
- 재빌드 중 읽기 트래픽 처리 방식
- 원본과 read model 차이를 비교하는 검증 쿼리

재빌드가 없다면 read model은 운영 부채가 됩니다.

## 쓰기 경로와 섞지 않는다

읽기 모델은 조회 최적화를 위해 중복과 denormalization을 허용합니다. 이 모델을 쓰기 판단의 기준으로 사용하면 문제가 생깁니다.

예를 들어 권한 부여, 결제 승인, 재고 차감 같은 중요한 결정은 원본 쓰기 모델이나 강한 일관성을 보장하는 저장소를 기준으로 해야 합니다. Read model은 화면을 빠르게 보여주기 위한 복사본입니다.

## 관측 지표를 둔다

Read model 운영에서 봐야 할 지표는 단순한 쿼리 속도만이 아닙니다.

- 원본 이벤트와 반영 시점의 lag
- 갱신 실패 수
- 재시도 큐 크기
- 원본과 read model의 불일치 샘플
- 재빌드 소요 시간

읽기 모델은 성능 문제를 데이터 동기화 문제로 바꾸는 선택일 수 있습니다. 그 선택이 합리적이려면 지연, 재빌드, 검증을 함께 설계해야 합니다.
