React 성능 문제를 만나면 `memo`, `useMemo`, `useCallback`을 먼저 떠올리기 쉽습니다. 하지만 최적화 도구를 먼저 넣으면 코드가 복잡해지고, 실제 병목은 그대로 남을 수 있습니다. 필요한 것은 렌더링 예산입니다.

렌더링 예산은 특정 화면에서 어떤 상호작용이 얼마 안에 끝나야 하는지, 어떤 컴포넌트가 몇 번까지 렌더링되어도 괜찮은지 정하는 기준입니다. 예산이 있어야 최적화가 감이 아니라 측정이 됩니다.

## 사용자 행동 기준으로 측정한다

컴포넌트 하나의 렌더 시간이 아니라 사용자 행동에서 시작해야 합니다.

- 검색어 입력
- 필터 변경
- 탭 전환
- 행 선택
- 폼 필드 수정
- 모달 열기

각 행동마다 기대 응답 시간을 정합니다. 예를 들어 검색어 입력은 100ms 안에 시각적 반응이 있어야 하고, 큰 목록 필터링은 300ms 안에 결과가 바뀌어야 할 수 있습니다.

이 기준이 있어야 "느린가?"라는 주관적 논쟁을 줄일 수 있습니다.

## 렌더링 횟수와 비용을 함께 본다

렌더링이 여러 번 일어난다고 무조건 나쁜 것은 아닙니다. 아주 작은 컴포넌트가 몇 번 렌더링되는 것은 문제 아닐 수 있습니다. 반대로 한 번만 렌더링되어도 무거운 차트나 큰 테이블은 병목이 됩니다.

측정할 때는 두 가지를 함께 봅니다.

- 어떤 컴포넌트가 자주 렌더링되는가
- 각 렌더링이 얼마나 비싼가

React Profiler는 이 구분에 도움이 됩니다. "많이 렌더링되는 컴포넌트"와 "한 번 렌더링할 때 비싼 컴포넌트"는 해결 방식이 다릅니다.

## 상태 위치를 먼저 점검한다

많은 렌더링 문제는 memo 부족이 아니라 상태 위치 문제입니다. 너무 상위 컴포넌트에 상태가 있으면 작은 입력 변경도 화면 전체를 다시 렌더링시킵니다.

상태를 점검할 때는 다음 질문을 합니다.

- 이 상태를 실제로 읽는 컴포넌트는 어디인가?
- URL이나 서버 캐시에 있어야 할 상태인가?
- 입력 중인 임시 값과 저장된 값을 분리했는가?
- 전역 store에 넣을 만큼 여러 화면이 공유하는가?

상태를 필요한 위치로 낮추는 것만으로도 최적화 코드 없이 문제가 사라지는 경우가 많습니다.

## 참조 안정성은 경계에서 관리한다

객체와 함수가 매 렌더마다 새로 만들어지면 하위 컴포넌트의 memo가 깨질 수 있습니다. 하지만 모든 곳에 `useCallback`을 넣으면 코드가 읽기 어려워집니다.

참조 안정성은 성능 경계에서 관리하는 편이 좋습니다. 예를 들어 큰 테이블, 가상화 리스트, 차트, 복잡한 폼 섹션처럼 비용이 큰 컴포넌트로 내려가는 props를 안정화합니다.

작은 버튼이나 단순 텍스트 컴포넌트에는 굳이 적용하지 않아도 됩니다. 최적화도 유지보수 비용을 가집니다.

## 리스트는 구조적으로 줄인다

큰 리스트 성능은 memo보다 구조적인 해결이 더 중요합니다. 5천 개 행을 모두 렌더링하면서 memo만 추가하면 한계가 있습니다.

다음 순서로 접근하는 편이 좋습니다.

- 페이지네이션이나 무한 스크롤로 렌더링 항목 수를 줄인다.
- 화면에 보이는 항목만 렌더링하는 가상화를 적용한다.
- 행 컴포넌트의 props를 안정화한다.
- 행 안의 무거운 계산을 미리 계산하거나 지연한다.

리스트는 렌더링 예산을 가장 쉽게 초과하는 영역이므로 별도 기준을 두는 것이 좋습니다.

React 성능 최적화는 도구 이름을 많이 쓰는 일이 아닙니다. 사용자 행동에서 예산을 정하고, 실제 병목 컴포넌트를 측정하고, 상태 위치와 렌더링 구조를 먼저 고치는 일입니다. 예산이 있으면 최적화의 시작점과 끝점을 알 수 있습니다.
