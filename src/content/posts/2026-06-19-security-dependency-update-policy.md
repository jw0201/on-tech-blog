의존성 업데이트는 미루기 쉽습니다. 기능 개발보다 눈에 덜 띄고, 바꾸면 깨질 수 있으며, 당장 장애를 만들지 않는 것처럼 보입니다. 하지만 오래 미룬 업데이트는 취약점 대응 때 한꺼번에 몰려와 더 큰 리스크가 됩니다. 의존성 관리는 보안 이벤트가 아니라 운영 루틴이어야 합니다.

## 업데이트 주기를 정한다

가장 나쁜 상태는 "언젠가 한 번" 업데이트하는 것입니다. 작은 업데이트를 자주 하면 변경 범위가 작고 원인 추적이 쉽습니다. 팀 규모와 서비스 특성에 맞춰 주기를 정합니다.

실무에서는 다음 정도가 출발점이 됩니다.

- patch 업데이트: 매주 또는 격주
- minor 업데이트: 월 1회
- major 업데이트: 분기별 계획 작업
- critical 취약점: 별도 긴급 경로

자동 PR 도구를 쓰더라도 병합 책임과 검증 기준은 사람이 정해야 합니다. PR이 열리는 것과 업데이트가 운영에 반영되는 것은 다릅니다.

## 모든 취약점을 같은 급으로 보지 않는다

취약점 알림은 많습니다. 그중 실제 위험은 애플리케이션이 해당 코드를 어떻게 사용하는지에 따라 달라집니다. 개발 의존성인지, 런타임 의존성인지, 외부 입력을 처리하는 경로인지, 네트워크에 노출되는지 확인해야 합니다.

우선순위를 정할 때 볼 항목은 다음과 같습니다.

- 런타임에 포함되는 패키지인가
- 취약한 함수나 경로를 실제로 호출하는가
- 공격자가 입력을 제어할 수 있는가
- 컨테이너 이미지나 배포 산출물에 포함되는가
- 이미 완화 장치가 있는가

CVSS 점수만으로 결정하면 실제 운영 리스크와 어긋날 수 있습니다. 점수는 시작점이고, 사용 맥락이 판단의 핵심입니다.

## lockfile 변경을 리뷰한다

의존성 업데이트 PR에서 코드 변경만 보면 부족합니다. lockfile은 실제로 설치될 패키지 그래프를 보여줍니다. 예상보다 많은 transitive dependency가 바뀌었는지, 새로운 native 모듈이 들어왔는지, 라이선스가 달라졌는지 확인해야 합니다.

업데이트 PR에는 최소한 다음 정보가 있으면 좋습니다.

- 직접 업데이트된 패키지
- 같이 바뀐 주요 하위 패키지
- 보안 수정 여부
- breaking change 여부
- 실행한 테스트와 빌드 결과

이 정보가 있어야 리뷰어가 단순히 "버전만 올렸네"라고 넘기지 않습니다.

## 롤백 가능한 단위로 병합한다

여러 패키지를 한 PR에 몰아넣으면 실패 원인을 찾기 어렵습니다. 같은 생태계의 patch 업데이트는 묶어도 되지만, major 업데이트나 빌드 도구 변경은 분리하는 편이 좋습니다. 특히 프레임워크, 번들러, ORM, 인증 라이브러리는 영향 범위가 큽니다.

롤백 기준도 미리 정합니다. 배포 후 에러율이 증가하거나 빌드 시간이 급증하거나 특정 브라우저에서 문제가 생기면 어떤 변경을 되돌릴지 알아야 합니다.

## 체크리스트

- patch, minor, major 업데이트 주기를 분리한다.
- 런타임 노출 여부와 실제 호출 경로로 우선순위를 정한다.
- lockfile 변경을 리뷰 대상에 포함한다.
- 큰 업데이트는 작은 PR로 나눈다.
- 업데이트 PR에 테스트와 빌드 결과를 남긴다.
- 긴급 취약점 대응 경로를 평시 루틴과 분리한다.

의존성 업데이트는 한 번에 몰아서 갚는 빚이 되기 쉽습니다. 작은 주기로 나누고 판단 기준을 명확히 하면, 보안 대응은 덜 급하고 운영은 더 예측 가능해집니다.
