모듈화를 시작하면 곧 공통 코드가 생깁니다. 날짜 포맷, 금액 타입, 사용자 ID, 에러 코드, 이벤트 스키마처럼 여러 도메인이 함께 쓰는 요소가 있습니다. 이것을 적절히 모으면 shared kernel이 됩니다.

문제는 shared kernel이 너무 쉽게 "아무거나 넣는 공통 폴더"가 된다는 점입니다. 처음에는 편하지만 시간이 지나면 모든 모듈이 공통 코드에 의존하고, 작은 변경도 전체 시스템을 흔듭니다.

## 공유할 것과 복사할 것을 구분한다

중복이 보인다고 무조건 공유하면 안 됩니다. 두 코드가 지금 같아 보여도 변화 이유가 다르면 분리해두는 편이 낫습니다.

공유 후보가 되려면 다음 조건을 만족해야 합니다.

- 여러 모듈이 같은 의미로 사용한다
- 변경 주기가 낮다
- 제품 정책보다 기술적 또는 도메인 기본 개념에 가깝다
- 잘못 바뀌면 시스템 전체 일관성이 깨진다

예를 들어 `Money`, `UserId`, `TimeRange` 같은 값 객체는 공유할 수 있습니다. 반대로 할인 정책, 알림 문구, 주문 상태 전이는 각 도메인의 변화 이유가 다를 수 있으므로 함부로 공유하지 않는 편이 좋습니다.

## shared가 domain을 알지 못하게 한다

공유 커널은 하위 레벨이어야 합니다. 특정 도메인의 use case나 repository, 화면 정책을 알기 시작하면 의존 방향이 뒤집힙니다.

나쁜 신호는 다음과 같습니다.

- `shared`가 `billing`, `order`, `admin` 모듈을 import한다
- 공통 유틸 함수 인자에 특정 도메인 DTO가 들어간다
- shared enum에 한 팀만 쓰는 상태가 계속 추가된다
- 공통 에러 타입이 제품 정책 메시지를 포함한다

shared kernel은 여러 모듈이 올라타는 바닥이어야지, 모든 도메인을 끌어안는 상위 계층이 되어서는 안 됩니다.

## 변경 절차를 더 엄격하게 둔다

공유 커널의 변경은 영향 범위가 넓습니다. 그래서 일반 모듈보다 리뷰 기준이 높아야 합니다.

간단한 규칙을 둘 수 있습니다.

- 새 export는 사용처가 두 곳 이상일 때만 추가
- 기존 타입 필드 삭제는 마이그레이션 계획 필요
- shared에 정책 로직을 넣을 때는 대안 검토
- 변경 시 의존 모듈 테스트를 함께 실행
- 문서나 예시 사용법 업데이트

이 규칙이 없으면 shared는 가장 쉬운 위치가 되고, 가장 위험한 위치가 됩니다.

## 버전 경계를 생각한다

모놀리식 저장소 안에서는 공유 타입을 즉시 바꾸기 쉽습니다. 하지만 서비스가 나뉘거나 패키지로 배포되면 shared kernel에도 버전 호환성이 필요합니다.

특히 이벤트 스키마, API DTO, 저장 데이터 형식은 한 번 배포되면 과거 데이터와 외부 소비자가 남습니다. 필드를 rename하는 대신 추가 후 deprecate하는 방식이 필요할 수 있습니다.

내부 공통 코드라고 해서 버전 사고가 필요 없는 것은 아닙니다. 경계를 넘는 데이터라면 내부든 외부든 호환성을 고려해야 합니다.

## 공통 폴더를 정기적으로 청소한다

shared kernel은 시간이 지나며 부풀어 오릅니다. 사용하지 않는 helper, 한 모듈만 남은 타입, 과거 정책이 섞입니다. 그래서 정기적인 정리가 필요합니다.

청소 기준은 단순합니다.

- 사용처가 하나뿐이면 해당 모듈로 이동
- 이름이 너무 추상적이면 의미를 좁힘
- 도메인 정책이 들어갔다면 소유 모듈로 이전
- 테스트가 없는 공통 로직은 테스트 추가 또는 제거

좋은 shared kernel은 많은 코드를 담고 있는 곳이 아닙니다. 정말 함께 유지해야 하는 최소 개념만 담고 있는 곳입니다. 공유의 비용을 의식하면 모듈 경계는 더 오래 건강하게 유지됩니다.
