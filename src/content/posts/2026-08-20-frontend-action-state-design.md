프론트엔드에서 비동기 액션은 생각보다 많은 상태를 만듭니다. 버튼을 눌렀는지, 요청이 진행 중인지, 낙관적 업데이트가 적용됐는지, 실패했는지, 다시 시도할 수 있는지, 서버 응답이 화면에 반영됐는지 같은 상태가 한 흐름 안에 들어옵니다.

문제는 이 흐름을 `isLoading` 하나로 표현할 때 시작됩니다. 처음에는 충분해 보이지만 저장 버튼, 삭제 버튼, 자동 저장, 목록 갱신이 한 화면에 함께 있으면 어느 액션이 진행 중인지 알기 어려워집니다.

## 액션 단위로 상태를 나눈다

페이지 전체에 하나의 `loading`을 두면 화면 전체가 과하게 잠깁니다. 사용자는 댓글 저장 중에도 필터를 바꾸고 싶을 수 있고, 프로필 사진 업로드 중에도 이름을 수정할 수 있습니다.

상태는 액션 단위로 나누는 편이 좋습니다.

- `saveProfile`
- `deleteAvatar`
- `resendInvitation`
- `refreshMembers`

각 액션은 최소한 다음 상태를 가질 수 있습니다.

- `idle`
- `pending`
- `succeeded`
- `failed`

여기에 취소 가능한 요청이라면 `cancelling`, 재시도 대기라면 `retrying`을 추가할 수 있습니다. 중요한 것은 상태 이름이 UI 정책과 직접 연결되어야 한다는 점입니다. `pending`이면 버튼을 비활성화하고, `failed`면 같은 영역에 오류와 재시도 버튼을 보여주는 식입니다.

## 실패 상태를 화면에 남긴다

실패한 액션은 사라지면 안 됩니다. 토스트만 띄우고 끝내면 사용자는 어떤 입력이 저장되지 않았는지 놓치기 쉽습니다.

실패 상태는 액션이 일어난 자리 근처에 남기는 편이 안전합니다.

- 저장 버튼 옆에 "저장 실패" 표시
- 실패한 행에만 재시도 버튼 표시
- 낙관적으로 추가한 항목을 흐리게 두고 복구 선택지 제공
- 자동 저장 실패 시 마지막 성공 저장 시각 표시

토스트는 알림이고, 인라인 오류는 복구 도구입니다. 둘을 같은 역할로 쓰면 장애 상황에서 UX가 약해집니다.

## 낙관적 업데이트는 롤백 전략과 함께 둔다

낙관적 업데이트는 빠른 느낌을 주지만 실패 처리가 없으면 데이터 신뢰도를 떨어뜨립니다. 좋아요, 체크박스, 정렬 순서처럼 되돌리기 쉬운 액션에는 잘 맞습니다. 결제, 권한 변경, 삭제처럼 실패 비용이 큰 액션에는 신중해야 합니다.

낙관적 업데이트를 쓸 때는 세 가지를 먼저 정합니다.

- 실패하면 이전 값으로 되돌릴지
- 실패한 상태를 유지하고 재시도하게 할지
- 서버 응답을 기준으로 다시 정렬하거나 병합할지

특히 목록에서는 임시 ID가 중요합니다. 클라이언트에서 만든 항목에 `tempId`를 두고, 서버 응답의 실제 ID와 매핑해야 중복 렌더링을 막을 수 있습니다.

## 중복 제출을 서버와 함께 막는다

프론트엔드 버튼 비활성화만으로 중복 제출을 막을 수는 없습니다. 더블 클릭, 브라우저 재시도, 네트워크 지연, 탭 중복 실행이 모두 가능합니다.

클라이언트는 사용자 경험을 위해 중복 클릭을 줄이고, 서버는 idempotency key나 요청 중복 감지를 통해 실제 중복 처리를 막아야 합니다. 저장이나 결제처럼 한 번만 실행되어야 하는 액션은 양쪽이 함께 설계되어야 합니다.

좋은 패턴은 액션 시작 시 클라이언트가 고유 키를 만들고, 실패 후 재시도할 때 같은 키를 쓰는 것입니다. 그러면 사용자는 안전하게 다시 누를 수 있고, 서버는 같은 작업을 두 번 처리하지 않습니다.

## 화면 잠금 범위를 좁힌다

액션 상태 설계의 목표는 사용자를 막는 것이 아니라, 위험한 조작만 막는 것입니다. 저장 중인 필드만 잠그고 다른 영역은 계속 탐색하게 두면 화면이 덜 답답합니다.

예를 들어 팀 설정 화면에서 팀 이름 저장 중이라고 멤버 목록 전체를 막을 필요는 없습니다. 반대로 플랜 다운그레이드 중에는 결제 관련 액션을 넓게 잠그는 편이 맞습니다.

액션 상태는 데이터 모델만큼이나 제품 정책입니다. 어떤 행동을 기다리게 할지, 어떤 실패를 복구하게 할지, 어떤 조작을 동시에 허용할지 결정해야 합니다. `isLoading`을 줄이고 액션 이름과 상태 전이를 명확히 두면, 복잡한 화면도 예측 가능하게 유지할 수 있습니다.
