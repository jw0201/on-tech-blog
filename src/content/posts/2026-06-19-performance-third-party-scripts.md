웹 성능을 개선할 때 애플리케이션 코드만 보면 절반만 본 것입니다. 분석 도구, 채팅 위젯, 광고 태그, A/B 테스트 스크립트가 초기 로딩과 메인 스레드를 크게 차지할 수 있습니다. 서드파티 스크립트는 기능의 일부이지만, 배포 통제권이 밖에 있다는 점에서 더 조심스럽게 다뤄야 합니다.

## 스크립트마다 소유자와 목적을 적는다

외부 스크립트는 쉽게 추가되고 잘 제거되지 않습니다. 어떤 팀이 왜 넣었는지 모르면 성능 문제가 생겨도 지우기 어렵습니다. 스크립트 목록에는 최소한 다음 정보가 있어야 합니다.

- 목적
- 소유 팀
- 로드되는 페이지
- 사용자 동의 필요 여부
- 제거해도 되는 조건
- 성능 예산

목록을 문서로만 두면 오래가지 않습니다. 가능하면 코드 근처에 설정으로 관리하고 PR 리뷰 대상에 포함합니다.

## 초기 렌더링에 꼭 필요한지 묻는다

많은 서드파티 스크립트는 첫 화면에 필요하지 않습니다. 분석 이벤트는 페이지가 보인 뒤 보내도 되고, 채팅 위젯은 사용자가 버튼을 눌렀을 때 로드해도 됩니다. 모든 스크립트를 `<head>`에 넣는 것은 가장 비싼 선택입니다.

```html
<script src="analytics.js" defer></script>
```

`async`와 `defer`도 구분해야 합니다. 실행 순서가 중요하지 않으면 `async`, HTML 파싱 이후 실행하면 되는 스크립트는 `defer`가 더 예측 가능합니다. 사용자 상호작용 전까지 필요 없는 기능은 동적 로딩이 낫습니다.

## 태그 매니저를 우회로로 만들지 않는다

태그 매니저는 편리하지만, 리뷰 없이 스크립트가 추가되는 통로가 되기 쉽습니다. 제품, 마케팅, 데이터 팀이 빠르게 실험할 수 있다는 장점은 있지만, 성능과 개인정보 리스크도 함께 늘어납니다.

운영 규칙이 필요합니다.

- 새 태그는 소유자와 종료일을 가진다.
- 민감 페이지에서는 허용된 태그만 실행한다.
- 태그 변경도 배포 변경처럼 기록한다.
- 성능 예산을 넘기면 자동으로 알림을 보낸다.

태그 매니저는 코드 리뷰를 없애는 도구가 아니라 변경 절차를 다르게 만드는 도구입니다.

## 장애 격리를 고려한다

외부 스크립트가 느리거나 실패해도 핵심 기능이 멈추면 안 됩니다. 결제, 로그인, 문서 작성 같은 주요 흐름에서는 서드파티 실패를 무시하거나 늦게 처리해야 합니다.

방어적으로 설계할 지점은 다음과 같습니다.

- 외부 전역 객체가 없을 때도 앱이 동작한다.
- 이벤트 전송 실패가 사용자 액션을 막지 않는다.
- 스크립트 로딩 시간이 일정 기준을 넘으면 중단한다.
- CSP와 허용 도메인을 최소화한다.

특히 동기 스크립트 하나가 렌더링을 막으면 성능 문제를 넘어 가용성 문제가 됩니다.

## 체크리스트

- 모든 서드파티 스크립트에 소유자와 목적을 둔다.
- 첫 화면에 필요 없는 스크립트는 지연 로딩한다.
- 태그 매니저 변경도 감사 가능한 절차로 관리한다.
- 외부 스크립트 실패가 핵심 기능을 막지 않게 한다.
- Long Task와 Web Vitals를 스크립트별로 관찰한다.
- CSP로 허용 도메인을 제한한다.

서드파티 스크립트는 공짜 기능이 아닙니다. 네트워크, 메인 스레드, 개인정보, 장애 전파 비용을 모두 씁니다. 비용을 보이게 만들면 어떤 스크립트를 남길지 더 쉽게 결정할 수 있습니다.
