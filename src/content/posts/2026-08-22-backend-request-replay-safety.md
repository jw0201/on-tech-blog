운영 환경에서 요청은 한 번만 오지 않습니다. 클라이언트가 재시도하고, 로드 밸런서가 연결을 끊고, 사용자가 버튼을 다시 누르고, 큐가 메시지를 재전송합니다. 그래서 중요한 백엔드 작업은 "한 번 실행된다"가 아니라 "여러 번 들어와도 결과가 망가지지 않는다"를 기준으로 설계해야 합니다.

요청 재실행 안전성은 결제나 주문 같은 큰 기능에만 필요한 것이 아닙니다. 초대 메일 발송, 포인트 지급, 파일 변환 시작, 권한 변경처럼 부작용이 있는 모든 API에 필요합니다.

## 안전한 읽기와 위험한 쓰기를 구분한다

먼저 API를 성격별로 나눕니다.

- 조회처럼 여러 번 실행해도 같은 읽기 결과만 반환하는 요청
- 설정 저장처럼 같은 값으로 여러 번 실행해도 결과가 같은 요청
- 포인트 적립, 이메일 발송처럼 실행 횟수 자체가 의미를 갖는 요청

세 번째 부류는 반드시 중복 방지 장치가 필요합니다. `POST /send-email`처럼 이름만 보면 단순해 보여도, 실제로는 외부 시스템에 부작용을 남기기 때문입니다.

## idempotency key는 결과까지 저장한다

idempotency key를 받을 때 흔한 실수는 "이미 처리한 키인지"만 저장하는 것입니다. 클라이언트가 같은 키로 재시도했을 때 이전과 같은 응답을 돌려주지 않으면, 호출자는 성공했는지 실패했는지 판단하기 어렵습니다.

좋은 구현은 키와 함께 처리 결과를 저장합니다.

- 요청 주체
- 요청 경로 또는 작업 종류
- 요청 본문 해시
- 처리 상태
- 최종 응답 코드
- 최종 응답 본문 또는 결과 ID
- 만료 시각

같은 키인데 본문 해시가 다르면 오류를 반환해야 합니다. 같은 키로 다른 작업을 실행할 수 있게 두면 디버깅하기 어려운 데이터 오염이 생깁니다.

## 트랜잭션 경계를 명확히 둔다

중복 방지는 보통 데이터베이스 제약 조건과 함께 동작해야 합니다. 애플리케이션 코드에서 먼저 조회하고 나중에 삽입하면 경쟁 조건이 생길 수 있습니다. 가능한 경우 고유 인덱스나 `insert on conflict` 같은 원자적 연산을 사용합니다.

예를 들어 포인트 지급이라면 `user_id`, `campaign_id`, `reason_key`에 고유 제약을 둘 수 있습니다. 요청이 두 번 들어와도 지급 레코드는 하나만 만들어지고, 두 번째 요청은 기존 결과를 읽어 응답합니다.

외부 API 호출이 끼어 있다면 더 조심해야 합니다. 데이터베이스 커밋 전에 외부 결제를 호출하면 롤백과 재시도 사이에서 상태가 어긋날 수 있습니다. 이때는 outbox 패턴이나 작업 큐를 사용해 내부 상태 변경과 외부 호출을 분리하는 편이 안전합니다.

## 재시도 가능한 오류와 아닌 오류를 나눈다

모든 실패를 재시도하면 장애를 키울 수 있습니다. 인증 실패, 권한 없음, 유효성 오류는 재시도해도 성공하지 않습니다. 반대로 네트워크 단절, 외부 API 503, 일시적인 lock timeout은 재시도 대상일 수 있습니다.

API 응답에는 호출자가 판단할 수 있는 신호가 있어야 합니다.

- `400`, `403`, `409`: 요청 수정 필요
- `429`: 일정 시간 후 재시도
- `500`, `503`: 서버 또는 의존성 문제
- 작업 진행 중: 같은 키로 다시 조회하거나 polling

재시도 정책은 클라이언트와 서버가 함께 맞춰야 합니다. 서버가 중복 실행에 약한데 클라이언트가 공격적으로 재시도하면 작은 지연도 데이터 오류로 이어집니다.

## 운영 로그에 재실행 흔적을 남긴다

요청 재실행 문제는 발생 후 추적이 어렵습니다. 로그에 idempotency key, 요청 주체, 원본 요청 ID, 중복 감지 여부를 남겨야 합니다. 그래야 사용자가 "두 번 결제된 것 같다"고 말했을 때 실제 처리 흐름을 따라갈 수 있습니다.

백엔드 안정성은 실패하지 않는 코드에서 나오지 않습니다. 실패하고, 끊기고, 다시 들어오는 현실을 기준으로 설계할 때 생깁니다. 부작용이 있는 API라면 첫 구현부터 요청 재실행을 정상 흐름으로 다루는 편이 낫습니다.
