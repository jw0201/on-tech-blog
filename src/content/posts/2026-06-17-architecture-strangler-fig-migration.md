레거시 시스템을 보면 새로 만들고 싶어집니다. 오래된 프레임워크, 불명확한 도메인 모델, 테스트 없는 코드가 한꺼번에 보이기 때문입니다. 하지만 전체 재작성은 위험합니다. 새 시스템을 완성하기 전까지 가치는 나오지 않고, 기존 시스템의 숨은 규칙을 놓치기 쉽습니다. 스트랭글러 패턴은 이 위험을 줄이는 마이그레이션 방식입니다.

핵심은 기존 시스템을 바로 제거하지 않고, 바깥에 새 경계를 만든 뒤 기능별로 트래픽을 조금씩 옮기는 것입니다.

## 먼저 경계를 감싼다

스트랭글러 패턴의 시작은 새 서비스 개발이 아니라 경계 만들기입니다. 클라이언트가 레거시에 직접 붙어 있다면 중간에 라우팅 계층을 둡니다. API 게이트웨이, BFF, 프록시, 모듈 인터페이스 등 형태는 시스템에 따라 다릅니다.

이 경계가 있어야 일부 요청은 기존 시스템으로 보내고, 일부 요청은 새 구현으로 보낼 수 있습니다. 경계 없이 내부 코드만 새로 만들면 전환 지점을 잡기 어렵고, 결국 큰 배포 한 번에 의존하게 됩니다.

## 기능을 얇게 잘라 옮긴다

마이그레이션 단위는 기술 레이어보다 사용자 기능이 좋습니다. 예를 들어 "주문 저장소를 새 DB로 교체"보다 "주문 조회 API 중 읽기 전용 화면부터 전환"이 안전합니다. 기능 단위로 옮기면 사용자 영향과 성공 기준을 정의하기 쉽습니다.

처음에는 쓰기보다 읽기를 옮기는 편이 낫습니다. 읽기 경로는 비교와 롤백이 쉽습니다. 새 구현과 기존 구현의 응답을 샘플링해서 비교하고, 차이가 줄어들면 트래픽을 늘립니다.

## 데이터 소유권을 서두르지 않는다

스트랭글러 마이그레이션에서 가장 어려운 부분은 데이터입니다. 새 서비스가 생겼다고 바로 DB 소유권을 옮기면 동기화 문제가 생깁니다. 처음에는 기존 DB를 읽거나, 이벤트를 받아 별도 읽기 모델을 만드는 방식이 현실적일 수 있습니다.

중요한 것은 임시 상태를 명시하는 것입니다. "새 서비스가 기존 DB를 직접 읽는다"는 구조가 영원히 남으면 레거시가 하나 더 생깁니다. 언제 데이터 소유권을 옮길지, 어떤 의존성을 제거해야 완료인지 기준을 둬야 합니다.

## 비교 관측을 넣는다

새 구현이 기존 시스템과 같은 결과를 내는지 확인하려면 관측 장치가 필요합니다. 읽기 API라면 그림자 요청을 보내 두 응답을 비교할 수 있습니다. 쓰기 기능이라면 이벤트 로그와 감사 테이블을 비교할 수 있습니다.

비교 결과는 단순 성공/실패보다 차이 유형을 남기는 편이 좋습니다. 필드 누락, 정렬 차이, 반올림 차이, 권한 차이처럼 나누면 실제 결함과 허용 가능한 차이를 구분할 수 있습니다.

## 완료 조건을 적는다

마이그레이션은 시작보다 끝내기가 어렵습니다. 새 시스템이 대부분의 트래픽을 처리해도 일부 배치나 관리자 기능이 레거시에 남을 수 있습니다. 그래서 시작할 때 완료 조건을 적어야 합니다.

- 특정 API 트래픽 100% 전환
- 기존 테이블 쓰기 중단
- 레거시 배치 제거
- 운영 런북과 알림 새 시스템 기준으로 변경
- 관련 코드와 인프라 삭제

삭제까지 포함해야 진짜 완료입니다. 그렇지 않으면 비용은 두 시스템을 모두 운영하는 형태로 남습니다.

## 체크리스트

- 클라이언트와 레거시 사이에 전환 가능한 경계를 만든다.
- 기술 레이어보다 사용자 기능 단위로 옮긴다.
- 읽기 경로부터 시작해 비교와 롤백 가능성을 확보한다.
- 데이터 소유권 이전은 별도 단계로 계획한다.
- 완료 조건에 레거시 코드와 인프라 삭제를 포함한다.

스트랭글러 패턴은 느려 보이지만, 운영 중인 시스템을 바꾸는 현실적인 속도입니다. 한 번에 새로 쓰는 대신 매주 작은 위험을 줄이면 마이그레이션은 프로젝트가 아니라 지속적인 개선이 됩니다.
