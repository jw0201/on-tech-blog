감사 로그는 평소에는 잘 보이지 않습니다. 하지만 권한 변경, 데이터 삭제, 결제 설정 변경 같은 일이 문제를 만들면 가장 먼저 찾게 되는 자료입니다. 이때 로그가 "업데이트됨" 정도만 남아 있으면 원인을 추적하기 어렵습니다. 감사 로그는 저장 자체보다 나중에 읽을 사람을 위해 설계해야 합니다.

## 다섯 가지를 빠뜨리지 않는다

감사 로그의 기본 구성은 단순합니다.

- 누가: 행위를 수행한 사용자 또는 시스템
- 무엇을: 수행한 행동
- 어디에: 대상 리소스
- 결과는: 성공, 실패, 거부
- 맥락은: 요청 ID, IP, 사용자 에이전트, 이유

예를 들어 팀 멤버 권한 변경이라면 다음처럼 남길 수 있습니다.

```json
{
  "actorId": "user_123",
  "action": "team.member.role_changed",
  "targetId": "team_456:user_789",
  "result": "succeeded",
  "metadata": {
    "fromRole": "viewer",
    "toRole": "admin",
    "requestId": "req_abc"
  }
}
```

행동 이름은 사람이 읽을 수 있어야 하고, 기계가 필터링할 수 있을 만큼 일관되어야 합니다.

## 변경 전후를 남긴다

감사 로그는 최종 상태만으로 부족한 경우가 많습니다. "관리자로 변경됨"보다 "viewer에서 admin으로 변경됨"이 훨씬 유용합니다. 설정값, 권한, 보안 정책처럼 중요한 변경에는 이전 값과 이후 값을 남깁니다.

다만 민감 정보는 그대로 남기면 안 됩니다. 비밀번호, API 키, 토큰 원문은 감사 로그에도 저장하지 않습니다. 필요하다면 마지막 4자리, 해시, 키 ID처럼 식별 가능한 최소 정보만 남깁니다.

## 실패와 거부도 기록한다

성공한 작업만 기록하면 공격 시도를 놓칠 수 있습니다. 권한이 없는 사용자가 관리자 기능을 여러 번 호출했거나, 만료된 토큰으로 중요한 API에 접근했다면 이것도 감사 대상입니다.

실패 로그는 너무 많아질 수 있으므로 모든 404를 감사 로그에 넣을 필요는 없습니다. 하지만 권한, 인증, 결제, 데이터 내보내기, 관리자 기능처럼 보안 의미가 큰 실패는 별도 이벤트로 남기는 편이 좋습니다.

## 애플리케이션 로그와 분리한다

감사 로그는 디버깅 로그와 목적이 다릅니다. 애플리케이션 로그는 문제를 빨리 찾기 위해 상세하고 일시적일 수 있습니다. 감사 로그는 나중에 조사와 증빙을 위해 오래 보존되어야 합니다. 따라서 저장소, 보존 기간, 접근 권한을 분리하는 것이 좋습니다.

특히 감사 로그를 수정하거나 삭제할 수 있는 권한은 제한해야 합니다. 운영자가 실수로 지울 수 있는 위치에만 두면 사고 조사 자료로 신뢰하기 어렵습니다.

## 검색 가능한 형태로 저장한다

감사 로그는 쌓아두기만 하면 가치가 떨어집니다. 사고가 났을 때 다음 질문에 빠르게 답할 수 있어야 합니다.

- 특정 사용자가 최근 24시간 동안 무엇을 했는가?
- 이 리소스를 누가 삭제했는가?
- 관리자 권한이 언제 누구에게 부여됐는가?
- 실패한 로그인과 권한 거부가 특정 IP에 몰려 있는가?

이 질문에 필요한 필드는 구조화된 컬럼이나 인덱스로 관리합니다. 전부 문자열 메시지에 묻어두면 검색이 어려워집니다.

## 체크리스트

- 주체, 행위, 대상, 결과, 맥락을 구조화해서 남긴다.
- 중요한 변경은 이전 값과 이후 값을 기록한다.
- 민감 정보 원문은 감사 로그에도 저장하지 않는다.
- 권한 거부와 인증 실패처럼 의미 있는 실패도 기록한다.
- 디버깅 로그와 보존 정책, 접근 권한을 분리한다.

감사 로그는 사고가 난 뒤에야 품질이 드러납니다. 그때 필요한 것은 많은 로그가 아니라 정확한 질문에 답할 수 있는 로그입니다. 미래의 조사자를 사용자라고 생각하면 무엇을 남겨야 할지 더 분명해집니다.
