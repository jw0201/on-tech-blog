서비스 간 호출이 늘어나면 내부 토큰도 늘어납니다. 처음에는 `INTERNAL_API_KEY` 하나로 충분해 보이지만, 시간이 지나면 이 키가 결제, 사용자 정보, 관리자 기능까지 모두 접근할 수 있는 만능 열쇠가 됩니다. 유출되거나 오용되면 피해 범위를 가늠하기 어렵습니다.

서비스 토큰의 기본 원칙은 짧게 살고 좁게 접근하는 것입니다.

## 토큰마다 주체를 분리한다

모든 내부 서비스가 같은 키를 쓰면 감사가 불가능합니다. 어떤 서비스가 어떤 요청을 했는지 로그에서 구분할 수 없고, 문제가 생겨도 전체 키를 회전해야 합니다.

토큰에는 호출 주체가 드러나야 합니다.

```json
{
  "sub": "service:billing-worker",
  "aud": "payments-api",
  "scope": ["payment.read", "payment.capture"],
  "exp": 1781496000
}
```

`sub`는 누가 호출하는지, `aud`는 어느 서비스를 대상으로 하는지, `scope`는 무엇을 할 수 있는지 나타냅니다. 이 세 가지가 분리되어야 정책을 세밀하게 적용할 수 있습니다.

## 범위는 API 기능 기준으로 작게 나눈다

`admin`이나 `internal` 같은 넓은 스코프는 편하지만 위험합니다. 서비스별 필요한 행동을 기준으로 스코프를 나눕니다.

- `user.read`
- `user.email.update`
- `invoice.issue`
- `payment.capture`
- `report.export`

너무 잘게 쪼개도 운영이 어려워집니다. 기준은 "이 권한이 유출되었을 때 영향 범위를 설명할 수 있는가"입니다. 설명이 너무 넓으면 스코프가 큰 것입니다.

## 만료 시간을 짧게 둔다

장기 고정 토큰은 회전되지 않고 방치되기 쉽습니다. 가능하면 서비스는 짧은 수명의 토큰을 발급받아 사용해야 합니다. 클라우드 IAM, workload identity, 사내 토큰 발급 서비스 같은 방식이 여기에 해당합니다.

만료가 짧으면 유출 피해 시간이 줄어듭니다. 대신 운영 안정성을 위해 자동 갱신과 캐시 전략이 필요합니다. 토큰 발급 서비스 장애가 전체 서비스 장애로 번지지 않게 짧은 캐시와 재시도 정책을 둡니다.

## 회전은 이벤트가 아니라 루틴이어야 한다

토큰 회전을 보안 사고 후 이벤트로만 하면 대부분 늦습니다. 정기 회전을 자동화하고, 회전 가능한 구조인지 계속 검증해야 합니다.

회전 가능한 시스템은 다음 조건을 만족합니다.

- 새 토큰을 먼저 배포할 수 있다.
- 이전 토큰과 새 토큰을 잠깐 함께 허용할 수 있다.
- 어떤 서비스가 이전 토큰을 계속 쓰는지 로그로 찾을 수 있다.
- 이전 토큰을 폐기한 뒤 실패율을 확인할 수 있다.

이중 허용 기간이 없으면 회전은 배포 순서 싸움이 됩니다. 특히 여러 팀이 운영하는 서비스에서는 실패하기 쉽습니다.

## 감사 로그에는 권한 판단 결과를 남긴다

토큰 검증 실패만 로그에 남기면 부족합니다. 중요한 API는 성공한 권한 판단도 남겨야 합니다.

- 호출 주체
- 대상 리소스
- 요청한 스코프
- 허용 또는 거부 결과
- 거부 이유
- 요청 ID

민감한 원문 토큰은 절대 로그에 남기지 않습니다. 필요하면 토큰 ID나 해시 일부만 남깁니다. 감사 로그는 사고 후 원인을 찾는 도구이자 권한 정책을 개선하는 자료입니다.

## 체크리스트

- 내부 서비스마다 별도 주체를 둔다.
- `sub`, `aud`, `scope`, `exp`를 구분해 검증한다.
- 스코프는 유출 영향 범위를 설명할 수 있을 만큼 좁힌다.
- 장기 고정 토큰보다 짧은 수명과 자동 갱신을 우선한다.
- 토큰 회전을 정기 루틴으로 자동화한다.
- 감사 로그에는 권한 판단 결과를 남기되 원문 토큰은 기록하지 않는다.

내부망이라고 안전한 것은 아닙니다. 서비스 토큰을 사용자 권한만큼 진지하게 다루면, 작은 실수가 전체 시스템 권한으로 번지는 일을 줄일 수 있습니다.
