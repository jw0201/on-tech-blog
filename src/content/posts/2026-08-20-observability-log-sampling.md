로그는 많을수록 안심되는 것처럼 보입니다. 하지만 트래픽이 커지면 저장 비용, 검색 비용, 개인정보 위험이 함께 커집니다. 그래서 로그 샘플링이 필요합니다. 문제는 샘플링을 단순히 10%로 줄이면 장애 상황에서 필요한 로그까지 사라질 수 있다는 점입니다.

좋은 로그 샘플링은 비용을 줄이면서도 분석 가능한 흔적을 남깁니다. 핵심은 모든 로그를 같은 확률로 버리지 않는 것입니다.

## 로그의 목적을 나눈다

로그는 목적이 다릅니다. 디버깅용 상세 로그, 감사 로그, 오류 로그, 접근 로그를 같은 정책으로 샘플링하면 안 됩니다.

일반적으로 다음처럼 구분합니다.

- 감사 로그: 샘플링하지 않는다.
- 보안 이벤트: 샘플링하지 않거나 별도 보존한다.
- 오류 로그: 기본적으로 보존한다.
- 성공 접근 로그: 비율 샘플링한다.
- 반복적인 debug 로그: 강하게 샘플링하거나 비활성화한다.

특히 감사 로그는 비용 문제가 있어도 함부로 줄이면 안 됩니다. 나중에 "누가 무엇을 했는가"를 증명해야 하는 로그이기 때문입니다.

## 오류와 느린 요청은 우선 보존한다

성공 요청은 일부만 있어도 통계 분석이 가능합니다. 하지만 오류 요청은 한 건의 샘플이 장애 원인을 알려줄 수 있습니다.

샘플링 예외로 둘 신호는 다음과 같습니다.

- 5xx 응답
- 인증과 권한 실패
- 외부 의존성 timeout
- 매우 느린 요청
- 재시도 한도 초과
- 데이터 불일치 감지

이런 로그는 기본 샘플링 비율과 별도로 보존합니다. 그래야 평소에는 비용을 줄이면서도 장애 순간에는 필요한 정보가 남습니다.

## 요청 단위 샘플링을 고려한다

로그 라인마다 독립적으로 샘플링하면 한 요청의 앞부분 로그는 있고 뒷부분 로그는 없는 상태가 됩니다. 이런 로그는 흐름을 재구성하기 어렵습니다.

요청 단위 샘플링은 request id나 trace id를 기준으로 보존 여부를 결정합니다. 한 요청이 선택되면 관련 로그를 함께 남깁니다. 이렇게 하면 샘플 수는 적어도 한 요청의 이야기는 온전히 볼 수 있습니다.

분산 시스템에서는 trace sampling과 로그 샘플링을 연결하는 것도 유용합니다. 선택된 trace의 주요 로그를 보존하면 추적과 로그가 함께 읽힙니다.

## 동적 샘플링을 준비한다

평상시와 장애 시의 로그 요구량은 다릅니다. 평소에는 성공 로그를 1%만 보존해도 충분할 수 있지만, 특정 엔드포인트 장애가 나면 그 구간의 로그를 일시적으로 늘리고 싶습니다.

동적 샘플링에는 운영 장치가 필요합니다.

- 서비스별 샘플링 비율 변경
- 엔드포인트별 예외 설정
- 특정 tenant나 request id 보존
- 시간 제한이 있는 debug 로그 활성화
- 변경 이력 기록

시간 제한이 없으면 임시 debug 로그가 영구 비용이 됩니다. 모든 동적 변경에는 만료 시간을 두는 편이 좋습니다.

## 샘플링 후에도 지표는 남긴다

로그를 줄였다고 관측이 사라지면 안 됩니다. 샘플링으로 원문 로그를 버리더라도 카운터와 히스토그램 같은 지표는 남겨야 합니다.

예를 들어 성공 접근 로그를 5%만 저장하더라도 총 요청 수, 오류율, 지연 시간 분포는 메트릭으로 완전하게 집계해야 합니다. 로그는 사례를 설명하고, 메트릭은 전체 흐름을 보여줍니다.

로그 샘플링은 비용 절감 설정이 아니라 관측 설계입니다. 어떤 로그를 절대 보존할지, 어떤 요청을 묶어서 남길지, 장애 시 어떻게 비율을 바꿀지 정해야 합니다. 잘 설계하면 로그 비용은 줄이면서도 장애 대응 능력은 잃지 않을 수 있습니다.
