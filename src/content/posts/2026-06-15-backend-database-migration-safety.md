데이터베이스 마이그레이션은 코드 배포보다 되돌리기 어렵습니다. 애플리케이션은 이전 버전으로 롤백할 수 있지만 이미 삭제된 컬럼, 변환된 데이터, 실패한 인덱스 생성은 간단히 되돌릴 수 없습니다. 그래서 마이그레이션은 "한 번에 바꾸기"보다 "배포 가능한 작은 단계"로 나누어야 합니다.

실무에서 가장 안전한 기본 패턴은 확장, 전환, 정리입니다.

## 1단계: 먼저 호환 가능한 구조를 추가한다

새 요구사항 때문에 `full_name`을 `first_name`, `last_name`으로 나누어야 한다고 가정해 봅니다. 위험한 방식은 기존 컬럼을 바로 삭제하고 새 컬럼을 필수로 만드는 것입니다. 이전 코드가 남아 있는 서버, 배치, 관리자 도구가 모두 깨질 수 있습니다.

첫 배포에서는 새 컬럼만 추가합니다.

```sql
ALTER TABLE users ADD COLUMN first_name text;
ALTER TABLE users ADD COLUMN last_name text;
```

이 단계의 원칙은 기존 코드가 계속 동작해야 한다는 것입니다. 새 컬럼은 nullable로 시작하고, 인덱스도 가능하면 온라인 생성 옵션을 사용합니다. 큰 테이블에서 잠금이 걸리는 DDL은 배포 시간보다 운영 리스크가 큽니다.

## 2단계: 쓰기 경로를 이중화한다

다음 배포에서는 애플리케이션이 기존 컬럼과 새 컬럼을 함께 씁니다. 읽기는 아직 기존 컬럼을 사용해도 됩니다. 이중 쓰기를 잠깐 유지하면 롤백 여지가 생깁니다.

```ts
await updateUser(userId, {
  fullName: `${firstName} ${lastName}`,
  firstName,
  lastName,
});
```

이때 중요한 것은 두 값이 어긋났을 때의 우선순위입니다. 새 값이 기준인지, 기존 값이 기준인지 정하지 않으면 디버깅이 어려워집니다. 가능하면 전환 기간 동안 불일치율을 메트릭으로 남깁니다.

## 3단계: 백필은 배포와 분리한다

기존 데이터 채우기는 애플리케이션 배포 스크립트에 넣지 않는 편이 좋습니다. 배포는 빠르게 끝나야 하고, 백필은 느리며 중단 가능해야 합니다.

백필 작업은 다음 속성을 가져야 합니다.

- 작은 배치 단위로 처리한다.
- 이미 처리한 행은 다시 실행해도 안전하다.
- 진행률과 실패 수를 기록한다.
- 트래픽이 높은 시간에는 멈출 수 있다.
- 데이터베이스 부하 제한을 둔다.

예를 들어 `WHERE first_name IS NULL LIMIT 1000` 같은 방식으로 반복 처리하면 재시작이 쉽습니다. 대량 업데이트 하나로 끝내려는 욕심은 잠금과 복제 지연을 만들 수 있습니다.

## 4단계: 읽기 경로를 새 구조로 전환한다

백필이 충분히 끝나고 이중 쓰기가 안정적이면 읽기 경로를 새 컬럼으로 바꿉니다. 이 배포 이후에도 기존 컬럼은 바로 지우지 않습니다. 롤백할 때 이전 코드가 필요로 하기 때문입니다.

전환 직후에는 새 읽기 결과와 기존 읽기 결과를 샘플링해서 비교하는 것도 좋습니다. 사용자에게 보이는 값이 바뀌는 마이그레이션이라면 더더욱 그렇습니다.

## 5단계: 마지막에 제약과 삭제를 적용한다

충분한 시간이 지난 뒤 정리 배포를 합니다. 새 컬럼에 `NOT NULL` 제약을 추가하고, 더 이상 쓰지 않는 컬럼을 제거합니다. 이 단계도 별도 배포로 두면 문제 발생 시 원인을 좁히기 쉽습니다.

삭제는 가장 마지막입니다. 특히 외부 분석 쿼리, 데이터 파이프라인, 고객지원 도구가 직접 DB 컬럼을 참조하는 조직에서는 코드 검색만으로 안전성을 판단하면 안 됩니다.

## 체크리스트

- 기존 코드와 호환되는 구조를 먼저 추가한다.
- 쓰기 전환과 읽기 전환을 같은 배포에 묶지 않는다.
- 백필은 재시작 가능하고 멱등적으로 만든다.
- 큰 테이블 DDL의 잠금과 복제 지연을 확인한다.
- 컬럼 삭제는 충분한 관측 기간 뒤 별도로 진행한다.

좋은 마이그레이션은 화려하지 않습니다. 작고 지루하며, 되돌릴 수 있는 중간 상태를 남깁니다. 운영 환경에서는 그 지루함이 가장 값싼 보험입니다.
