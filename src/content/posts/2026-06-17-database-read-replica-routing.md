읽기 복제본은 데이터베이스 부하를 줄이는 흔한 방법입니다. 쓰기는 primary에 보내고, 조회는 replica로 보내면 primary의 부담을 낮출 수 있습니다. 하지만 복제본은 공짜 성능 향상이 아닙니다. 복제 지연 때문에 사용자가 방금 쓴 데이터를 바로 못 보는 문제가 생길 수 있습니다.

## 복제 지연을 정상 상황으로 본다

읽기 복제본은 primary의 변경을 따라옵니다. 대부분 빠르지만 항상 즉시는 아닙니다. 트래픽이 몰리거나 큰 마이그레이션, 장기 트랜잭션, 네트워크 문제가 있으면 지연이 커질 수 있습니다.

따라서 설계의 기본 가정은 "replica는 잠깐 오래된 데이터를 줄 수 있다"여야 합니다. 이 사실을 숨기고 모든 읽기를 복제본으로 보내면 사용자 경험이 흔들립니다.

예를 들어 사용자가 프로필을 수정한 직후 이전 이름이 보이면 저장 실패로 오해할 수 있습니다. 이런 화면은 성능보다 읽기 일관성이 중요합니다.

## 방금 쓴 사용자는 primary에서 읽는다

가장 실용적인 정책은 쓰기 직후 일정 시간 동안 같은 사용자의 읽기를 primary로 보내는 것입니다. 이를 read-after-write 보장이라고 볼 수 있습니다.

구현 방식은 단순할 수 있습니다. 세션이나 요청 컨텍스트에 최근 쓰기 시각을 기록하고, 짧은 기간 동안 primary를 사용합니다.

```ts
function shouldReadFromPrimary(context: RequestContext) {
  return Date.now() - context.lastWriteAt < 5000;
}
```

시간 기준은 서비스 특성에 따라 달라집니다. 복제 지연 메트릭을 보고 현실적인 값을 정해야 합니다.

## 읽기 종류를 분류한다

모든 조회가 같은 일관성을 필요로 하지는 않습니다.

- 방금 수정한 내 정보: primary 권장
- 관리자 통계 대시보드: replica 가능
- 검색 결과와 추천 목록: replica 가능
- 결제 상태와 권한 확인: primary 권장
- 알림 읽음 상태: 제품 정책에 따라 결정

이 분류를 코드에 반영하면 라우팅이 명확해집니다. 단순히 `findUser`는 replica, `updateUser`는 primary처럼 함수 단위로만 나누면 실제 사용 맥락을 놓칠 수 있습니다.

## 지연을 관측한다

읽기 복제본을 운영한다면 복제 지연 메트릭은 필수입니다. 평균보다 p95, p99 지연을 보는 편이 좋습니다. 장애는 보통 꼬리 지연에서 드러납니다.

애플리케이션 로그에도 어떤 요청이 primary를 읽었는지 replica를 읽었는지 남기면 디버깅이 쉬워집니다. 사용자가 "저장했는데 안 보여요"라고 말할 때 replica 지연인지, 캐시 문제인지, 실제 저장 실패인지 구분할 수 있습니다.

## 장애 시 우회 정책을 둔다

replica가 느려지거나 끊겼을 때 어떻게 할지도 정해야 합니다. 모든 읽기를 primary로 돌리면 서비스는 살아날 수 있지만 primary 부하가 급격히 늘어납니다. 반대로 replica 오류를 그대로 사용자에게 내보내면 가용성이 떨어집니다.

실무에서는 기능별로 우선순위를 둡니다. 핵심 사용자 흐름은 primary로 우회하고, 무거운 통계나 비핵심 목록은 일시적으로 제한할 수 있습니다. 이 정책은 장애 중에 즉흥적으로 정하기보다 미리 런북에 남기는 편이 좋습니다.

## 체크리스트

- replica는 잠깐 오래된 데이터를 줄 수 있다고 가정한다.
- 쓰기 직후 사용자의 읽기는 primary로 보내는 정책을 둔다.
- 조회 기능별로 필요한 일관성 수준을 분류한다.
- 복제 지연과 라우팅 결정을 로그와 메트릭으로 남긴다.
- replica 장애 시 primary 우회 범위와 제한할 기능을 정한다.

읽기 복제본은 성능 도구이지만, 사용자에게는 데이터 일관성 문제로 보입니다. 빠른 조회와 믿을 수 있는 화면 사이의 균형을 코드에 명시해야 안전하게 쓸 수 있습니다.
