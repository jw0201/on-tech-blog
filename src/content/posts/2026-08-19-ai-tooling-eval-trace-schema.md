AI 도구의 품질은 데모에서는 좋아 보이다가 실제 업무에서는 애매해지는 경우가 많습니다. 이유 중 하나는 실패를 재현할 기록이 부족하기 때문입니다. "이번 답이 별로였다"는 느낌만 남고, 어떤 컨텍스트에서 어떤 도구 호출을 거쳐 어떤 결과가 나왔는지 추적하기 어렵습니다.

평가를 제대로 하려면 프롬프트와 최종 답변만 저장해서는 부족합니다. 에이전트가 본 정보, 선택한 도구, 수정한 파일, 검증 결과까지 하나의 트레이스로 남겨야 합니다.

## 평가 단위를 작업으로 잡는다

모델 호출 하나를 평가 단위로 잡으면 실제 품질과 멀어집니다. 사용자가 원하는 것은 한 번의 답변이 아니라 작업 완료입니다. 코드 수정, 문서 생성, 장애 분석처럼 여러 단계가 필요한 업무에서는 중간 판단이 결과를 크게 좌우합니다.

트레이스의 최상위 단위는 다음 정보를 가져야 합니다.

```json
{
  "taskId": "eval_20260819_001",
  "intent": "fix_test_failure",
  "repository": "checkout-service",
  "startedAt": "2026-08-19T00:00:00Z",
  "result": "passed"
}
```

`intent`는 자유 텍스트보다 제한된 enum이 좋습니다. 그래야 같은 종류의 작업끼리 비교할 수 있습니다.

## 컨텍스트 출처를 기록한다

AI 도구는 어떤 정보를 봤는지에 따라 답이 달라집니다. 그래서 단순히 "컨텍스트를 제공했다"가 아니라 어떤 파일, 문서, 로그, 검색 결과가 들어갔는지 기록해야 합니다.

유용한 필드는 다음과 같습니다.

- `sourceType`: file, terminal, web, issue, user_message
- `sourceId`: 파일 경로, URL, 이슈 번호 등
- `range`: 파일이면 줄 범위
- `summary`: 긴 내용을 요약한 짧은 설명
- `includedAt`: 컨텍스트에 들어간 시각

민감한 원문을 모두 저장하기 어렵다면 해시와 요약만 남길 수 있습니다. 중요한 것은 나중에 같은 조건을 최대한 복원할 수 있어야 한다는 점입니다.

## 도구 호출은 입력과 결과를 나눈다

에이전트 평가에서 도구 호출은 핵심입니다. 같은 모델이라도 파일 검색을 잘못하거나 테스트를 건너뛰면 결과가 달라집니다.

각 도구 호출에는 최소한 다음을 남깁니다.

```json
{
  "tool": "shell",
  "purpose": "run_unit_tests",
  "input": "npm test -- --runInBand",
  "exitCode": 0,
  "durationMs": 18320
}
```

출력 전체를 저장하면 비용과 보안 문제가 생깁니다. 대신 실패 원인, 마지막 몇 줄, 구조화된 요약을 저장하는 방식이 현실적입니다.

## 평가 기준은 후처리 가능해야 한다

최종 결과를 `good` 또는 `bad`로만 저장하면 나중에 분석하기 어렵습니다. 더 나은 방식은 자동 기준과 사람 기준을 분리하는 것입니다.

- 빌드 통과 여부
- 테스트 통과 여부
- 린트 통과 여부
- 수정 파일 수
- 사용자 재작업 필요 여부
- 보안 정책 위반 여부

자동 기준은 CI에서 바로 채울 수 있고, 사람 기준은 리뷰어가 나중에 붙일 수 있습니다. 두 기준을 분리하면 모델이 테스트는 통과했지만 설계가 나쁜 경우를 따로 볼 수 있습니다.

## 실패 사례를 자산으로 만든다

트레이스의 가장 큰 가치는 실패를 축적하는 데 있습니다. 실패 트레이스가 있으면 프롬프트를 바꿨을 때 정말 좋아졌는지 확인할 수 있습니다. 또한 특정 작업 유형에서 반복되는 약점을 찾을 수 있습니다.

예를 들어 다음 질문에 답할 수 있습니다.

- 테스트 실패 수정에서는 컨텍스트 부족이 많은가, 잘못된 수정이 많은가.
- 문서 작업에서는 사용자의 톤을 얼마나 자주 놓치는가.
- 보안 관련 작업에서는 검증 명령을 충분히 실행하는가.

AI 도구 평가는 모델 이름 비교가 아니라 작업 품질 관리입니다. 트레이스 스키마를 먼저 만들면 새 모델이나 새 프롬프트를 도입할 때 감이 아니라 기록으로 판단할 수 있습니다.
