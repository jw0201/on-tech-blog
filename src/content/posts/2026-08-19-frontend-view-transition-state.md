뷰 전환은 페이지가 바뀔 때 살짝 움직이는 애니메이션만을 뜻하지 않습니다. 사용자는 화면이 바뀌는 동안 현재 작업이 유지되는지, 새 화면이 준비되었는지, 실패했을 때 어디로 돌아갈 수 있는지를 함께 판단합니다.

그래서 전환을 `route change` 이벤트 하나로 처리하면 금방 한계가 옵니다. 목록에서 상세로 들어갈 때, 모달을 닫을 때, 필터를 바꿀 때, 탭을 이동할 때 필요한 정책이 모두 다르기 때문입니다.

## 전환의 목적을 먼저 나눈다

모든 전환이 같은 의미를 갖지는 않습니다.

- 탐색 전환: 사용자가 다른 리소스로 이동한다.
- 상태 전환: 같은 화면 안에서 조건이나 모드가 바뀐다.
- 작업 전환: 저장, 승인, 삭제 같은 명령 이후 화면이 갱신된다.
- 복구 전환: 실패 후 이전 상태나 안전한 상태로 돌아간다.

탐색 전환에서는 새 화면의 위치와 제목이 중요합니다. 상태 전환에서는 기존 맥락을 얼마나 유지할지가 중요합니다. 작업 전환에서는 명령이 반영되었는지 확인할 수 있어야 합니다.

이 구분이 없으면 모든 변화에 같은 skeleton, 같은 fade, 같은 스크롤 초기화를 붙이게 됩니다.

## 데이터 보존 정책을 명시한다

전환 중 데이터를 언제 지울지 결정해야 합니다. 예를 들어 검색 필터를 바꿨을 때 기존 목록을 바로 지우면 조건 변경은 명확하지만 화면이 비어 보입니다. 반대로 기존 목록을 유지하면 안정적이지만 사용자는 새 조건이 적용되었는지 헷갈릴 수 있습니다.

실무에서는 다음처럼 정책을 나누면 좋습니다.

- 같은 리소스의 정렬 변경은 기존 데이터를 유지하고 pending 표시를 붙인다.
- 리소스 ID가 바뀌는 상세 이동은 본문 skeleton으로 전환한다.
- 폼 제출 후 결과 반영은 낙관적 UI와 서버 확인 상태를 분리한다.
- 권한 변경처럼 의미가 큰 전환은 이전 화면을 남기지 않는다.

중요한 것은 `keepPreviousData` 같은 옵션을 습관적으로 켜는 것이 아니라, 사용자가 보는 의미를 기준으로 결정하는 것입니다.

## 포커스와 스크롤도 상태다

화면이 바뀌었는데 포커스가 사라지거나 스크롤이 예상 밖으로 움직이면 사용자는 흐름을 잃습니다. 특히 키보드 사용자와 스크린 리더 사용자에게는 전환 애니메이션보다 포커스 이동이 더 큰 신호입니다.

기본 규칙은 단순합니다.

- 페이지 수준 탐색은 제목 영역이나 주요 컨텐츠로 포커스를 이동한다.
- 탭 전환은 탭 목록의 현재 위치를 유지한다.
- 모달 종료는 모달을 연 버튼으로 포커스를 되돌린다.
- 목록 상세 왕복은 가능한 경우 목록 위치를 복원한다.

스크롤 복원도 브라우저에게만 맡기기 어렵습니다. 필터가 바뀌어 목록 내용 자체가 달라졌다면 이전 스크롤을 복원하는 것이 오히려 이상할 수 있습니다.

## 실패 전환을 준비한다

전환은 실패할 수 있습니다. 다음 화면의 데이터가 오지 않거나, 저장 후 갱신이 실패하거나, 권한이 사라질 수 있습니다. 이때 전환 상태가 없으면 사용자는 빈 화면이나 깨진 중간 상태를 보게 됩니다.

좋은 전환 모델은 최소한 다음 상태를 갖습니다.

- 이전 상태
- 전환 중 상태
- 새 상태
- 실패 후 복구 상태

예를 들어 결제 수단 변경 후 서버 반영이 실패하면 단순히 토스트 하나를 띄우는 것보다 이전 결제 수단을 복원하고 실패한 명령만 다시 시도할 수 있게 해야 합니다.

## 테스트는 움직임보다 계약을 본다

전환 테스트는 애니메이션 프레임을 세밀하게 검증하기보다 사용자가 기대하는 계약을 확인해야 합니다.

확인할 항목은 다음과 같습니다.

1. 전환 중 클릭 가능한 영역이 의도대로 잠기는가.
2. 이전 데이터가 유지되는 경우 갱신 중임이 보이는가.
3. 실패했을 때 이전 상태와 재시도 동선이 남는가.
4. 포커스와 스크롤이 전환 종류에 맞게 이동하는가.

뷰 전환을 시각 효과로만 보면 멋진 순간은 만들 수 있지만 안정적인 흐름은 만들기 어렵습니다. 전환을 상태 모델로 다루면 사용자는 화면이 바뀌는 동안에도 어디에 있고 무엇을 할 수 있는지 이해할 수 있습니다.
