배포 파이프라인에서 `npm test`와 이미지 빌드가 통과했다고 해서 운영 준비가 끝난 것은 아닙니다. 실제 장애는 배포 이후에 드러납니다. 환경 변수가 빠졌거나, 마이그레이션이 느리거나, 외부 API 권한이 바뀌었거나, 새 버전이 특정 라우트에서만 실패할 수 있습니다.

헬스 게이트는 이런 문제를 빠르게 감지하고 배포를 멈추는 장치입니다. 거창한 플랫폼이 없어도 작은 팀에서 충분히 시작할 수 있습니다.

## 헬스 체크는 얕은 것과 깊은 것을 나눈다

가장 흔한 실수는 `/health` 하나에 모든 것을 넣는 것입니다. 로드밸런서가 호출하는 헬스 체크가 데이터베이스, 캐시, 외부 API까지 모두 확인하면 작은 의존성 장애가 전체 서버 제거로 이어질 수 있습니다.

헬스 체크는 용도별로 나눕니다.

- `liveness`: 프로세스가 살아 있는지 확인
- `readiness`: 트래픽을 받을 준비가 되었는지 확인
- `startup`: 초기화가 끝났는지 확인
- `diagnostics`: 운영자가 상세 의존성을 확인

로드밸런서에는 가벼운 체크를 연결하고, 배포 게이트에는 조금 더 깊은 체크를 연결하는 식으로 구분합니다.

## 스모크 테스트는 사용자 경로를 얇게 통과한다

스모크 테스트는 전체 E2E 테스트가 아닙니다. 배포된 환경에서 핵심 경로가 최소한 동작하는지 확인하는 빠른 테스트입니다.

예를 들어 SaaS 앱이라면 다음 정도가 적당합니다.

- 로그인 페이지가 200으로 응답한다.
- 테스트 계정으로 로그인할 수 있다.
- 대시보드 주요 API가 성공한다.
- 읽기 전용 상세 페이지 하나가 열린다.
- 로그아웃이 동작한다.

결제나 메일 발송처럼 부작용이 큰 경로는 테스트 전용 샌드박스나 dry-run 모드가 필요합니다. 운영 데이터에 흔적을 남기는 스모크 테스트는 오래 유지되기 어렵습니다.

## 배포 중단 기준을 숫자로 정한다

"이상하면 멈춘다"는 기준은 자동화하기 어렵습니다. 배포 게이트에는 숫자가 필요합니다.

- 새 버전의 5xx 비율이 2분 동안 1%를 넘으면 중단
- p95 응답 시간이 이전 버전 대비 50% 이상 증가하면 중단
- 스모크 테스트가 2회 연속 실패하면 롤백
- 에러 로그에서 특정 치명 코드가 감지되면 중단

처음부터 완벽할 필요는 없습니다. 중요한 것은 사람의 감이 아니라 파이프라인이 읽을 수 있는 조건으로 만드는 것입니다.

## 카나리 배포와 함께 쓰면 효과가 커진다

헬스 게이트는 전체 트래픽 배포보다 카나리 배포에서 더 강력합니다. 새 버전에 5% 트래픽만 보내고 지표를 비교하면 문제를 작은 범위에서 잡을 수 있습니다.

카나리에서 봐야 할 지표는 서비스마다 다르지만 기본은 비슷합니다.

- HTTP 5xx와 주요 제품 에러 코드
- p95, p99 지연 시간
- 재시도율과 타임아웃
- 큐 적체량
- 핵심 비즈니스 이벤트 성공률

단순 인프라 지표만 보면 사용자 영향이 늦게 보일 수 있습니다. 제품 이벤트도 함께 봐야 합니다.

## 알림은 배포 정보와 연결한다

배포 직후 알림이 울렸는데 어떤 버전 때문인지 모르면 대응이 늦어집니다. 로그와 메트릭에는 버전, 커밋 SHA, 배포 환경, 인스턴스 정보를 태그로 남겨야 합니다.

대시보드에는 배포 시점을 마커로 표시합니다. 배포 마커와 지표 변화를 같은 화면에서 볼 수 있으면 원인 추정 시간이 줄어듭니다.

## 체크리스트

- `/health` 하나에 모든 확인을 넣지 않는다.
- 로드밸런서 체크와 배포 게이트 체크를 분리한다.
- 스모크 테스트는 핵심 사용자 경로를 빠르게 검증한다.
- 중단 기준을 비율, 시간, 횟수로 명시한다.
- 배포 버전 정보를 로그와 메트릭에 태그로 남긴다.

좋은 배포 파이프라인은 성공 버튼이 아니라 중단 버튼을 잘 갖춘 시스템입니다. 문제가 작을 때 멈출 수 있어야 빠르게 자주 배포할 수 있습니다.
