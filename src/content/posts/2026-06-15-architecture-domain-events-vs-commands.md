메시지 기반 시스템을 만들다 보면 모든 것이 이벤트처럼 보입니다. `UserCreated`, `SendWelcomeEmail`, `RecalculateInvoice`가 같은 큐를 타고 흐릅니다. 하지만 이 이름들은 같은 종류가 아닙니다. 어떤 것은 이미 일어난 사실이고, 어떤 것은 누군가에게 시키는 명령입니다.

도메인 이벤트와 커맨드를 구분하지 않으면 재처리, 실패 처리, 소유권이 흐려집니다.

## 이벤트는 이미 일어난 사실이다

도메인 이벤트는 과거형으로 이름 붙이는 것이 좋습니다.

- `OrderPlaced`
- `PaymentCaptured`
- `UserEmailChanged`
- `SubscriptionCancelled`

이벤트 발행자는 "이 일이 일어났다"만 알립니다. 누가 무엇을 할지는 알지 않습니다. 주문이 생성되면 이메일 서비스, 추천 시스템, 분석 파이프라인이 각자 필요한 일을 할 수 있습니다.

이 구조의 장점은 발행자와 소비자가 느슨하게 연결된다는 것입니다. 주문 서비스는 이메일 발송 성공 여부를 몰라도 됩니다.

## 커맨드는 누군가에게 시키는 요청이다

커맨드는 명령형 또는 의도 중심 이름이 자연스럽습니다.

- `SendWelcomeEmail`
- `CapturePayment`
- `GenerateMonthlyInvoice`
- `RebuildSearchIndex`

커맨드는 대상이 더 분명합니다. 누가 처리해야 하는지, 실패하면 누가 책임지는지 정해야 합니다. 결제 캡처 커맨드가 실패했는데 아무도 모르면 돈을 받지 못합니다.

커맨드는 보통 단일 소유자가 처리하고, 응답이나 상태 추적이 필요할 수 있습니다.

## 같은 메시지를 두 의미로 쓰지 않는다

나쁜 예는 `UserCreated` 이벤트를 이메일 발송 명령처럼 사용하는 것입니다. 이메일 서비스가 실패하면 `UserCreated`를 재시도합니다. 그러면 분석 서비스나 CRM 동기화도 같은 이벤트를 다시 받을 수 있습니다. 멱등성이 약하면 중복 처리가 발생합니다.

이메일 발송이 반드시 필요한 업무라면 이벤트 소비자가 내부적으로 `SendWelcomeEmail` 커맨드를 만들거나, 워크플로가 명시적으로 커맨드를 발행하는 편이 낫습니다.

이벤트 재처리는 "과거 사실을 다시 전달"하는 것이고, 커맨드 재처리는 "요청을 다시 수행"하는 것입니다. 결과가 다를 수 있으니 정책도 달라야 합니다.

## 이벤트 소비자는 독립적으로 실패해야 한다

하나의 이벤트에 여러 소비자가 붙을 때, 한 소비자의 실패가 다른 소비자를 막으면 안 됩니다. 이메일 발송 실패 때문에 분석 적재가 멈추면 결합도가 높아진 것입니다.

각 소비자는 별도 구독, 별도 재시도, 별도 데드레터 큐를 갖는 편이 좋습니다. 운영 대시보드도 소비자별로 나누어야 합니다. `OrderPlaced` 이벤트 전체 실패율보다 `OrderPlaced -> tax-sync` 실패율이 더 행동 가능한 정보입니다.

## 메시지에는 원인과 식별자를 넣는다

이벤트와 커맨드 모두 추적 가능한 식별자가 필요합니다.

```json
{
  "id": "evt_01J...",
  "type": "PaymentCaptured",
  "occurredAt": "2026-06-15T07:50:00+09:00",
  "aggregateId": "order_123",
  "causationId": "cmd_456",
  "correlationId": "req_789",
  "data": {
    "paymentId": "pay_abc",
    "amount": 49000
  }
}
```

`causationId`는 이 메시지를 만든 직접 원인이고, `correlationId`는 더 큰 사용자 요청이나 워크플로를 묶습니다. 장애 조사에서 이 둘은 큰 차이를 만듭니다.

## 체크리스트

- 이미 일어난 사실은 과거형 이벤트로 이름 붙인다.
- 특정 처리 요청은 커맨드로 분리한다.
- 이벤트 재처리와 커맨드 재시도의 의미를 구분한다.
- 이벤트 소비자는 독립적인 재시도와 데드레터 큐를 가진다.
- 메시지에는 `id`, `causationId`, `correlationId`를 포함한다.

메시지 아키텍처의 어려움은 큐를 붙이는 데 있지 않습니다. 메시지가 무엇을 의미하는지 팀이 같은 언어로 말하는 데 있습니다. 이벤트와 커맨드를 구분하면 그 언어가 훨씬 선명해집니다.
