타임아웃은 장애를 막는 가장 기본적인 장치지만, 많은 시스템에서 `30s` 같은 숫자로 방치됩니다. 문제는 타임아웃이 너무 길면 장애가 전파되고, 너무 짧으면 정상 요청까지 실패한다는 점입니다. 타임아웃은 감으로 정하는 상수가 아니라 요청 전체의 시간 예산입니다.

## 사용자 요청의 전체 예산부터 정한다

먼저 사용자가 기다릴 수 있는 시간을 정합니다. 예를 들어 API 응답 목표가 1초라면 백엔드 내부 호출 전체가 그 안에 들어와야 합니다.

```text
전체 예산: 1000ms
- 게이트웨이와 인증: 100ms
- 서비스 A 처리: 250ms
- 서비스 B 호출: 300ms
- DB 조회: 200ms
- 버퍼: 150ms
```

이렇게 나누면 각 구간의 타임아웃이 전체 목표와 연결됩니다. 반대로 모든 하위 호출에 5초 타임아웃을 주면 상위 요청의 목표는 의미가 없어집니다.

## 하위 호출은 남은 시간을 넘지 않는다

요청이 이미 600ms를 사용했다면 하위 서비스에 800ms 타임아웃을 줄 수 없습니다. 상위 요청이 먼저 끊기고 하위 작업만 계속 남을 수 있기 때문입니다. 가능하면 요청 컨텍스트에 deadline을 담아 하위 호출이 남은 시간을 계산하게 합니다.

```ts
const remainingMs = deadline.getTime() - Date.now();
const timeoutMs = Math.min(remainingMs - 50, serviceDefaultTimeoutMs);
```

여기서 50ms 같은 작은 여유는 응답 정리와 로깅을 위한 버퍼입니다. 버퍼 없이 끝까지 쓰면 상위 레이어가 에러를 정리할 시간이 없습니다.

## 재시도는 타임아웃을 늘리는 기능이 아니다

재시도를 추가하면 성공률이 올라갈 수 있지만, 전체 지연도 같이 늘어납니다. `timeout 1초, retry 3회`는 최악의 경우 3초 이상을 의미합니다. 재시도 횟수와 백오프까지 포함해서 예산 안에 들어와야 합니다.

```text
호출 예산: 300ms
- 1차 시도: 120ms
- 짧은 backoff: 30ms
- 2차 시도: 120ms
- 정리 버퍼: 30ms
```

멱등하지 않은 작업에는 재시도를 넣기 전에 요청 키, 중복 처리, 외부 시스템의 보장 범위를 먼저 확인해야 합니다. 타임아웃과 재시도는 항상 함께 설계됩니다.

## 큐와 커넥션 대기 시간도 포함한다

타임아웃을 소켓 read 시간에만 걸면 이미 늦습니다. 커넥션 풀에서 기다리는 시간, 큐에서 대기하는 시간, DNS나 TLS 준비 시간도 사용자가 체감하는 지연입니다. 라이브러리마다 어떤 구간에 타임아웃이 적용되는지 확인해야 합니다.

운영 지표도 구간별로 나눠 봐야 합니다.

- 큐 대기 시간
- 커넥션 획득 시간
- 원격 서비스 처리 시간
- 응답 본문 읽기 시간
- 재시도 횟수와 최종 실패 사유

이렇게 나눠야 타임아웃을 늘릴지, 풀 크기를 조정할지, 호출 구조를 바꿀지 판단할 수 있습니다.

## 체크리스트

- 사용자 요청의 전체 시간 예산을 먼저 정한다.
- 하위 호출 타임아웃은 남은 deadline을 넘지 않는다.
- 재시도 횟수와 backoff를 예산에 포함한다.
- 커넥션 풀 대기와 큐 대기 시간을 따로 측정한다.
- 타임아웃 실패를 서비스별, 구간별로 기록한다.

좋은 타임아웃은 요청을 빨리 포기하는 숫자가 아닙니다. 시스템이 감당할 수 있는 시간을 명확히 나누고, 장애가 한 레이어에 머물도록 만드는 경계입니다.
