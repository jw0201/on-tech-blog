AI 코딩 도구는 빠르게 초안을 만듭니다. 문제는 그 초안이 코드베이스의 실제 규칙과 어긋날 때입니다. 존재하지 않는 유틸을 호출하거나, 팀의 에러 처리 방식을 무시하거나, 테스트 없이 새로운 패턴을 만들기도 합니다. AI 코드 생성을 실무에 쓰려면 "무엇을 만들지"보다 "어디에 맞춰 만들지"를 더 구체적으로 알려줘야 합니다.

## 먼저 근거 파일을 지정한다

좋은 프롬프트는 요구사항만 말하지 않습니다. 참고해야 할 파일을 함께 줍니다. 예를 들어 새 API 엔드포인트를 만들 때는 라우터, 서비스, 테스트 파일 중 가장 비슷한 예시를 지정합니다.

```text
users 라우터와 같은 패턴으로 teams 라우터를 추가해.
참고 파일:
- src/routes/users.ts
- src/services/user-service.ts
- tests/users.test.ts
```

이렇게 하면 AI가 일반적인 Express 예제가 아니라 현재 프로젝트의 에러 처리, 검증, 테스트 스타일을 따라갈 가능성이 높아집니다.

## 금지할 선택지도 알려준다

AI는 빈칸을 채우려는 성향이 강합니다. 요구사항에 없는 라이브러리를 추가하거나, 기존 헬퍼를 찾지 못하면 새로 만들 수 있습니다. 그래서 금지 조건을 명확히 두는 편이 좋습니다.

- 새 의존성을 추가하지 않는다.
- 기존 공개 API의 응답 구조를 바꾸지 않는다.
- 인증 미들웨어를 우회하지 않는다.
- 관련 없는 리팩터링을 하지 않는다.
- 테스트가 실패하면 구현을 계속 고친다.

금지 조건은 창의성을 막기 위한 것이 아니라 리뷰 범위를 줄이기 위한 장치입니다. 변경이 작을수록 사람이 검증하기 쉽습니다.

## 완료 조건을 명령으로 준다

"잘 동작하게 해줘"는 검증 가능한 완료 조건이 아닙니다. 프로젝트에서 실제로 통과해야 하는 명령을 알려주는 편이 좋습니다.

```text
완료 전 반드시 실행:
- npm test -- teams
- npm run typecheck
- npm run lint
```

AI 도구가 터미널을 사용할 수 있다면 이 명령은 작업 루프의 일부가 됩니다. 사용할 수 없더라도 최종 답변에서 실행 여부를 확인하게 만들 수 있습니다. 중요한 것은 결과가 말이 아니라 명령 출력으로 검증된다는 점입니다.

## 생성된 코드의 리뷰 질문을 바꾼다

AI가 만든 코드를 볼 때 "동작하나?"만 보면 부족합니다. 다음 질문을 같이 봐야 합니다.

- 기존 패턴과 다른 추상화를 만들었는가?
- 실패 경로와 권한 경로가 테스트됐는가?
- 타입을 넓게 만들어 문제를 숨기지 않았는가?
- 불필요하게 많은 파일을 건드렸는가?
- 사람이 이해하기 어려운 일반화가 들어갔는가?

AI가 만든 코드는 대체로 문법보다 맥락에서 틀립니다. 리뷰도 맥락 중심이어야 합니다.

## 작은 단위로 요청한다

한 번에 큰 기능을 맡기면 AI는 중간 결정들을 임의로 채웁니다. 데이터 모델, API, UI, 테스트를 한 요청에 묶으면 검토할 표면이 너무 커집니다. 먼저 데이터 흐름을 정하고, 다음에 API, 그다음 UI처럼 나누면 품질이 좋아집니다.

특히 마이그레이션, 권한, 결제, 보안 관련 작업은 작은 단위가 중요합니다. AI가 빠르게 작성할 수 있다는 사실이 변경을 크게 만들어도 된다는 뜻은 아닙니다.

## 체크리스트

- 요구사항과 함께 참고할 기존 파일을 지정한다.
- 새 라이브러리, 공개 계약 변경, 관련 없는 리팩터링 금지 조건을 둔다.
- 완료 조건을 테스트와 빌드 명령으로 표현한다.
- 리뷰에서는 문법보다 프로젝트 맥락의 어긋남을 본다.
- 큰 기능은 검증 가능한 작은 변경으로 나눈다.

AI 코드 생성은 코드를 대신 이해해 주지 않습니다. 하지만 올바른 근거와 검증 루프를 주면 반복 작업의 속도를 크게 줄여 줍니다. 핵심은 모델을 믿는 것이 아니라 코드베이스에 묶어 두는 것입니다.
