카나리 배포는 새 버전을 일부 트래픽에 먼저 노출해 위험을 줄이는 방식입니다. 하지만 카나리를 켜 놓고 대시보드 수십 개를 사람이 바라보는 방식은 오래가지 않습니다. 좋은 카나리 판단은 많은 메트릭이 아니라 적은 메트릭을 정확히 고르는 데서 시작합니다.

## 사용자 영향 메트릭을 먼저 둔다

카나리의 목적은 새 버전이 사용자에게 나쁜 영향을 주는지 빠르게 알아내는 것입니다. CPU 사용률이나 메모리 사용량은 원인 분석에는 중요하지만, 첫 판단 기준은 사용자 영향이어야 합니다.

서비스마다 다르지만 보통 다음이 우선입니다.

- 요청 성공률
- 오류 응답률
- p95 또는 p99 지연 시간
- 핵심 전환 이벤트 성공률
- 결제, 로그인, 저장 같은 중요 작업 실패율

시스템 내부 메트릭은 이 다음입니다. 새 버전의 CPU가 높더라도 사용자 영향이 없다면 관찰을 이어갈 수 있습니다. 반대로 CPU가 정상이어도 결제 실패가 늘면 즉시 멈춰야 합니다.

## 비교 대상은 이전 버전이다

카나리 메트릭은 절대값보다 상대 비교가 중요합니다. 오늘 트래픽이 평소보다 느린 날일 수 있고, 특정 지역 네트워크가 불안정할 수도 있습니다. 그래서 카나리 버전과 stable 버전을 같은 시간대, 같은 조건에서 비교해야 합니다.

```text
rollback if:
  canary_error_rate > stable_error_rate + 1%
  for 5 minutes
  and canary_request_count > 1000
```

요청 수 조건도 필요합니다. 샘플이 너무 작으면 한두 건의 실패로 롤백이 발생합니다. 반대로 트래픽이 적은 서비스라면 시간 기준보다 최소 요청 수를 더 중요하게 둬야 합니다.

## 메트릭 수를 제한한다

카나리 게이트에 들어가는 메트릭은 3개에서 5개 정도가 다루기 좋습니다. 너무 많으면 어떤 신호가 실제 롤백 이유인지 모호해지고, 작은 노이즈가 배포를 자주 막습니다.

추천 조합은 다음과 같습니다.

- 전체 오류율
- 핵심 API p95 지연 시간
- 핵심 비즈니스 이벤트 성공률
- 프로세스 재시작 또는 크래시 수
- 외부 의존성 호출 실패율

나머지는 알림이 아니라 조사 대시보드에 두면 됩니다. 카나리 게이트는 판정 장치이고, 대시보드는 원인 분석 도구입니다.

## 롤백 기준은 배포 전에 정한다

배포 중에 "이 정도면 괜찮은가"를 논의하면 이미 늦습니다. 기준이 없으면 사람은 새 버전을 살리고 싶은 쪽으로 해석하기 쉽습니다. 롤백 기준은 PR, 릴리스 노트, 배포 설정 중 한 곳에 명시되어야 합니다.

좋은 기준은 구체적입니다.

```text
5분 동안 다음 중 하나가 발생하면 자동 롤백:
- stable 대비 5xx 비율이 0.5%p 이상 증가
- checkout_success 이벤트가 2% 이상 감소
- checkout API p95가 stable 대비 30% 이상 증가
```

기준은 서비스 특성에 맞게 조정해야 합니다. 관리자 도구와 결제 시스템은 같은 임계값을 쓸 수 없습니다.

## 카나리 제외 대상을 명확히 한다

모든 변경이 카나리에 적합한 것은 아닙니다. 데이터 마이그레이션, 큐 컨슈머 변경, 스키마 삭제, 캐시 키 변경처럼 트래픽 일부만 바꿔서는 격리되지 않는 변경이 있습니다.

이런 작업은 카나리 대신 별도 전략이 필요합니다.

- 확장 가능한 스키마 변경 후 코드 배포
- 읽기 경로와 쓰기 경로 분리
- 기능 플래그로 동작 제어
- 백필을 작은 단위로 실행
- 롤백 대신 전진 수정 계획 준비

카나리는 만능 안전장치가 아닙니다. 격리 가능한 트래픽 변경에 가장 잘 맞습니다.

## 체크리스트

- 사용자 영향 메트릭을 첫 판단 기준으로 삼는다.
- stable 버전과 같은 시간대에 비교한다.
- 카나리 게이트 메트릭은 3개에서 5개로 제한한다.
- 롤백 기준을 배포 전에 숫자로 정한다.
- 카나리에 맞지 않는 변경 유형을 별도로 관리한다.

카나리 배포의 품질은 대시보드의 화려함이 아니라 롤백 결정을 빠르고 덜 감정적으로 만드는 기준에서 나옵니다.
