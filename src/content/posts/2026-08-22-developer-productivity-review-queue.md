개발 속도가 느려지는 이유가 구현 시간이 아니라 리뷰 대기 시간인 팀이 많습니다. PR은 열려 있는데 리뷰어가 없고, 리뷰가 와도 큰 방향만 논의하다 며칠이 지나갑니다. 이 상태가 반복되면 개발자는 큰 PR을 더 크게 만들고, 리뷰어는 더 보기 싫어지는 악순환이 생깁니다.

코드 리뷰 대기열은 도구보다 팀 습관의 문제입니다. 몇 가지 기준만 정해도 흐름이 많이 좋아집니다.

## PR 크기를 리뷰 가능한 단위로 줄인다

가장 효과적인 방법은 PR을 작게 만드는 것입니다. "작다"는 줄 수만 뜻하지 않습니다. 리뷰어가 한 번에 의도를 이해하고 위험을 판단할 수 있어야 합니다.

좋은 PR 단위는 다음과 같습니다.

- 스키마 추가만 하는 PR
- 기존 동작을 보존하는 내부 리팩터링
- 한 화면의 한 사용자 흐름 변경
- 테스트 보강 후 기능 변경
- 기능 플래그 뒤에 숨긴 첫 단계 구현

나쁜 PR은 데이터 모델, API, 화면, 스타일, 테스트, 리팩터링이 한 번에 들어갑니다. 리뷰어는 어디를 기준으로 봐야 할지 모르고, 작은 문제도 전체 승인을 막습니다.

## 리뷰 요청에 초점을 적는다

리뷰어에게 "확인 부탁드립니다"만 보내면 리뷰 범위가 흐립니다. PR 설명에는 리뷰어가 집중해야 할 지점을 적어야 합니다.

- API 응답 형식이 기존 클라이언트와 호환되는지 봐주세요
- 권한 검사가 빠진 경로가 없는지 봐주세요
- 렌더링 성능보다 상태 전이 정확성을 우선 봐주세요
- 파일 이동이 대부분이고 실제 로직 변경은 3개 커밋입니다

리뷰 요청이 구체적이면 리뷰어는 더 빨리 시작할 수 있고, 작성자도 불필요한 논쟁을 줄일 수 있습니다.

## 리뷰 소유자를 명확히 둔다

모두가 리뷰어이면 아무도 리뷰하지 않습니다. 각 영역마다 기본 리뷰 소유자가 필요합니다. 소유자는 코드 소유자와 같을 수도 있고, 변경 성격에 따라 다를 수도 있습니다.

예를 들어 결제 API는 백엔드 소유자와 보안 관점 리뷰어가 필요할 수 있습니다. 디자인 시스템 변경은 프론트엔드 소유자와 제품 디자이너가 함께 봐야 할 수 있습니다.

자동 reviewer 지정은 도움이 되지만 충분하지 않습니다. 팀 안에서 "이 영역은 누가 최종 판단하는가"가 분명해야 합니다.

## 리뷰 시간을 일정에 넣는다

리뷰는 남는 시간에 하면 계속 밀립니다. 팀이 리뷰를 중요한 작업으로 본다면 일정에도 들어가야 합니다.

가벼운 방식으로 시작할 수 있습니다.

- 오전과 오후에 15분 리뷰 슬롯
- 하루 이상 대기 중인 PR 우선 확인
- 릴리스 전 위험 PR 먼저 리뷰
- 리뷰 대기 PR 수를 스탠드업에서 공유

리뷰 시간을 정하면 작성자도 기대 시간을 예측할 수 있습니다.

## 승인 기준과 코멘트 종류를 나눈다

모든 코멘트가 merge를 막아야 하는 것은 아닙니다. 취향, 개선 제안, 반드시 고쳐야 하는 결함을 구분하지 않으면 리뷰가 느려집니다.

팀에서 간단한 접두어를 쓸 수 있습니다.

- `blocker`: merge 전 반드시 수정
- `question`: 의도 확인
- `suggestion`: 개선 제안
- `nit`: 사소한 취향 또는 정리

이 구분은 리뷰를 부드럽게 만들 뿐 아니라, 작성자가 어떤 코멘트부터 처리해야 하는지 알려줍니다.

코드 리뷰 대기열을 줄이는 핵심은 "빨리 봐주세요"라고 더 자주 말하는 것이 아닙니다. 리뷰하기 쉬운 단위로 나누고, 책임과 기준을 분명히 하는 것입니다. 리뷰가 빨라지면 배포 속도만 좋아지는 것이 아니라 코드 품질 논의도 더 선명해집니다.
