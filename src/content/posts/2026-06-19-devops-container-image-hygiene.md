컨테이너 이미지는 한 번 만들면 어디서나 같은 방식으로 실행된다는 장점이 있습니다. 하지만 이미지가 크고, 태그가 불명확하고, 빌드 시점마다 내용이 달라지면 이 장점은 빠르게 사라집니다. 운영용 이미지는 "실행에 필요한 것만 담긴 재현 가능한 결과물"이어야 합니다.

## 태그보다 digest를 신뢰한다

`node:22` 같은 태그는 시간이 지나면 가리키는 이미지가 바뀔 수 있습니다. 개발 환경에서는 편하지만 운영 빌드에서는 재현성을 떨어뜨립니다. 베이스 이미지는 가능한 한 버전을 고정하고, 중요한 배포에서는 digest까지 기록합니다.

```dockerfile
FROM node:22.22.3-slim
```

완벽한 고정이 항상 가능한 것은 아니지만, 적어도 `latest`는 피해야 합니다. "어제 빌드와 오늘 빌드가 왜 다른가"를 디버깅하는 비용은 생각보다 큽니다.

## 빌드 도구와 런타임을 분리한다

애플리케이션 실행에 컴파일러, 패키지 매니저 캐시, 테스트 도구가 필요하지 않은 경우가 많습니다. 멀티 스테이지 빌드를 사용하면 빌드에 필요한 파일과 실행에 필요한 파일을 분리할 수 있습니다.

```dockerfile
FROM node:22.22.3-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22.22.3-slim AS runtime
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/dist ./dist
COPY --from=build /app/package*.json ./
RUN npm ci --omit=dev
CMD ["node", "dist/server.js"]
```

이미지가 작아지면 배포 속도만 빨라지는 것이 아닙니다. 스캔해야 할 패키지 수와 공격 표면도 줄어듭니다.

## 레이어 캐시를 의도적으로 설계한다

Dockerfile의 순서는 빌드 속도에 큰 영향을 줍니다. 소스 코드를 먼저 복사한 뒤 의존성을 설치하면 작은 코드 변경에도 의존성 설치 레이어가 깨집니다. 보통은 lockfile을 먼저 복사해 의존성을 설치하고, 그 다음 소스 코드를 복사합니다.

이 원칙은 CI 비용에도 영향을 줍니다. 캐시가 잘 유지되면 빌드가 빨라지고, 캐시가 자주 깨지면 배포 파이프라인이 느려집니다.

## root로 실행하지 않는다

컨테이너 내부의 root는 호스트 root와 같지는 않지만, 취약점이 있을 때 피해 범위를 키울 수 있습니다. 런타임 이미지는 가능하면 non-root 사용자로 실행합니다.

```dockerfile
RUN useradd --create-home appuser
USER appuser
```

파일 권한도 함께 확인해야 합니다. non-root로 바꾼 뒤 로그 디렉터리나 임시 파일 경로에 쓰지 못해 장애가 나는 경우가 흔합니다.

## 이미지에 비밀을 넣지 않는다

빌드 인자로 토큰을 넘기거나 `.env` 파일을 복사하면 이미지 레이어에 비밀이 남을 수 있습니다. 삭제해도 이전 레이어에 남아 있을 수 있기 때문에, 비밀은 런타임 주입이나 CI의 secret mount 기능을 사용해야 합니다.

## 체크리스트

- 운영 이미지에서 `latest` 태그를 피한다.
- lockfile 기반으로 의존성을 재현 가능하게 설치한다.
- 빌드 스테이지와 런타임 스테이지를 분리한다.
- 런타임은 non-root 사용자로 실행한다.
- 이미지 레이어에 토큰과 `.env`를 남기지 않는다.
- 이미지 크기와 취약점 스캔 결과를 배포 파이프라인에서 확인한다.

좋은 컨테이너 이미지는 특별한 기술보다 습관에서 나옵니다. 필요한 것만 담고, 같은 입력에서 같은 결과를 만들고, 운영에서 바뀌면 안 되는 것을 고정하는 습관입니다.
