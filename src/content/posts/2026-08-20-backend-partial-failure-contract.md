백엔드 API는 성공 아니면 실패처럼 보이지만, 실제 시스템에서는 부분 실패가 흔합니다. 초대 메일 20개 중 17개만 성공할 수 있고, 파일 100개 중 일부만 인덱싱될 수 있습니다. 권한 변경은 적용됐지만 알림 발송은 실패할 수도 있습니다.

이런 상황을 HTTP 500 하나로 숨기면 클라이언트는 무엇을 다시 시도해야 하는지 알 수 없습니다. 반대로 무조건 200으로 처리하면 사용자는 실패를 놓칩니다. 부분 실패는 명시적인 응답 계약이 필요합니다.

## 전체 결과와 항목 결과를 분리한다

배치 API는 전체 요청의 처리 결과와 개별 항목의 처리 결과를 나누어 표현해야 합니다.

```json
{
  "status": "partial_success",
  "summary": {
    "total": 5,
    "succeeded": 3,
    "failed": 2
  },
  "items": [
    { "clientId": "a1", "status": "succeeded", "resourceId": "inv_101" },
    { "clientId": "a2", "status": "failed", "errorCode": "INVALID_EMAIL" }
  ]
}
```

여기서 `status`는 전체 요청의 결과를 말하고, `items`는 각 항목의 운명을 말합니다. 클라이언트는 실패한 항목만 표시하거나 재시도할 수 있습니다.

## 클라이언트가 넣은 식별자를 되돌려준다

부분 실패 응답에서 가장 중요한 필드는 `clientId`입니다. 서버가 처리한 순서와 클라이언트가 보낸 순서가 달라질 수 있고, 일부 항목은 서버 리소스 ID가 없을 수 있기 때문입니다.

클라이언트가 보낸 임시 식별자를 응답에 그대로 포함하면 화면의 행, 폼 필드, 업로드 카드와 서버 결과를 정확히 매핑할 수 있습니다.

이 값은 비즈니스 ID가 아니어도 됩니다. 요청 안에서만 유일하면 충분합니다. 다만 로그 분석을 위해 요청 ID와 함께 남기면 장애 조사에 도움이 됩니다.

## 오류 코드는 복구 가능성을 표현해야 한다

부분 실패에서 오류 메시지만 내려주면 클라이언트가 자동 복구를 하기 어렵습니다. 오류 코드는 사용자가 고칠 수 있는 문제인지, 시간이 지나면 해결될 문제인지, 관리자 개입이 필요한 문제인지 구분할 수 있어야 합니다.

예시는 다음과 같습니다.

- `INVALID_INPUT`: 사용자가 값을 수정해야 한다.
- `ALREADY_EXISTS`: 중복 생성이므로 기존 리소스를 보여줄 수 있다.
- `RATE_LIMITED`: 나중에 재시도할 수 있다.
- `DEPENDENCY_TIMEOUT`: 서버가 재시도했거나 재시도할 수 있다.
- `PERMISSION_DENIED`: 권한 흐름으로 안내해야 한다.

`retryable: true` 같은 명시 필드를 함께 주면 클라이언트 구현이 더 단순해집니다.

## 재시도 단위를 작게 만든다

부분 실패 API는 실패한 항목만 다시 보낼 수 있어야 합니다. 전체 요청을 그대로 재시도하게 만들면 이미 성공한 항목이 중복 처리될 수 있습니다.

이때 서버는 멱등성을 함께 제공해야 합니다. 항목마다 idempotency key를 받거나, 요청 범위의 operation id와 항목 client id를 조합해 중복 처리를 막을 수 있습니다.

재시도 응답도 같은 형식을 쓰는 편이 좋습니다. 처음 요청과 재시도 요청의 응답 구조가 다르면 클라이언트 상태 병합이 복잡해집니다.

## HTTP 상태 코드를 신중하게 고른다

부분 성공은 HTTP 상태 코드만으로 표현하기 어렵습니다. 실무에서는 요청 자체가 유효했고 서버가 결과 본문을 반환할 수 있다면 200을 쓰고, 본문에 `partial_success`를 명시하는 방식이 많이 쓰입니다.

반대로 인증 실패, 요청 본문 파싱 실패, 배치 크기 초과처럼 요청 전체가 처리 대상이 될 수 없으면 4xx를 반환하는 편이 명확합니다. 서버 내부 장애로 결과를 만들 수 없다면 5xx가 맞습니다.

중요한 것은 팀 안에서 기준을 고정하는 것입니다. 같은 종류의 부분 실패가 어떤 API에서는 200, 어떤 API에서는 500으로 나오면 클라이언트는 공통 처리를 만들 수 없습니다.

부분 실패는 예외가 아니라 분산 시스템의 기본 조건입니다. 응답 계약에 전체 결과, 항목별 결과, 클라이언트 식별자, 복구 가능한 오류 코드를 넣어두면 사용자는 실패한 만큼만 다시 시도할 수 있고, 시스템은 이미 성공한 일을 안전하게 보존할 수 있습니다.
