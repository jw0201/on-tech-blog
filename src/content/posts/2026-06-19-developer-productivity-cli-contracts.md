팀 내부 CLI는 반복 작업을 줄이는 좋은 도구입니다. 배포 준비, 테스트 데이터 생성, 로그 조회, 마이그레이션 검증 같은 일을 명령 하나로 처리할 수 있습니다. 하지만 계약 없이 만든 CLI는 금방 깨지는 스크립트가 됩니다. 사람이 쓰는 도구이면서 자동화도 호출하기 때문입니다.

## 입력 옵션을 명확히 한다

CLI의 옵션은 시간이 지나면 늘어납니다. 처음부터 이름과 기본값을 신중하게 정해야 합니다. 특히 운영에 영향을 주는 명령은 dry-run을 기본으로 두는 편이 안전합니다.

```bash
tool users backfill --from 2026-06-01 --to 2026-06-07 --dry-run
```

좋은 옵션은 읽었을 때 행동이 예측됩니다. `--force`처럼 넓은 의미의 옵션은 가능하면 피하고, `--skip-confirmation`, `--overwrite-existing`처럼 무엇을 건너뛰는지 드러내는 이름이 낫습니다.

## 출력은 사람용과 기계용을 분리한다

CLI는 터미널에서 사람이 읽기도 하고 CI에서 파싱하기도 합니다. 두 용도를 한 출력에 섞으면 나중에 자동화가 깨집니다. 사람이 읽는 기본 출력과 기계가 읽는 JSON 출력을 분리합니다.

```bash
tool deploy status --format json
```

JSON 출력은 안정적인 계약으로 취급해야 합니다. 필드 이름을 바꾸거나 중첩 구조를 바꾸면 해당 CLI를 호출하는 다른 스크립트가 깨질 수 있습니다. 사람이 읽는 문구는 비교적 자유롭게 바꿔도 되지만, 기계용 출력은 버전 관리가 필요합니다.

## 종료 코드를 설계한다

CLI 자동화에서 가장 중요한 계약은 종료 코드입니다. 모든 실패를 `1`로만 처리해도 동작은 하지만, CI나 상위 스크립트가 적절히 대응하기 어렵습니다.

예를 들어 다음처럼 구분할 수 있습니다.

- `0`: 성공
- `1`: 일반 실패
- `2`: 입력 오류
- `3`: 외부 서비스 일시 실패
- `4`: 검증 실패

너무 많은 종료 코드는 부담이지만, 재시도 가능한 실패와 재시도해도 소용없는 실패는 구분하는 편이 좋습니다.

## 로그와 결과를 섞지 않는다

기계가 파싱하는 결과가 stdout에 있다면 진행 로그는 stderr로 보내는 것이 안전합니다. 그래야 파이프나 파일 저장이 예측 가능해집니다.

```bash
tool report --format json > report.json
```

이때 진행 로그가 stdout에 섞이면 `report.json`은 깨진 JSON이 됩니다. 작은 규칙이지만 자동화 신뢰도에 큰 차이를 만듭니다.

## 체크리스트

- 위험한 명령은 dry-run과 확인 절차를 둔다.
- 옵션 이름은 실제 행동을 드러내게 만든다.
- 사람용 출력과 JSON 같은 기계용 출력을 분리한다.
- 종료 코드로 입력 오류, 검증 실패, 일시 실패를 구분한다.
- 결과는 stdout, 로그는 stderr로 분리한다.
- 기계용 출력은 변경 시 버전을 고려한다.

내부 CLI는 팀의 작은 제품입니다. 계약을 정해 두면 사람이 편해질 뿐 아니라 CI, 봇, 다른 스크립트가 안정적으로 기대어 쓸 수 있습니다.
