개발 생산성은 거대한 플랫폼 프로젝트로만 좋아지지 않습니다. 오히려 매일 반복되는 작은 불편을 줄이는 자동화가 더 빠르게 효과를 냅니다. 새 서비스를 만들 때 복사해야 하는 설정, PR마다 확인하는 체크리스트, 릴리스 전 수동 명령 같은 것들입니다. 이런 작업은 하나하나 작지만 팀 전체로 보면 큰 시간을 씁니다.

## 반복 빈도와 실수 비용을 본다

자동화 후보를 고를 때는 귀찮음만 보지 말고 반복 빈도와 실수 비용을 함께 봅니다. 한 달에 한 번 하는 작업이라도 실수하면 장애가 나는 배포 절차는 자동화 가치가 높습니다. 매일 하지만 10초면 끝나는 작업은 우선순위가 낮을 수 있습니다.

간단한 기준은 다음과 같습니다.

- 여러 사람이 같은 순서를 반복한다.
- 문서를 보고 따라 해도 실수가 자주 난다.
- 실패를 늦게 발견한다.
- 결과가 항상 같은 형식이어야 한다.
- 새 팀원이 익히는 데 오래 걸린다.

이 중 두세 개가 맞으면 작은 스크립트나 템플릿으로 시작할 만합니다.

## 문서를 명령으로 바꾼다

가장 좋은 자동화는 문서의 절차를 실행 가능한 명령으로 바꾸는 것입니다. 예를 들어 릴리스 문서에 "테스트 실행, 빌드, 태그 생성, 배포"가 적혀 있다면 일부라도 스크립트로 묶을 수 있습니다.

```json
{
  "scripts": {
    "release:check": "npm run test && npm run build"
  }
}
```

처음부터 모든 단계를 자동화할 필요는 없습니다. 수동 승인이나 위험한 배포 버튼은 남겨도 됩니다. 중요한 것은 사람이 기억해야 하는 순서를 줄이는 것입니다.

## 실패 메시지를 친절하게 만든다

자동화는 실패했을 때 품질이 드러납니다. 단순히 명령이 실패하고 긴 로그를 뱉으면 사람은 다시 전문가를 찾아야 합니다. 좋은 스크립트는 실패 원인과 다음 행동을 알려줍니다.

예를 들어 환경 변수가 없을 때 "undefined" 에러가 나는 대신 다음처럼 말하는 편이 낫습니다.

```text
DATABASE_URL이 설정되어 있지 않습니다.
.env.local을 만들거나 onboarding 문서의 로컬 DB 설정을 확인하세요.
```

작은 메시지 하나가 반복 질문을 줄입니다.

## 소유자 없는 자동화는 금방 낡는다

자동화도 코드입니다. 의존성이 바뀌고, 팀 규칙이 바뀌고, 더 이상 쓰지 않는 명령이 남습니다. 그래서 소유자와 삭제 기준이 필요합니다. 스크립트가 실패했을 때 누구에게 물어볼지, 어떤 조건이면 제거할지 정해두면 방치되는 도구가 줄어듭니다.

작은 자동화일수록 README나 스크립트 상단에 목적을 짧게 남기는 것도 좋습니다. "왜 있는지"를 알아야 미래의 팀원이 안전하게 고칠 수 있습니다.

## 성공 지표는 사용 여부다

자동화의 성공은 멋진 구조가 아니라 실제 사용 여부입니다. 팀원이 자발적으로 쓰고, 문서에서 수동 절차가 줄어들고, 같은 질문이 줄면 성공입니다. 반대로 아무도 쓰지 않는 도구라면 기능이 많아도 실패입니다.

그래서 처음에는 가장 작은 형태로 배포하고 피드백을 받습니다. CLI가 필요 없다면 npm script로 충분하고, 웹 UI가 필요 없다면 체크리스트 생성기로 충분합니다.

## 체크리스트

- 반복 빈도와 실수 비용이 모두 높은 작업부터 고른다.
- 문서의 절차를 실행 가능한 명령으로 조금씩 바꾼다.
- 실패 메시지에 원인과 다음 행동을 담는다.
- 자동화에도 소유자와 삭제 기준을 둔다.
- 사용률과 질문 감소를 성공 지표로 본다.

좋은 개발 생산성 개선은 거창하지 않을 때가 많습니다. 팀이 매일 밟는 작은 돌부리를 하나씩 치우면, 속도는 조용히 빨라집니다.
