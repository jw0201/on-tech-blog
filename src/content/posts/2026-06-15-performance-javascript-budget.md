웹 성능 문제는 "사이트가 무겁다"라는 말로 시작하면 해결이 어렵습니다. 무엇이 얼마나 무거운지, 어떤 페이지에서 문제가 되는지, 어느 정도까지 허용할지 정해야 합니다. 자바스크립트 예산은 이 대화를 숫자로 바꾸는 도구입니다.

예산은 단순히 번들 크기를 제한하는 것이 아닙니다. 다운로드, 파싱, 실행, 하이드레이션, 서드파티 스크립트까지 포함해 사용자가 실제로 기다리는 시간을 관리하는 기준입니다.

## 페이지 유형별로 예산을 다르게 둔다

모든 페이지에 같은 기준을 적용하면 현실과 맞지 않습니다. 로그인 페이지, 마케팅 랜딩, 대시보드, 에디터는 필요한 기능이 다릅니다.

예를 들어 이렇게 나눌 수 있습니다.

- 공개 랜딩: 초기 JS 80KB gzip 이하
- 로그인: 초기 JS 120KB gzip 이하
- 일반 대시보드: 초기 JS 200KB gzip 이하
- 에디터: 초기 JS 350KB gzip 이하, 지연 로딩 필수

중요한 것은 숫자의 절대값보다 합의된 기준입니다. 팀이 새 라이브러리를 추가할 때 "이 페이지 예산 안에 들어가는가"를 물을 수 있어야 합니다.

## 크기와 실행 시간을 함께 본다

작은 코드가 항상 빠른 것은 아닙니다. 정규식, 암호화, 대량 JSON 처리, 복잡한 렌더링 로직은 크기보다 실행 시간이 문제입니다. 반대로 큰 라이브러리라도 초기 경로에서 실행되지 않으면 영향이 작을 수 있습니다.

그래서 예산은 최소 두 가지를 봐야 합니다.

- 전송 크기: gzip 또는 brotli 기준 번들 크기
- 메인 스레드 비용: 파싱, 컴파일, 실행, 긴 작업

Chrome 성능 프로파일에서 50ms 이상 긴 작업이 반복되면 사용자 입력이 밀릴 수 있습니다. 특히 저사양 모바일 기기에서는 같은 코드도 훨씬 느리게 실행됩니다.

## 서드파티 스크립트도 제품 코드처럼 관리한다

분석, 채팅, A/B 테스트, 광고, 태그 매니저는 성능 예산을 쉽게 무너뜨립니다. 문제는 이 스크립트들이 코드 리뷰를 거치지 않고 추가되는 경우가 많다는 점입니다.

서드파티 스크립트에는 별도 등록 절차가 필요합니다.

- 소유 팀
- 사용 목적
- 로드되는 페이지
- 비동기 로딩 여부
- 장애 시 사용자 영향
- 제거 기준

목적을 잃은 스크립트는 계속 비용만 냅니다. 분기마다 목록을 검토하는 것만으로도 성능과 개인정보 리스크를 줄일 수 있습니다.

## 지연 로딩은 경계가 중요하다

지연 로딩은 좋은 도구지만 무조건 쪼개면 네트워크 왕복이 늘고 사용자 경험이 나빠질 수 있습니다. 경계는 사용자 행동을 기준으로 잡습니다.

- 모달을 열 때 필요한 코드
- 관리자 전용 기능
- 차트 상세 보기
- 드래그 앤 드롭 에디터
- 드물게 쓰는 내보내기 기능

반대로 첫 화면 렌더링에 반드시 필요한 컴포넌트를 과하게 지연하면 로딩 스피너만 늘어납니다. 지연 로딩은 초기 경로에서 빼도 되는 코드를 찾는 작업입니다.

## CI에서 회귀를 막는다

예산은 문서에만 있으면 잘 지켜지지 않습니다. 번들 분석 결과를 CI에서 비교하고, 예산 초과 시 PR에 표시해야 합니다.

실패 기준은 너무 엄격하게 시작하지 않는 편이 좋습니다. 예를 들어 초기에는 "주요 번들이 10KB 이상 증가하면 경고"로 시작하고, 기준이 안정되면 실패로 바꿀 수 있습니다. 갑작스러운 차단보다 꾸준한 가시성이 먼저입니다.

## 체크리스트

- 페이지 유형별 JS 예산을 따로 둔다.
- 전송 크기와 메인 스레드 실행 시간을 함께 본다.
- 서드파티 스크립트에는 소유자와 제거 기준을 둔다.
- 사용자 행동 기준으로 지연 로딩 경계를 정한다.
- CI에서 번들 증가와 예산 초과를 PR에 노출한다.

성능은 취향 논쟁이 되기 쉽습니다. 자바스크립트 예산을 정하면 논의가 "느낌"에서 "변화량"으로 옮겨갑니다. 그때부터 성능은 관리 가능한 품질 속성이 됩니다.
