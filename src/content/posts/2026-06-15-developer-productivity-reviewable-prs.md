좋은 PR은 리뷰어가 빠르게 읽고 자신 있게 승인할 수 있는 단위입니다. 흔히 "작은 PR을 만들자"고 말하지만, 크기만 줄인다고 리뷰가 쉬워지는 것은 아닙니다. 작은 변경이라도 의도가 불분명하면 리뷰어는 맥락을 다시 캐야 합니다.

리뷰하기 쉬운 PR은 변경 이유, 범위, 검증 방법이 선명합니다.

## 한 PR에는 하나의 판단만 담는다

리뷰어가 어려워하는 PR은 여러 종류의 판단을 동시에 요구합니다.

- 기능 요구사항이 맞는가
- 아키텍처 방향이 맞는가
- 리팩터링이 안전한가
- 스타일 변경이 필요한가
- 테스트가 충분한가

이 모든 것이 한 PR에 섞이면 리뷰가 느려집니다. 가능하면 준비 작업, 리팩터링, 기능 변경, 정리 작업을 나눕니다. 예를 들어 먼저 타입 이름을 정리하는 PR을 만들고, 다음 PR에서 기능을 추가하면 실제 제품 변경을 보기 쉬워집니다.

나누는 기준은 파일 수가 아니라 리뷰어가 해야 할 판단의 종류입니다.

## 설명은 변경 요약보다 리뷰 경로를 안내한다

PR 설명에는 "무엇을 바꿨다"보다 "어떻게 읽으면 된다"가 더 도움이 됩니다.

```md
## 변경
- 결제 실패 사유를 API 응답에 추가
- 프론트엔드 결제 화면에서 사유별 안내 문구 표시

## 리뷰 포인트
- `PaymentFailureReason` enum 이름이 제품 용어와 맞는지
- 재시도 가능한 실패와 불가능한 실패의 분류가 맞는지

## 검증
- `npm test -- payment`
- 스테이징에서 만료 카드 케이스 확인
```

리뷰 포인트가 있으면 리뷰어는 중요한 부분에 집중할 수 있습니다. 반대로 "전체적으로 봐주세요"는 리뷰어에게 모든 맥락 비용을 넘깁니다.

## 기계적인 변경은 분리한다

포맷팅, import 정렬, 파일 이동, 자동 변환은 기능 변경과 섞지 않는 편이 좋습니다. 리뷰 화면에서 실제 로직 변경이 묻히기 때문입니다.

어쩔 수 없이 함께 들어갔다면 PR 설명에 명시합니다.

- `src/generated`는 스키마 생성 결과입니다.
- `*.snap`은 문구 변경에 따른 스냅샷 갱신입니다.
- `components/checkout` 파일 이동은 내용 변경 없이 경로만 변경했습니다.

리뷰어가 봐야 할 파일과 넘어가도 되는 파일을 구분해 주면 리뷰 품질이 올라갑니다.

## 검증 명령은 성공과 실패를 모두 남긴다

PR에서 가장 신뢰를 주는 정보는 검증 흔적입니다. 단순히 "테스트 완료"보다 실행한 명령을 적는 것이 낫습니다.

```text
검증:
- npm run lint
- npm test -- checkout
- npm run build
```

실패한 명령이 있다면 숨기지 말고 이유를 씁니다. 예를 들어 "기존 `analytics.test.ts`가 main에서도 실패함"처럼 남기면 리뷰어가 현재 변경과 무관한 실패인지 판단할 수 있습니다.

## 리뷰 댓글을 줄이는 작은 습관

반복되는 리뷰 댓글은 PR 작성 단계에서 줄일 수 있습니다.

- 공개 API 변경에는 마이그레이션 메모를 붙인다.
- 성능 영향이 있는 변경에는 전후 수치를 남긴다.
- 보안 관련 변경에는 위협 모델을 짧게 적는다.
- UI 변경에는 스크린샷이나 녹화를 첨부한다.
- 데이터 마이그레이션에는 롤백 경로를 적는다.

리뷰어가 물어볼 질문을 미리 답하면 대기 시간이 줄어듭니다.

## 체크리스트

- 한 PR에는 가능한 한 하나의 판단 종류만 담는다.
- 설명에는 변경 요약과 리뷰 포인트를 분리한다.
- 기계적인 변경은 기능 변경과 분리하거나 명확히 표시한다.
- 검증 명령을 구체적으로 적고 실패도 숨기지 않는다.
- API, 성능, 보안, UI, 데이터 변경에는 추가 맥락을 남긴다.

리뷰하기 쉬운 PR은 팀의 시간을 아낍니다. 작성자가 조금 더 맥락을 담아두면 리뷰어는 더 빠르게 핵심을 보고, 변경은 더 안전하게 main에 들어갑니다.
