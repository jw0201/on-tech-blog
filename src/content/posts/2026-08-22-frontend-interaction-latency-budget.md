웹 성능을 이야기할 때 초기 로딩만 보는 팀이 많습니다. 하지만 실제 제품에서 사용자가 매일 느끼는 품질은 클릭 후 반응, 입력 중 끊김, 목록 필터 변경, 모달 열기 같은 반복 인터랙션에서 결정됩니다.

인터랙션 지연 시간은 "빠르면 좋다"로 두면 관리되지 않습니다. 기능마다 허용 가능한 예산을 정하고, 그 예산을 넘는 작업을 코드 리뷰와 릴리스 과정에서 잡아내야 합니다.

## 인터랙션을 기능 단위로 나눈다

먼저 화면의 주요 인터랙션을 목록으로 만듭니다.

- 검색어 입력
- 테이블 정렬
- 필터 토글
- 저장 버튼 클릭
- 사이드 패널 열기
- 드래그 앤 드롭

각 인터랙션마다 사용자가 기대하는 반응 속도는 다릅니다. 텍스트 입력은 거의 즉시 반응해야 하고, 저장은 네트워크 요청 때문에 조금 기다릴 수 있습니다. 반대로 패널 열기나 필터 토글은 로컬 UI처럼 느껴져야 합니다.

## 예산은 숫자로 적는다

예산은 추상적인 원칙보다 숫자가 낫습니다.

- 입력 글자 반영: 50ms 이하
- 버튼 누름 상태 표시: 100ms 이하
- 로컬 필터 결과 표시: 150ms 이하
- 서버 저장 피드백 시작: 200ms 이하
- 무거운 차트 재계산: 500ms 이하, 진행 상태 표시

이 숫자는 절대 규칙이 아니라 팀의 기준선입니다. 중요한 점은 "이번 변경이 사용자가 기다리는 시간을 얼마나 늘리는가"를 말할 수 있어야 한다는 것입니다.

## 긴 작업은 메인 스레드에서 빼낸다

인터랙션이 느려지는 흔한 이유는 클릭 핸들러 안에서 너무 많은 일을 하기 때문입니다. JSON 파싱, 큰 배열 정렬, 마크다운 렌더링, 차트 데이터 변환, 암호화 연산이 모두 메인 스레드를 막을 수 있습니다.

해결책은 작업 성격에 따라 다릅니다.

- 렌더링과 무관한 계산은 Web Worker로 이동
- 목록 필터는 인덱스나 서버 쿼리로 대체
- 입력 중 검증은 debounce와 최소 검증으로 제한
- 차트 데이터는 화면 진입 전 미리 준비
- React 렌더링은 memoization보다 상태 범위 축소를 먼저 검토

`useMemo`를 붙이는 것만으로는 구조적인 지연을 해결하기 어렵습니다. 어떤 상태 변경이 어떤 컴포넌트를 다시 렌더링하는지 먼저 좁혀야 합니다.

## 측정 위치를 코드에 남긴다

브라우저 Performance 패널은 디버깅에는 좋지만, 매번 사람이 열어야 합니다. 반복적으로 중요한 인터랙션은 코드에 측정 지점을 남기는 편이 좋습니다.

예를 들어 저장 버튼이라면 클릭 시점, pending 표시 시점, 서버 응답 시점, 화면 반영 완료 시점을 각각 측정할 수 있습니다. 이렇게 하면 "API가 느린지", "렌더링이 느린지", "상태 병합이 느린지"를 나눠 볼 수 있습니다.

실무에서는 다음 정도면 충분합니다.

- 개발 환경에서 콘솔로 duration 출력
- E2E 테스트에서 주요 인터랙션 시간 기록
- 운영 환경에서는 샘플링해서 웹 바이탈이나 자체 이벤트로 전송

모든 클릭을 추적할 필요는 없습니다. 사용 빈도가 높고 느려질 가능성이 큰 흐름만 잡아도 효과가 큽니다.

## 느림을 숨기지 말고 설계한다

모든 인터랙션을 즉시 끝낼 수는 없습니다. 중요한 것은 느린 작업을 사용자가 이해할 수 있게 만드는 것입니다.

저장은 버튼의 pending 상태로 충분할 수 있습니다. 대량 내보내기는 작업 큐와 완료 알림이 필요할 수 있습니다. 대시보드 재계산은 이전 결과를 유지하면서 갱신 중임을 표시하는 편이 낫습니다.

성능 예산은 단순히 빠른 코드를 쓰자는 말이 아닙니다. 사용자가 기다려야 하는 시간을 제품 정책으로 다루자는 약속입니다. 인터랙션별 예산을 정하면 성능 논의가 감각이 아니라 기준으로 바뀝니다.
