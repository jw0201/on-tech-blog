테스트는 보통 예시에서 시작합니다. 특정 입력을 넣고 기대 출력이 맞는지 확인합니다. 이 방식은 읽기 쉽고 디버깅하기 좋습니다. 하지만 입력 조합이 많은 로직에서는 예시 몇 개가 충분하지 않을 수 있습니다. 프로퍼티 기반 테스트는 이 빈틈을 메우는 도구입니다.

프로퍼티 기반 테스트의 핵심은 "이 입력에서는 이 값이 나온다"가 아니라 "어떤 입력이 와도 이 성질은 유지된다"를 검증하는 것입니다.

## 변환 함수에 잘 맞는다

가장 좋은 후보는 순수한 변환 함수입니다. 정렬, 파싱, 직렬화, 금액 계산, 권한 규칙, 날짜 범위 병합 같은 로직이 여기에 속합니다. 외부 시스템과 통신하지 않고 입력과 출력이 명확할수록 효과가 큽니다.

예를 들어 태그 목록을 정규화하는 함수가 있다고 가정합니다. 몇 가지 예시를 직접 쓰는 대신 다음 성질을 검증할 수 있습니다.

- 결과에는 빈 문자열이 없다.
- 결과에는 중복 태그가 없다.
- 모든 태그는 소문자다.
- 같은 입력을 다시 정규화해도 결과가 바뀌지 않는다.

마지막 성질은 멱등성입니다. 이런 성질은 예시 테스트보다 버그를 더 잘 잡아낼 때가 많습니다.

## 역변환이 있으면 강력하다

인코딩과 디코딩처럼 서로 반대 방향의 함수가 있다면 프로퍼티 기반 테스트가 특히 유용합니다.

```ts
decode(encode(value)) === value
```

이 한 줄의 성질은 사람이 떠올리기 어려운 많은 입력을 검사합니다. URL 파라미터 직렬화, CSV 파싱, 설정 파일 변환, 내부 DTO 매핑 같은 곳에 잘 맞습니다.

물론 완전히 같은 값으로 돌아오지 않는 경우도 있습니다. 날짜 문자열이 표준 형식으로 바뀌거나, 공백이 정리될 수 있습니다. 이때는 "정규화된 값이 같다"처럼 성질을 현실에 맞게 정의하면 됩니다.

## 실패 사례를 재현 가능하게 남긴다

프로퍼티 기반 테스트가 무작위 입력을 만든다고 해서 실패가 재현 불가능하면 안 됩니다. 좋은 도구는 실패한 입력과 시드를 출력합니다. 테스트 환경에서는 이 값을 로그에 남기고, 발견된 중요한 실패는 일반 예시 테스트로도 고정하는 편이 좋습니다.

즉 프로퍼티 기반 테스트는 예시 테스트를 대체하지 않습니다. 예상 못 한 입력을 찾아주고, 그중 중요한 버그는 사람이 읽을 수 있는 회귀 테스트로 남기는 관계입니다.

## 모든 곳에 쓰지는 않는다

프로퍼티 기반 테스트는 강력하지만 비용도 있습니다. 성질을 잘못 정의하면 테스트가 모호해지고, 생성기가 너무 넓으면 의미 없는 입력만 많이 검사합니다. UI 스냅샷, 복잡한 외부 API 연동, 사람이 읽어야 하는 워크플로 테스트에는 보통 맞지 않습니다.

처음 도입할 때는 다음 기준으로 고릅니다.

- 입력 공간이 넓다.
- 출력의 불변 조건을 말할 수 있다.
- 순수 함수 또는 격리된 도메인 로직이다.
- 과거에 경계값 버그가 자주 났다.

이 네 가지가 맞으면 도입 효과를 보기 쉽습니다.

## 체크리스트

- 예시 테스트로 부족한 입력 조합이 있는지 찾는다.
- 정렬, 파싱, 직렬화, 계산처럼 순수한 로직부터 시작한다.
- 멱등성, 역변환, 순서 보존 같은 성질을 정의한다.
- 실패한 입력은 재현 가능한 예시 테스트로 남긴다.
- 외부 의존성이 큰 흐름에는 억지로 적용하지 않는다.

프로퍼티 기반 테스트는 더 많은 테스트를 쓰자는 이야기가 아닙니다. 사람이 손으로 고르기 어려운 입력을 기계에게 맡기자는 이야기입니다. 성질만 잘 고르면 작은 테스트가 생각보다 넓은 안전망이 됩니다.
