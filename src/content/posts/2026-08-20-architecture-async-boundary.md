비동기 처리는 시스템을 느슨하게 연결해줍니다. 요청을 빠르게 끝내고, 외부 장애를 흡수하고, 무거운 작업을 뒤로 미룰 수 있습니다. 하지만 비동기 경계는 단순히 큐를 하나 붙이는 일이 아닙니다. 일관성, 실패 복구, 사용자 경험이 함께 바뀌는 아키텍처 결정입니다.

동기 호출을 비동기로 바꾸면 함수 호출 하나가 사라지는 대신 새로운 질문들이 생깁니다. 작업은 언제 완료되는가, 실패하면 누가 알 수 있는가, 중복 실행은 안전한가, 사용자는 어떤 상태를 보게 되는가.

## 비동기로 바꾸는 이유를 명확히 한다

먼저 비동기가 필요한 이유를 구분해야 합니다.

- 응답 시간을 줄이고 싶다.
- 외부 서비스 장애를 격리하고 싶다.
- 대량 작업을 나눠 처리하고 싶다.
- 여러 소비자가 같은 이벤트를 사용하게 하고 싶다.
- 재시도와 지연 실행이 필요하다.

이유에 따라 설계가 달라집니다. 단순히 응답 시간을 줄이려는 작업과 여러 도메인 이벤트를 배포하려는 작업은 같은 큐를 쓰더라도 모델이 다릅니다.

## 완료 상태를 제품 언어로 만든다

비동기 작업은 즉시 끝나지 않습니다. 따라서 사용자가 볼 상태가 필요합니다.

- 요청됨
- 처리 중
- 일부 완료
- 실패
- 재시도 중
- 완료

이 상태는 내부 job status와 완전히 같을 필요는 없지만, 사용자가 다음 행동을 결정할 수 있어야 합니다. 예를 들어 파일 업로드 후 인덱싱이 진행 중이라면 검색 결과에 바로 나타나지 않을 수 있음을 화면에서 표현해야 합니다.

상태가 없으면 사용자는 새로고침을 반복하고, 고객지원 팀은 "기다리면 됩니다"라는 답변을 하게 됩니다.

## 중복 실행을 기본 조건으로 둔다

큐 기반 시스템에서는 중복 실행이 생길 수 있습니다. worker가 처리 후 ack 전에 죽거나, 네트워크 문제로 같은 메시지가 다시 전달될 수 있습니다. 따라서 consumer는 기본적으로 멱등적이어야 합니다.

멱등성을 만드는 방법은 여러 가지입니다.

- 작업 ID를 저장하고 이미 처리한 작업을 건너뛴다.
- 결과 테이블에 unique constraint를 둔다.
- 상태 전이를 조건부 업데이트로 처리한다.
- 외부 API 호출에는 idempotency key를 사용한다.

"우리 큐는 exactly once를 보장한다"는 주장만 믿고 비즈니스 로직을 짜면 위험합니다. 운영 현실에서는 at least once로 생각하는 편이 안전합니다.

## 실패를 숨기지 않는다

비동기 작업 실패는 요청자에게 바로 보이지 않을 수 있습니다. 그래서 실패를 관측하고 알리는 설계가 중요합니다.

최소한 다음을 갖추는 것이 좋습니다.

- dead letter queue 또는 실패 테이블
- 재시도 횟수와 마지막 오류
- 작업 유형별 실패율
- 오래 대기 중인 작업 수
- 운영자가 재시도하거나 취소하는 도구

사용자에게 영향이 있는 작업은 내부 알림만으로 충분하지 않습니다. 화면 상태나 알림으로 실패를 알려야 합니다.

## 이벤트와 명령을 섞지 않는다

비동기 메시지는 크게 이벤트와 명령으로 나눌 수 있습니다. 이벤트는 이미 일어난 사실입니다. 명령은 누군가에게 어떤 일을 하라고 지시하는 요청입니다.

`OrderPaid`는 이벤트이고, `SendReceiptEmail`은 명령입니다. 둘을 섞으면 소유권이 흐려집니다. 이벤트는 여러 소비자가 독립적으로 반응할 수 있지만, 명령은 특정 처리자가 책임지고 성공이나 실패를 관리해야 합니다.

메시지 이름만 명확히 해도 시스템 이해도가 크게 올라갑니다.

비동기 경계는 성능 최적화 도구가 아니라 시스템의 책임 경계입니다. 사용자가 보는 상태, 중복 실행, 실패 복구, 관측 지표까지 함께 설계해야 큐가 복잡도를 숨기는 구멍이 아니라 신뢰성을 높이는 장치가 됩니다.
