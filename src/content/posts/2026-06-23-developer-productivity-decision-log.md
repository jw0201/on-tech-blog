팀이 느려지는 이유 중 하나는 같은 결정을 반복해서 논의하기 때문입니다. 왜 이 라이브러리를 골랐는지, 왜 이 API는 비동기인지, 왜 이 기능은 플래그 뒤에 있는지 기억하는 사람이 사라지면 토론은 처음부터 다시 시작됩니다. 작은 결정 로그는 이 반복 비용을 줄입니다.

ADR처럼 격식을 갖춘 문서도 좋지만, 모든 결정이 긴 문서를 필요로 하지는 않습니다. 중요한 것은 결정의 배경과 포기한 대안을 짧게 남기는 것입니다.

## 결정 로그의 단위를 작게 잡는다

결정 로그는 프로젝트 전체의 철학을 쓰는 곳이 아닙니다. 나중에 누군가 "왜 이렇게 했지"라고 물을 만한 선택을 기록하는 곳입니다.

예시는 다음과 같습니다.

- 결제 상태를 폴링 대신 웹훅으로 갱신한다.
- 관리자 목록 API는 offset 대신 cursor 페이지네이션을 쓴다.
- 이미지 업로드는 서버 경유 대신 사전 서명 URL을 쓴다.
- E2E 테스트는 결제 성공 경로 하나만 smoke로 유지한다.
- 기능 플래그는 30일 안에 제거한다.

하나의 로그는 짧아야 합니다. 읽는 데 2분이 넘으면 팀은 다시 읽지 않습니다.

## 형식을 고정한다

자유 형식 문서는 쓰기 쉽지만 나중에 찾기 어렵습니다. 결정 로그는 반복 가능한 템플릿이 있어야 합니다.

```markdown
## 2026-06-23: 결제 완료 처리는 웹훅을 기준으로 한다

상태: 채택

맥락:
클라이언트 리다이렉트는 사용자가 창을 닫으면 누락될 수 있다.

결정:
결제 완료의 최종 상태 변경은 결제사 웹훅에서 처리한다.

대안:
- 클라이언트 리다이렉트에서 즉시 완료 처리
- 주기적 폴링으로 결제 상태 확인

결과:
주문 UI는 잠시 "확인 중" 상태를 보여줄 수 있다.
```

핵심은 "결정"만 적지 않는 것입니다. 맥락과 대안을 함께 적어야 나중에 조건이 바뀌었을 때 다시 판단할 수 있습니다.

## 코드 가까이에 둔다

문서가 위키 한구석에 있으면 잊힙니다. 결정 로그는 코드 저장소 안에 두는 편이 좋습니다. PR에서 함께 리뷰되고, 변경 이력도 남습니다.

추천 위치는 팀 성격에 따라 다릅니다.

- 저장소 전체 결정: `docs/decisions`
- 특정 도메인 결정: `src/orders/decisions.md`
- 운영 결정: `docs/runbooks/decisions.md`

너무 흩어지면 찾기 어렵고, 너무 중앙화하면 쓰기 어렵습니다. 도메인별 한 파일 정도가 실용적인 균형입니다.

## 상태를 관리한다

결정은 영원하지 않습니다. 당시에는 맞았지만 지금은 바뀐 선택도 있습니다. 그래서 상태 필드가 필요합니다.

간단한 상태만으로 충분합니다.

- 제안
- 채택
- 대체됨
- 폐기

대체된 결정은 삭제하지 말고 새 결정으로 연결합니다. 과거 결정을 지우면 같은 실수를 반복할 가능성이 커집니다.

## 회의록과 구분한다

결정 로그는 회의에서 나온 모든 말을 기록하는 곳이 아닙니다. 누가 어떤 의견을 냈는지보다 최종 선택과 이유가 중요합니다. 감정, 논쟁, 진행 상황을 모두 넣으면 문서가 길어지고 읽히지 않습니다.

좋은 결정 로그는 다음 질문에 답합니다.

- 어떤 문제를 해결하려 했나
- 어떤 선택을 했나
- 어떤 대안을 버렸나
- 이 선택 때문에 생기는 제약은 무엇인가
- 언제 다시 검토해야 하나

## 체크리스트

- 나중에 다시 논의될 만한 선택만 기록한다.
- 맥락, 결정, 대안, 결과 형식을 고정한다.
- 문서를 코드 저장소 가까이에 둔다.
- 결정 상태와 대체 관계를 남긴다.
- 회의록이 아니라 판단 근거만 기록한다.

결정 로그는 문서화를 위한 문서가 아닙니다. 팀이 같은 질문에 시간을 다시 쓰지 않게 만드는 작은 장치입니다.
