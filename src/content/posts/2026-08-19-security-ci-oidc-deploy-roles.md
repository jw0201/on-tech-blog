CI는 배포 권한을 갖기 때문에 공격자에게 매력적인 표적입니다. 저장소 secret에 장기 클라우드 키를 넣어두면 유출 시 피해 범위가 큽니다. 키를 회전하더라도 어떤 워크플로에서 어디까지 쓸 수 있는지 관리하기 어렵습니다.

OIDC 기반 배포 역할은 CI가 실행될 때 짧게 유효한 토큰으로 클라우드 역할을 얻는 방식입니다. 장기 키를 저장하지 않고도 배포할 수 있습니다.

## 저장소 secret을 권한 경계로 보지 않는다

secret은 숨겨진 문자열일 뿐입니다. 한 번 접근 권한이 있는 워크플로에서는 같은 secret을 사용할 수 있고, 실수로 로그에 노출될 수도 있습니다. 또한 secret 이름만으로는 어떤 브랜치, 어떤 환경, 어떤 job에서 쓰이는지 알기 어렵습니다.

OIDC를 쓰면 클라우드 쪽 trust policy에서 조건을 걸 수 있습니다.

- 특정 저장소
- 특정 브랜치
- 특정 환경
- 특정 workflow 파일
- 특정 subject claim

권한 판단을 CI 설정과 클라우드 IAM 정책 양쪽에서 확인할 수 있다는 점이 중요합니다.

## 역할을 환경별로 나눈다

production과 staging이 같은 배포 역할을 공유하면 작은 실수가 큰 장애로 이어질 수 있습니다. 환경별로 역할을 나누고, production 역할은 더 엄격한 조건을 둡니다.

예를 들어 production 역할은 다음 조건을 요구할 수 있습니다.

- 기본 브랜치에서만 실행
- GitHub Environment 승인 완료
- 특정 workflow 경로
- 태그 또는 릴리스 이벤트

staging 역할은 pull request preview를 위해 조금 넓게 허용할 수 있지만, 접근 가능한 클라우드 리소스는 제한해야 합니다.

## 역할 권한은 배포 작업만 허용한다

CI 역할에 관리자 권한을 주면 OIDC를 쓰는 장점이 줄어듭니다. 역할은 배포에 필요한 API만 허용해야 합니다.

검토할 권한은 다음과 같습니다.

- 컨테이너 이미지 push
- 특정 서비스 업데이트
- 특정 bucket 업로드
- 특정 secret read
- migration job 실행

반대로 사용자 관리, 광범위한 secret 읽기, IAM 정책 수정 같은 권한은 배포 역할에서 제외해야 합니다.

## Claim 조건을 코드 리뷰 대상으로 만든다

OIDC trust policy는 보안 설정이지만 코드와 함께 리뷰되어야 합니다. 특히 `sub` 조건이 넓으면 의도하지 않은 workflow가 역할을 얻을 수 있습니다.

나쁜 예는 다음과 같습니다.

```text
repo:org/repo:*
```

더 나은 조건은 다음처럼 구체적입니다.

```text
repo:org/repo:environment:production
```

클라우드마다 claim 표현은 다르지만 원칙은 같습니다. 누가, 어떤 이벤트에서, 어떤 환경을 대상으로 할 때 역할을 받을 수 있는지 좁혀야 합니다.

## 전환은 병행 기간을 둔다

장기 키에서 OIDC로 바꿀 때는 바로 secret을 지우기보다 짧은 병행 기간을 두는 편이 안전합니다.

1. OIDC 역할을 만들고 최소 권한을 부여한다.
2. staging 배포부터 전환한다.
3. production 배포를 전환하되 기존 키는 비활성 대기한다.
4. 배포 로그와 클라우드 감사 로그를 확인한다.
5. 기존 장기 키를 폐기하고 secret에서 제거한다.

CI 배포 보안의 목표는 "키를 잘 숨기기"가 아니라 "훔칠 장기 키를 없애기"입니다. OIDC 역할과 좁은 trust policy를 사용하면 배포 권한을 훨씬 선명하게 관리할 수 있습니다.
