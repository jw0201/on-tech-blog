큐는 서비스 사이의 결합을 줄이는 좋은 도구입니다. 하지만 큐를 넣었다고 자동으로 느슨한 결합이 생기지는 않습니다. 메시지 스키마, 재시도 정책, 순서 보장, 실패 처리 계약이 없으면 큐는 보이지 않는 API가 되고, 장애는 더 늦게 발견됩니다.

큐를 시스템 경계로 쓸 때는 HTTP API를 설계하듯 계약을 정해야 합니다.

## 메시지 스키마를 버전 관리한다

큐 메시지는 코드 내부 객체가 아닙니다. 생산자와 소비자가 서로 다른 배포 주기를 가질 수 있으므로 메시지 스키마는 명시적으로 버전 관리해야 합니다.

```json
{
  "schemaVersion": 2,
  "eventId": "evt_123",
  "type": "invoice.created",
  "occurredAt": "2026-06-23T00:00:00Z",
  "payload": {
    "invoiceId": "inv_123",
    "accountId": "acct_456"
  }
}
```

소비자는 모르는 필드를 무시할 수 있어야 하고, 생산자는 기존 필드를 갑자기 삭제하면 안 됩니다. 메시지 변경은 데이터베이스 마이그레이션처럼 확장, 전환, 정리 순서로 진행하는 것이 안전합니다.

## 재시도 가능 오류를 구분한다

큐 소비자는 실패하면 재시도됩니다. 하지만 모든 실패가 재시도 대상은 아닙니다. 일시적인 네트워크 오류와 잘못된 메시지 스키마를 같은 방식으로 다루면 큐가 막힙니다.

오류는 최소한 세 가지로 나눕니다.

- 일시 오류: 외부 API 타임아웃, 데이터베이스 연결 실패
- 영구 오류: 필수 필드 누락, 지원하지 않는 타입
- 비즈니스 보류: 아직 필요한 데이터가 생성되지 않음

일시 오류는 지수 백오프로 재시도하고, 영구 오류는 dead letter queue로 보내야 합니다. 비즈니스 보류는 재시도보다 상태 전환이나 보상 작업이 더 적합할 수 있습니다.

## 순서 보장의 범위를 좁힌다

큐에서 전체 순서를 보장하려 하면 처리량과 운영성이 크게 떨어집니다. 대부분의 시스템은 전체 순서가 아니라 특정 키 안에서의 순서만 필요합니다.

예를 들어 계정 이벤트는 `accountId` 단위 순서가 중요할 수 있지만, 서로 다른 계정끼리는 순서가 필요 없습니다. 이 기준을 파티션 키로 명시해야 합니다.

```text
partition key:
  accountId for account lifecycle events
  orderId for order payment events
```

순서가 필요 없는 이벤트는 병렬 처리할 수 있게 두는 편이 좋습니다. 순서 요구사항을 좁히는 것이 큐 설계의 핵심입니다.

## 소비자 소유권을 명확히 한다

하나의 메시지를 여러 팀이 소비하기 시작하면 생산자는 누가 어떤 필드에 의존하는지 알기 어렵습니다. 이벤트는 공개 API처럼 소유권과 변경 절차가 있어야 합니다.

문서에는 다음을 적어야 합니다.

- 이벤트 소유 팀
- 생산 조건
- 필드 의미와 타입
- 소비 중인 서비스 목록
- 호환성 규칙
- 폐기 예정 필드와 일정

소비자 목록은 완벽하지 않아도 됩니다. 중요한 것은 변경 전에 알릴 수 있는 최소한의 경로를 만드는 것입니다.

## DLQ는 알림이 아니라 작업 큐다

Dead letter queue는 실패 메시지를 버리는 장소가 아닙니다. 운영자가 원인을 확인하고 재처리하거나 폐기할 수 있는 작업 큐입니다.

DLQ 운영에 필요한 기능은 다음입니다.

- 실패 원인과 스택 정보 확인
- 원본 메시지 조회
- 동일 원인 묶음 보기
- 수정 후 재처리
- 의도적 폐기와 감사 로그

DLQ가 쌓이는데 아무도 보지 않으면 큐 기반 시스템은 조용히 데이터 불일치를 만듭니다.

## 체크리스트

- 메시지 스키마와 버전을 명시한다.
- 일시 오류, 영구 오류, 비즈니스 보류를 구분한다.
- 순서 보장은 필요한 키 범위로 좁힌다.
- 이벤트 소유 팀과 소비자 목록을 관리한다.
- DLQ를 재처리 가능한 운영 큐로 다룬다.

큐는 비동기를 위한 배관이 아니라 서비스 사이의 계약입니다. 계약으로 다루면 배포는 느슨해지고, 장애는 더 빨리 설명됩니다.
