벌크 API는 단순해 보입니다. 단건 API가 있으니 배열을 받아 반복하면 될 것 같습니다. 하지만 실제 운영에서는 부분 실패, 중복 요청, 타임아웃, 재시도 때문에 단건 API보다 훨씬 까다롭습니다. 벌크 API를 안정적으로 만들려면 "성공 응답 모양"보다 "실패가 섞였을 때의 계약"을 먼저 정해야 합니다.

## 전부 성공만 허용할지 정한다

가장 먼저 결정할 것은 원자성입니다. 100개 중 하나라도 실패하면 전체를 실패시킬지, 성공 가능한 99개는 처리할지 정해야 합니다. 둘 중 하나가 항상 정답은 아닙니다.

결제, 재고 차감, 권한 변경처럼 일관성이 중요한 작업은 전체 성공 또는 전체 실패가 낫습니다. 반대로 알림 발송, 태그 추가, 상품 정보 갱신처럼 항목 간 의존성이 약한 작업은 부분 성공이 실용적입니다.

문제는 이 정책을 문서화하지 않은 API입니다. 클라이언트는 실패 응답을 보고 어떤 항목이 반영됐는지 알 수 없고, 결국 운영자가 데이터베이스를 직접 확인해야 합니다.

## 응답은 항목별 결과를 포함한다

부분 성공을 허용한다면 응답에는 반드시 항목별 결과가 있어야 합니다.

```json
{
  "requestId": "bulk_01J...",
  "results": [
    { "clientId": "row-1", "status": "succeeded", "resourceId": "u_123" },
    { "clientId": "row-2", "status": "failed", "code": "DUPLICATE_EMAIL" }
  ]
}
```

여기서 `clientId`가 중요합니다. 서버의 리소스 ID는 실패한 항목에는 없을 수 있습니다. 클라이언트가 보낸 식별자를 그대로 돌려주면 화면의 어느 행이 실패했는지 정확히 표시할 수 있습니다.

## 재시도 가능한 실패를 구분한다

벌크 처리 중 일부 실패는 다시 보내면 성공할 수 있습니다. 일시적인 네트워크 오류, 외부 API 제한, 잠금 충돌 같은 경우입니다. 반대로 유효성 오류, 권한 부족, 중복 데이터는 그대로 재시도해도 실패합니다.

따라서 오류 코드는 재시도 가능 여부를 포함해야 합니다.

```json
{
  "status": "failed",
  "code": "RATE_LIMITED",
  "retryable": true,
  "message": "잠시 후 다시 시도해 주세요."
}
```

클라이언트가 이 값을 알면 실패한 항목만 다시 보내거나, 사용자에게 수정이 필요한 항목만 강조할 수 있습니다.

## 멱등성 키를 지원한다

벌크 API는 타임아웃이 자주 발생합니다. 요청은 서버에서 처리됐지만 클라이언트는 응답을 받지 못하는 상황이 생깁니다. 이때 같은 요청을 다시 보내면 중복 생성이나 중복 발송이 일어날 수 있습니다.

해결책은 요청 단위의 멱등성 키입니다. 클라이언트가 `Idempotency-Key`를 보내고, 서버는 같은 키와 같은 본문에 대해 이전 결과를 반환합니다. 항목별 `clientId`와 함께 쓰면 중복 방지와 결과 매칭이 쉬워집니다.

주의할 점은 멱등성 키의 보관 기간입니다. 영원히 저장할 필요는 없지만, 클라이언트 재시도 정책보다 충분히 길어야 합니다. 예를 들어 24시간 보관이면 대부분의 운영 재시도에는 충분합니다.

## 큰 요청은 작업으로 분리한다

처리량이 큰 벌크 API를 동기 HTTP 요청으로 끝내려 하면 타임아웃과 메모리 문제가 따라옵니다. 수천 개 이상을 처리하거나 외부 시스템 호출이 섞인다면 작업 생성 API로 나누는 편이 좋습니다.

첫 요청은 작업 ID를 반환하고, 클라이언트는 진행률과 결과를 조회합니다. 이 방식은 느리지만 관측 가능하고 취소나 재시도가 쉽습니다. 특히 운영자가 실패 항목을 다운로드해야 하는 기능이라면 비동기 작업 모델이 더 자연스럽습니다.

## 체크리스트

- 전체 실패와 부분 성공 중 어느 계약인지 명시한다.
- 부분 성공이면 항목별 결과와 클라이언트 식별자를 돌려준다.
- 오류 코드에 재시도 가능 여부를 포함한다.
- 중복 요청을 막기 위해 멱등성 키를 지원한다.
- 큰 작업은 동기 API보다 작업 큐와 상태 조회로 분리한다.

벌크 API의 품질은 빠른 성공보다 애매한 실패를 얼마나 잘 설명하는지에서 드러납니다. 사용자가 실패한 몇 개만 고칠 수 있다면, 벌크 기능은 운영 도구가 아니라 믿을 수 있는 제품 기능이 됩니다.
