CI가 초록색이고 배포 명령이 성공했다고 해서 릴리스가 끝난 것은 아닙니다. 새 버전이 트래픽을 받기 시작한 뒤 오류율, 지연 시간, 핵심 사용자 흐름이 정상인지 확인해야 배포가 완료됐다고 말할 수 있습니다.

배포 관측성은 큰 플랫폼 팀만의 일이 아닙니다. 작은 서비스도 최소 체크리스트를 갖추면 장애 감지와 롤백 판단이 훨씬 빨라집니다.

## 배포 이벤트를 로그와 지표에 남긴다

가장 먼저 필요한 것은 "언제 어떤 버전이 배포됐는지"입니다. 장애 그래프에서 오류율이 올라간 시점과 배포 시점을 함께 볼 수 있어야 합니다.

배포 이벤트에는 다음 정보가 있으면 좋습니다.

- 서비스 이름
- 배포 환경
- 버전 또는 커밋 SHA
- 배포 시작과 완료 시각
- 배포한 주체
- 롤백 여부

이 정보는 대시보드 주석, 로그 이벤트, 릴리스 테이블 중 어디에 있어도 됩니다. 중요한 것은 장애 분석자가 터미널 기록을 뒤지지 않아도 되는 것입니다.

## 핵심 지표는 버전별로 본다

전체 오류율만 보면 새 버전 문제가 가려질 수 있습니다. 트래픽이 점진적으로 넘어가는 동안에는 구버전과 신버전이 같이 떠 있기 때문입니다.

릴리스 확인 지표는 가능한 한 버전별로 나눠 봅니다.

- HTTP 5xx 비율
- 주요 API p95 지연 시간
- 프론트엔드 오류 수
- 작업 큐 실패율
- DB connection pool 대기 시간
- 외부 API 실패율

버전 라벨을 너무 많이 붙이면 cardinality 문제가 생길 수 있으니 보존 기간과 집계 방식을 정해야 합니다. 그래도 배포 직후 몇 시간 동안 새 버전만 따로 보는 능력은 매우 유용합니다.

## 사용자 흐름 기반 스모크 테스트를 둔다

헬스 체크 엔드포인트가 200을 반환해도 실제 사용자가 로그인하거나 결제하거나 파일을 업로드할 수 있다는 뜻은 아닙니다. 배포 후 스모크 테스트는 시스템 내부 상태보다 사용자 흐름을 기준으로 잡아야 합니다.

좋은 스모크 테스트는 짧고 결정적입니다.

- 로그인 후 내 정보 조회
- 검색 API 호출
- 샘플 데이터 생성과 삭제
- 주요 페이지 렌더링
- 권한이 필요한 API의 정상 응답

스모크 테스트가 너무 길면 배포마다 무시됩니다. 가장 많이 쓰이고 실패 비용이 큰 흐름을 작게 자동화하는 편이 낫습니다.

## 롤백 기준을 미리 정한다

장애가 난 뒤 회의하면서 롤백 기준을 정하면 늦습니다. 배포 전에 어떤 지표가 어느 정도 나빠지면 롤백할지 합의해야 합니다.

예시는 다음과 같습니다.

- 새 버전 5xx가 5분간 2% 초과
- 로그인 성공률이 기준선 대비 10% 이상 하락
- 결제 생성 실패가 3건 이상 발생
- p95 지연 시간이 2배 이상 증가하고 원인이 배포 변경과 연결됨

기준은 서비스마다 달라야 합니다. 내부 관리자 도구와 결제 API의 기준이 같을 수는 없습니다.

## 배포 완료 메시지에 관측 결과를 포함한다

배포 알림은 "완료" 한 줄보다 조금 더 구체적이어야 합니다.

- 배포 버전
- 스모크 테스트 결과
- 주요 지표 확인 결과
- 롤백 필요 없음 또는 감시 중
- 관련 대시보드 링크

이렇게 남겨두면 나중에 문제가 생겼을 때 릴리스 당시 상태를 빠르게 확인할 수 있습니다.

배포 관측성은 완벽한 대시보드를 만드는 일이 아닙니다. 새 코드가 사용자에게 닿는 순간을 팀이 함께 볼 수 있게 만드는 일입니다. 배포 성공 기준을 CI 결과에서 운영 신호까지 확장하면 릴리스가 훨씬 덜 불안해집니다.
