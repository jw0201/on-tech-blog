계약 테스트는 서비스 사이의 약속을 지키는 데 도움이 됩니다. 하지만 fixture가 오래되면 테스트는 오히려 거짓 안정감을 줍니다. 실제 API는 바뀌었는데 샘플 JSON만 통과하거나, 어떤 팀이 고쳐야 하는지 알 수 없는 실패가 반복됩니다. 계약 테스트의 품질은 테스트 코드보다 fixture 관리에서 갈립니다.

## fixture의 소유자를 정한다

소비자 중심 계약 테스트에서는 API를 사용하는 쪽이 기대하는 응답을 정의합니다. 제공자 중심에서는 서버가 대표 응답을 제공합니다. 어떤 방식을 쓰든 fixture의 소유자가 명확해야 합니다.

소유자가 없으면 fixture는 공용 쓰레기통이 됩니다. 필드를 추가해도 되는지, 삭제해도 되는지, 실패했을 때 누가 고칠지 알 수 없습니다. 저장소 구조에도 소유권을 드러내는 편이 좋습니다.

```text
contracts/
  billing-api/
    owner: payments-platform
    consumers/
      admin-dashboard/
      invoice-worker/
```

문서가 따로 있더라도 파일 구조에서 어느 정도 읽혀야 합니다.

## 정상 케이스만 두지 않는다

계약은 성공 응답만의 문제가 아닙니다. 권한 없음, validation 실패, rate limit, 빈 결과, deprecated 필드도 계약의 일부입니다. 특히 클라이언트가 에러 코드를 분기한다면 에러 응답 fixture가 반드시 필요합니다.

```json
{
  "error": {
    "code": "INVALID_STATUS",
    "message": "status must be one of paid, pending, void"
  }
}
```

에러 메시지 전체를 엄격하게 고정할지, 코드만 고정할지도 정해야 합니다. 사용자에게 노출되지 않는 내부 메시지를 고정하면 작은 문구 수정에도 테스트가 깨질 수 있습니다.

## fixture에 버전을 붙인다

API가 진화하면 fixture도 진화합니다. 변경을 덮어쓰기만 하면 이전 소비자가 어떤 계약에 의존했는지 사라집니다. 큰 변경에는 버전을 붙여 공존 기간을 둡니다.

```text
invoice-created.v1.json
invoice-created.v2.json
```

버전은 무조건 많을수록 좋은 것이 아닙니다. 지원이 끝난 버전은 제거해야 합니다. 다만 제거할 때는 어떤 소비자가 더 이상 사용하지 않는지 확인할 수 있어야 합니다.

## 실패 메시지를 행동 가능하게 만든다

계약 테스트가 실패했을 때 "JSON mismatch"만 보이면 사람이 diff를 파야 합니다. 실패 메시지는 어떤 필드가 깨졌고, 그것이 breaking change인지 알려줘야 합니다.

유용한 실패 메시지에는 다음 정보가 들어갑니다.

- 변경된 경로: `data.items[0].price.currency`
- 기대 타입과 실제 타입
- 필수 필드 누락 여부
- 영향을 받는 소비자
- 허용 가능한 업데이트 절차

실패 메시지가 좋아지면 계약 테스트는 팀 간 blame 도구가 아니라 대화의 출발점이 됩니다.

## 체크리스트

- fixture마다 소유 팀이나 소비자를 명확히 둔다.
- 성공, 실패, 빈 결과, 권한 케이스를 함께 관리한다.
- 큰 계약 변경에는 fixture 버전을 둔다.
- 내부 문구보다 안정적인 코드와 구조를 검증한다.
- 실패 메시지에 영향받는 소비자와 필드 경로를 표시한다.

계약 테스트는 한 번 작성하고 끝나는 테스트가 아닙니다. 서비스 사이의 약속이 바뀔 때마다 함께 업데이트되는 작은 문서이자 실행 가능한 합의입니다.
