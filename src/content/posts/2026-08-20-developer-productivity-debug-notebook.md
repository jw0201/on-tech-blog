장애나 까다로운 버그를 조사할 때 개발자는 많은 작은 결정을 합니다. 어떤 로그를 볼지, 어떤 메트릭이 의미 있는지, 어떤 SQL로 상태를 확인할지, 어느 시점부터 이상했는지 판단합니다. 문제는 이 지식이 티켓과 채팅, 터미널 히스토리에 흩어진다는 점입니다.

디버깅 노트북은 반복되는 조사 흐름을 문서화한 작업 도구입니다. 회고 문서처럼 사건이 끝난 뒤 쓰는 글이 아니라, 다음 조사 때 바로 실행할 수 있는 짧은 절차 모음입니다.

## 증상에서 시작한다

좋은 디버깅 노트북은 시스템 구조가 아니라 증상으로 시작합니다. 문제를 만난 사람은 보통 "사용자 가입이 실패한다"거나 "결제 상태가 pending에 머문다"처럼 증상을 가지고 들어옵니다.

각 증상 아래에는 바로 확인할 질문을 둡니다.

- 영향받은 사용자나 테넌트는 누구인가?
- 언제부터 발생했는가?
- 모든 요청인가, 특정 조건인가?
- 최근 배포나 설정 변경이 있었는가?
- 재시도하면 성공하는가?

이 질문은 조사의 방향을 빠르게 좁힙니다.

## 명령과 쿼리는 실행 가능한 형태로 둔다

"로그를 확인한다"는 노트는 별 도움이 되지 않습니다. 어떤 로그를 어떤 필드로 필터링해야 하는지 적어야 합니다.

예를 들면 다음처럼 구체화합니다.

```bash
kubectl logs deploy/payment-worker --since=30m | rg "request_id|payment_id"
```

SQL도 마찬가지입니다. 운영 데이터베이스에 그대로 붙여 넣는 쿼리는 조심해야 하지만, 읽기 전용 확인 쿼리 템플릿은 큰 도움이 됩니다.

```sql
select id, status, updated_at, last_error
from payment_jobs
where payment_id = :payment_id;
```

변수 위치를 명확히 두면 다음 사람이 빠르게 사용할 수 있습니다.

## 정상 기준을 함께 적는다

조사 명령만 있으면 결과 해석이 어렵습니다. 노트북에는 정상 범위도 함께 있어야 합니다.

- 큐 대기 시간이 평소 2분 이하인지
- 실패율이 1%를 넘으면 비정상인지
- 특정 상태가 10분 이상 유지되면 stuck인지
- 재시도 횟수가 몇 회 이상이면 수동 개입이 필요한지

정상 기준이 없으면 같은 그래프를 보고도 사람마다 다른 결론을 냅니다.

## 의사결정 분기를 만든다

디버깅은 직선 절차가 아닙니다. 확인 결과에 따라 다음 행동이 달라집니다. 그래서 노트북에는 분기가 있어야 합니다.

- 큐에 작업이 없으면 API 요청 생성 경로를 확인한다.
- 작업은 있지만 worker 로그가 없으면 배포 상태를 확인한다.
- worker가 처리했지만 상태가 그대로면 DB 업데이트 실패를 확인한다.
- 외부 API timeout이면 재시도 정책과 rate limit을 확인한다.

이런 분기는 신규 온콜이 문제를 놓치지 않게 해줍니다.

## 해결 후 노트북을 갱신한다

디버깅 노트북은 사건이 끝난 뒤 가장 가치가 커집니다. 이번 조사에서 새로 알게 된 확인 방법, 쓸모없었던 가설, 추가된 대시보드 링크를 바로 반영해야 합니다.

다만 모든 세부사항을 넣으면 문서가 무거워집니다. 남길 것은 재사용 가능한 절차입니다.

- 다시 쓸 수 있는 명령
- 새로 발견한 정상 기준
- 반복 가능한 복구 절차
- 잘못된 기존 가정

디버깅 노트북은 지식을 멋지게 정리하는 문서가 아닙니다. 다음 장애에서 20분을 줄이는 작업대입니다. 증상, 확인 명령, 정상 기준, 분기, 복구 절차를 작게 모아두면 팀 전체의 조사 속도가 꾸준히 빨라집니다.
