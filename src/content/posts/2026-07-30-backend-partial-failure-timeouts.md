분산 시스템에서 가장 위험한 가정은 "대부분 빠르니까 괜찮다"입니다. 의존 서비스가 느려질 때 호출자는 기다리고, 스레드와 connection pool은 쌓이고, 결국 멀쩡한 기능까지 같이 느려집니다.

Timeout은 실패를 없애는 장치가 아니라 실패의 범위를 자르는 장치입니다.

## 사용자 예산에서 시작한다

먼저 사용자가 기다릴 수 있는 전체 시간을 정합니다. 예를 들어 검색 API가 800ms 안에 응답해야 한다면, 내부 호출 하나에 800ms를 모두 줄 수 없습니다.

요청 경로가 다음과 같다면 각 단계의 예산이 필요합니다.

- 인증 확인
- 검색 인덱스 조회
- 권한 필터링
- 추천 데이터 보강
- 응답 직렬화

각 호출의 timeout을 합쳤을 때 전체 SLO를 넘지 않도록 설계해야 합니다.

## p95가 아니라 꼬리를 본다

평균 응답 시간이 40ms인 서비스도 p99가 2초일 수 있습니다. Timeout을 평균 근처에 두면 정상 요청을 너무 많이 실패시키고, p99보다 훨씬 크게 두면 장애 전파를 막지 못합니다.

현실적인 기준은 다음 데이터를 함께 보는 것입니다.

- p95, p99 latency
- timeout 발생률
- 재시도 성공률
- 호출자 thread 또는 worker 포화도
- 의존 서비스 장애 시나리오

Timeout은 한 번 정하고 끝나는 값이 아니라 운영 지표로 조정하는 값입니다.

## 재시도와 함께 계산한다

Timeout만 짧게 하고 재시도를 여러 번 걸면 전체 지연은 오히려 길어질 수 있습니다.

```text
timeout 300ms * 3 attempts = 최대 900ms
```

여기에 backoff와 네트워크 비용까지 더해집니다. 호출자가 사용자 요청 안에서 재시도한다면 전체 deadline을 공유해야 합니다. 첫 번째 시도가 250ms를 썼다면 두 번째 시도에는 남은 예산만 줘야 합니다.

## fallback을 명시한다

Timeout 이후에 무엇을 할지 정하지 않으면 코드는 보통 예외를 던지고 끝납니다. 하지만 모든 의존성이 같은 중요도를 갖지는 않습니다.

예를 들어 다음처럼 나눌 수 있습니다.

- 결제 승인: 실패를 사용자에게 명확히 알린다.
- 추천 상품: 빈 배열로 응답한다.
- 감사 로그: outbox에 저장하고 나중에 전송한다.
- 프로필 이미지: 기본 이미지를 사용한다.

중요하지 않은 보강 데이터 때문에 핵심 요청이 실패하면 사용자 경험이 불필요하게 약해집니다.

## 로그에는 남은 예산을 남긴다

Timeout 로그에는 단순히 "timeout"만 남기지 말고 호출 당시의 예산과 실제 소요 시간을 남깁니다.

- dependency 이름
- timeout 값
- elapsed time
- attempt 번호
- request deadline까지 남은 시간
- fallback 사용 여부

이 정보가 있어야 timeout을 늘려야 하는지, 의존 서비스를 고쳐야 하는지, 재시도 정책을 바꿔야 하는지 판단할 수 있습니다.

좋은 timeout은 사용자를 오래 기다리게 하지 않으면서도 정상적인 느림을 과하게 실패시키지 않습니다. 그 균형은 코드 상수보다 관측과 장애 연습에서 나옵니다.
