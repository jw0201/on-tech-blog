테스트 커버리지 80%는 듣기 좋은 목표입니다. 하지만 커버리지 숫자가 높아도 중요한 경계가 비어 있으면 장애는 그대로 납니다. 반대로 숫자는 낮아도 결제, 권한, 데이터 변환 같은 핵심 경로를 잘 막고 있으면 실제 품질은 더 높을 수 있습니다.

커버리지는 "얼마나 많은 줄을 실행했는가"보다 "어떤 실패를 막을 수 있는가"로 봐야 합니다.

## 변경이 잦은 곳과 비싼 곳을 먼저 본다

테스트 우선순위는 위험도에 따라 정합니다. 위험도는 대략 두 축입니다.

- 자주 바뀌는 코드인가
- 실패했을 때 비용이 큰가

둘 다 높으면 테스트를 두껍게 가져갑니다. 예를 들어 가격 계산, 권한 체크, 데이터 동기화, 배포 설정 생성 코드는 작은 실수도 비용이 큽니다. 반면 단순한 정적 페이지나 관리자 화면의 보조 문구는 같은 수준의 테스트가 필요하지 않을 수 있습니다.

모든 코드를 똑같이 대하면 테스트는 많아지지만 신뢰는 늘지 않습니다.

## 계약 경계를 테스트한다

장애는 모듈 내부보다 경계에서 자주 생깁니다. 프론트엔드와 백엔드의 응답 형식, 서비스와 메시지 큐의 이벤트 스키마, 배치와 데이터베이스의 컬럼 의미 같은 곳입니다.

이런 경계에는 계약 테스트가 효과적입니다.

```ts
expect(response).toMatchObject({
  id: expect.any(String),
  status: expect.stringMatching(/pending|paid|failed/),
  totalAmount: expect.any(Number),
});
```

핵심은 내부 구현이 아니라 외부에서 기대하는 형태를 검증하는 것입니다. 리팩터링을 해도 계약이 유지되면 테스트가 지나가고, 호환성을 깨면 빨리 실패해야 합니다.

## 회귀 테스트는 버그가 난 자리에서 시작한다

버그를 고친 뒤 가장 좋은 테스트는 "이번 문제가 다시 나면 실패하는 테스트"입니다. 이미 실제로 발생한 문제라서 가치가 분명합니다.

회귀 테스트를 작성할 때는 구현 세부보다 증상을 기준으로 둡니다.

- 특정 입력에서 잘못된 가격이 계산되었다.
- 만료된 세션이 관리자 API를 통과했다.
- 빈 배열 응답에서 화면이 무한 로딩에 빠졌다.
- 재시도 중복으로 같은 웹훅이 두 번 처리되었다.

테스트 이름에도 버그의 조건을 드러내면 나중에 삭제하기 어렵습니다. `it("handles empty items")`보다 `it("shows an empty state instead of staying in loading when items is empty")`가 낫습니다.

## 너무 넓은 E2E는 신호를 흐린다

E2E 테스트는 사용자 관점 검증에 강하지만 느리고 흔들리기 쉽습니다. 모든 것을 E2E로 막으려 하면 실패 원인을 찾는 시간이 길어집니다.

좋은 분배는 보통 이렇습니다.

- 순수 로직: 단위 테스트
- API 계약: 통합 또는 계약 테스트
- 주요 사용자 흐름: 소수의 E2E
- 배포 환경 확인: 스모크 테스트

E2E는 "서비스가 실제로 이어지는가"를 확인하는 얇은 층으로 유지하는 편이 좋습니다. 세부 분기는 더 낮은 레벨에서 빠르게 검증합니다.

## 커버리지 예외를 문서화한다

테스트하지 않기로 한 영역도 이유를 남겨야 합니다. 생성 코드, 단순 타입 선언, 외부 라이브러리 어댑터의 얇은 위임처럼 커버리지에서 제외할 수 있는 영역은 있습니다. 하지만 예외가 늘어나면 숫자의 의미가 사라집니다.

커버리지 제외 주석에는 짧은 이유를 남깁니다. "어렵기 때문"이 아니라 "브라우저 네이티브 API 위임이며 Playwright 스모크 테스트에서 검증"처럼 대체 검증 경로를 적습니다.

## 체크리스트

- 커버리지 목표보다 위험한 코드 경로를 먼저 찾는다.
- 외부 계약 경계에 테스트를 둔다.
- 실제 버그 수정에는 회귀 테스트를 붙인다.
- E2E는 핵심 흐름 위주로 얇게 유지한다.
- 커버리지 제외에는 대체 검증 이유를 남긴다.

테스트의 목적은 숫자를 채우는 것이 아니라 바뀌어도 안심할 수 있는 영역을 늘리는 것입니다. 커버리지는 결과 지표일 뿐, 품질 전략 자체가 되어서는 안 됩니다.
