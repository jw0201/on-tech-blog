API 문서는 배포 당일에는 맞습니다. 문제는 시간이 지나면서 실제 응답과 문서가 조금씩 어긋난다는 점입니다. 필드가 추가되고, null 가능성이 바뀌고, 오류 코드가 늘어나고, enum 값이 조용히 확장됩니다. 이 차이를 API 계약 드리프트라고 볼 수 있습니다.

드리프트는 한 번에 큰 장애를 만들기보다 클라이언트 곳곳에 작은 예외 처리를 늘립니다. 결국 "문서에는 없지만 실제로는 이렇게 온다"라는 지식이 사람 머릿속에 쌓입니다.

## 계약의 기준을 하나로 정한다

먼저 무엇을 계약의 원본으로 삼을지 정해야 합니다. OpenAPI 스키마, 코드의 타입 정의, protobuf 파일, JSON Schema 중 하나가 기준이어야 합니다.

중요한 것은 기준이 여러 개가 되지 않는 것입니다. 타입 정의는 A, 문서는 B, 테스트 fixture는 C를 기준으로 움직이면 드리프트를 잡을 수 없습니다.

가능하면 계약 파일에서 다음 산출물을 생성합니다.

- API 문서
- 서버 응답 검증 코드
- 클라이언트 타입
- 예제 요청과 응답 fixture

생성까지 어렵더라도 CI에서 계약 파일과 실제 응답을 비교하는 단계는 두는 편이 좋습니다.

## 예제 응답도 테스트 대상이다

문서의 예제 응답은 사용자에게 가장 먼저 읽히는 API입니다. 하지만 예제는 자주 오래됩니다. 필드 하나가 바뀌어도 문서 빌드는 성공하기 때문입니다.

예제 JSON을 테스트 fixture로 사용하면 이 문제를 줄일 수 있습니다. 예제가 스키마를 통과하는지 검사하고, 서버에서 내려오는 실제 응답도 같은 스키마를 통과하는지 확인합니다.

예제에는 성공 응답만 두지 말고 실패 응답도 포함해야 합니다.

- 인증 실패
- 권한 없음
- validation 오류
- rate limit
- 부분 실패

실패 응답은 클라이언트 UX와 직접 연결되기 때문에 성공 응답만큼 중요합니다.

## 소비자 관점의 필수 필드를 표시한다

서버 팀 입장에서는 어떤 필드가 사용 중인지 모를 때가 많습니다. 그래서 필드를 제거하거나 null로 바꾸는 변경이 예상보다 큰 장애를 만들 수 있습니다.

소비자 주도 계약 테스트는 이 문제에 도움이 됩니다. 클라이언트가 실제로 의존하는 필드와 조건을 테스트로 표현하고, 서버 CI에서 검증하게 만드는 방식입니다.

모든 소비자를 완벽히 커버할 필요는 없습니다. 중요한 화면이나 외부 연동부터 시작하면 됩니다. 예를 들어 결제 내역 화면이 `status`, `amount`, `currency`, `createdAt`에 의존한다면 이 네 필드는 계약 테스트에 명확히 들어가야 합니다.

## 호환 가능한 변경의 기준을 문서화한다

어떤 변경이 안전한지 팀마다 기준이 다릅니다. 그래서 호환성 규칙을 명시해야 합니다.

일반적으로 안전한 변경은 다음과 같습니다.

- 선택 필드 추가
- enum 값 추가, 단 클라이언트가 unknown을 처리할 때
- 응답 객체에 새 중첩 객체 추가

위험한 변경은 다음과 같습니다.

- 필수 필드 제거
- 타입 변경
- null 가능성 변경
- 오류 코드 의미 변경
- 정렬 순서 기본값 변경

특히 enum 확장은 자주 과소평가됩니다. 클라이언트가 exhaustive switch를 쓰고 있다면 새 값 하나가 런타임 오류가 될 수 있습니다.

## 운영 로그로 계약 위반을 찾는다

테스트만으로 모든 소비자를 알 수는 없습니다. 운영 환경에서 스키마 검증을 샘플링해 응답이 계약을 벗어나는지 볼 수 있습니다. 요청 전체를 로깅하지 않고도 검증 실패의 필드 경로와 오류 코드만 남기면 충분한 경우가 많습니다.

단, 개인정보나 응답 본문 전체를 무심코 로그에 남기지 않도록 주의해야 합니다. 계약 위반을 찾으려다 보안 사고를 만들면 안 됩니다.

API 계약은 문서가 아니라 살아 있는 경계입니다. 스키마, 예제, 소비자 테스트, 운영 검증을 함께 묶으면 드리프트를 빨리 발견할 수 있고, 클라이언트와 서버가 같은 현실을 보고 일할 수 있습니다.
