프론트엔드 성능 문제처럼 보이지만 원인이 API payload에 있는 경우가 많습니다. 목록 화면에 쓰지 않는 상세 필드가 잔뜩 내려오고, 작은 카드 하나를 그리기 위해 깊은 관계 데이터가 모두 포함되고, 페이지 크기가 화면보다 훨씬 큽니다.

API payload shaping은 화면이 실제로 필요한 데이터만, 필요한 구조로, 필요한 시점에 받게 만드는 일입니다.

## 목록과 상세 응답을 분리한다

가장 흔한 문제는 목록 API가 상세 API와 같은 모델을 반환하는 것입니다. 목록에서는 제목, 상태, 작성자 이름, 수정일 정도만 필요한데 상세 설명, 권한 목록, 변경 이력까지 내려오면 낭비가 큽니다.

목록 응답은 목록에 맞게 작게 설계합니다.

- 식별자
- 화면에 바로 표시할 핵심 필드
- 정렬과 필터에 필요한 값
- 다음 페이지를 가져올 cursor
- 필요한 경우 요약 통계

상세 화면에서만 필요한 데이터는 별도 endpoint나 lazy query로 분리합니다. 이렇게 하면 초기 렌더링이 빨라지고 캐시 단위도 명확해집니다.

## 중첩 깊이를 제한한다

관계 데이터를 편하게 내려주다 보면 응답이 나무처럼 커집니다. 프로젝트가 팀을 포함하고, 팀이 멤버를 포함하고, 멤버가 권한과 프로필 이미지를 포함하는 식입니다. 이런 응답은 작은 변경에도 캐시 무효화 범위가 커지고, 클라이언트 상태 병합도 어려워집니다.

중첩은 화면에서 한 번에 보여주는 수준까지만 허용하는 편이 좋습니다. 더 필요한 데이터는 명시적으로 추가 요청합니다.

예를 들어 프로젝트 목록에서는 팀 이름과 멤버 수만 내려주고, 멤버 상세는 팀 패널을 열 때 가져옵니다. 사용자가 보지 않는 데이터를 미리 가져오는 것은 빠른 UX가 아니라 불필요한 비용일 수 있습니다.

## 필드 선택은 신중하게 도입한다

GraphQL이나 `fields` 파라미터처럼 클라이언트가 필드를 고르는 방식은 강력합니다. 하지만 캐시, 권한, 문서화가 복잡해질 수 있습니다.

작은 팀에서는 먼저 endpoint별 응답 모델을 명확히 나누는 것이 더 단순합니다. 필드 선택이 필요해지는 경우는 대체로 다음과 같습니다.

- 여러 클라이언트가 같은 리소스를 다른 모양으로 사용
- 모바일과 데스크톱 payload 차이가 큼
- 네트워크 비용이 제품 성능의 주요 병목
- 백엔드가 응답 조합을 안정적으로 관리할 수 있음

도입한다면 허용 필드 목록, 권한 검사, 캐시 키 규칙을 함께 설계해야 합니다.

## 페이지 크기는 데이터 크기로도 본다

페이지 크기를 row 수로만 정하면 안 됩니다. 50개 행이어도 각 행이 무겁다면 응답은 커집니다. 반대로 작은 행은 100개도 부담이 적을 수 있습니다.

페이지 크기는 다음 요소를 함께 보고 정합니다.

- 평균 응답 byte 크기
- p95 직렬화 시간
- 클라이언트 파싱 시간
- 렌더링되는 DOM 수
- 사용자가 실제로 스크롤하는 범위

운영 지표를 보면 "사용자는 대부분 첫 20개만 보는데 200개씩 내려준다" 같은 낭비를 쉽게 찾을 수 있습니다.

## payload 변경은 계약 변경이다

응답 필드를 줄이는 것은 성능 개선이지만 동시에 API 계약 변경입니다. 사용 중인 클라이언트가 있다면 필드 제거는 깨지는 변경이 될 수 있습니다. 먼저 사용 여부를 확인하고, deprecate 기간을 두고, 필요한 경우 버전 분리를 해야 합니다.

새 필드를 추가할 때도 비용을 봐야 합니다. 필드 하나가 내부적으로 N+1 쿼리를 만들거나 외부 API 호출을 유발할 수 있습니다.

API payload shaping은 단순 최적화가 아닙니다. 화면 목적, 데이터 소유권, 캐시 정책, 호환성을 함께 다루는 설계입니다. 필요한 데이터를 작고 예측 가능한 모양으로 내려주면 프론트엔드와 백엔드 성능이 동시에 좋아집니다.
