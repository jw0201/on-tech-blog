스트리밍 렌더링은 사용자가 모든 데이터를 기다리지 않고 화면을 먼저 볼 수 있게 합니다. 하지만 단순히 `Loading...`을 여러 곳에 뿌리면 화면이 덜컹거리고, 사용자는 무엇이 준비된 것인지 알기 어렵습니다. 좋은 스트리밍 UI는 빠르게 보이는 것보다 예측 가능하게 채워지는 것이 중요합니다.

## 먼저 보여줄 영역을 정한다

모든 영역을 동시에 스트리밍할 필요는 없습니다. 사용자가 페이지를 이해하는 데 필요한 뼈대와 상호작용 가능한 핵심 영역을 먼저 정해야 합니다.

예를 들어 대시보드라면 다음 순서가 자연스럽습니다.

- 페이지 제목과 필터 상태
- 현재 선택된 기간, 계정, 권한 정보
- 핵심 지표의 카드 틀
- 느린 차트와 상세 테이블
- 추천, 로그, 보조 설명

이 순서는 기술 구조보다 사용자의 읽기 순서를 기준으로 잡는 편이 좋습니다. 서버에서 빨리 오는 데이터가 항상 먼저 보여야 하는 것은 아닙니다.

## fallback은 실제 레이아웃을 닮아야 한다

fallback이 실제 콘텐츠와 크기가 다르면 데이터가 도착할 때 레이아웃이 흔들립니다. 스켈레톤은 장식이 아니라 공간 예약 장치입니다. 카드, 표, 리스트처럼 고정된 형태가 있다면 실제 컴포넌트와 같은 `min-height`, 열 너비, 패딩을 공유해야 합니다.

```tsx
<Suspense fallback={<MetricCardSkeleton />}>
  <RevenueMetricCard period={period} />
</Suspense>
```

스켈레톤 컴포넌트는 별도 디자인을 만들기보다 실제 카드의 구조를 재사용하는 편이 유지보수에 좋습니다. 제목 줄, 값 영역, 보조 텍스트 영역만 비워 두면 됩니다.

## 지연의 의미를 나눈다

모든 로딩이 같은 의미는 아닙니다. 초기 진입 로딩, 필터 변경 후 재계산, 백그라운드 새로고침은 서로 다른 상태입니다. 같은 스피너로 표시하면 사용자는 화면이 멈췄는지, 새 데이터를 가져오는 중인지 구분할 수 없습니다.

실무에서는 세 가지 상태를 분리하면 충분한 경우가 많습니다.

- `initial`: 아직 의미 있는 데이터가 없다.
- `refreshing`: 기존 데이터를 유지한 채 새 데이터를 가져온다.
- `partial`: 일부 영역은 준비됐고 일부 영역은 지연된다.

필터 변경처럼 사용자가 직접 일으킨 작업은 이전 데이터를 흐리게 유지하고 상단에 작은 진행 상태를 보여주는 것이 좋습니다. 빈 화면으로 되돌리면 사용자는 맥락을 잃습니다.

## 실패 영역을 작게 가둔다

스트리밍 UI에서 한 영역의 실패가 전체 페이지 실패로 번지면 장점이 사라집니다. 느린 차트 API가 실패해도 상단 지표와 필터는 계속 사용할 수 있어야 합니다.

에러 경계는 데이터 소스 단위로 나누는 것이 실용적입니다.

```tsx
<ChartErrorBoundary fallback={<ChartUnavailable />}>
  <Suspense fallback={<ChartSkeleton />}>
    <TrafficChart />
  </Suspense>
</ChartErrorBoundary>
```

fallback과 error UI는 비슷한 크기를 가져야 합니다. 그래야 실패가 발생해도 페이지 높이가 갑자기 바뀌지 않습니다.

## 측정 기준을 정한다

스트리밍은 체감 성능을 개선하기 위한 기술입니다. 따라서 빌드 후에는 다음 지표를 확인해야 합니다.

- 첫 의미 콘텐츠가 보이는 시간
- 주요 상호작용 가능 시점
- 스켈레톤이 실제 콘텐츠로 바뀌는 평균 시간
- 사용자가 같은 필터를 반복 클릭하는 비율
- 에러 fallback 노출 빈도

특히 스켈레톤이 5초 이상 오래 남는 영역은 성능 문제가 아니라 제품 문제로 보일 수 있습니다. 그런 영역은 캐시, 사전 계산, 페이지 분리 중 하나를 검토해야 합니다.

## 체크리스트

- 먼저 보여줄 영역을 사용자의 읽기 순서로 정했다.
- fallback이 실제 컴포넌트와 같은 공간을 차지한다.
- 초기 로딩과 새로고침 로딩을 구분한다.
- 실패를 데이터 소스 단위로 격리한다.
- 스트리밍 도입 전후의 체감 지표를 비교한다.

스트리밍 렌더링은 마법처럼 빠른 화면을 만드는 기능이 아닙니다. 화면이 준비되는 과정을 사용자가 이해할 수 있게 설계할 때 비로소 제품 경험이 좋아집니다.
