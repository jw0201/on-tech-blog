읽기 모델은 쓰기 모델에서 데이터를 복사한 테이블이 아닙니다. 사용자가 자주 묻는 질문에 빠르고 안정적으로 답하기 위한 별도의 형태입니다. 그래서 읽기 모델을 만들 때는 "어떤 데이터를 복제할까"보다 "어떤 질문에 답할까"를 먼저 정해야 합니다.

## 화면의 질문을 문장으로 적는다

좋은 읽기 모델은 특정 조회 요구에서 출발합니다. 예를 들어 관리자 화면이 다음 질문에 답해야 한다고 해봅니다.

```text
최근 30일 동안 결제 실패가 3회 이상인 고객을
담당자, 마지막 실패 사유, 현재 플랜과 함께 보여준다.
```

이 문장이 있으면 필요한 필드, 정렬 기준, 필터, 갱신 지연 허용 범위가 보입니다. 반대로 "고객 데이터를 빠르게 조회한다"는 요구만 있으면 읽기 모델은 쓰기 테이블의 애매한 복사본이 됩니다.

## 정규화보다 조회 경로를 우선한다

읽기 모델은 중복을 허용합니다. 담당자 이름, 플랜명, 마지막 이벤트 요약을 한 문서에 넣을 수 있습니다. 중요한 것은 조회 시점에 여러 서비스를 다시 조합하지 않는 것입니다.

```json
{
  "customerId": "cus_123",
  "ownerName": "Jina",
  "planName": "Pro",
  "failedPaymentCount30d": 4,
  "lastFailureReason": "card_declined"
}
```

중복은 비용이지만, 읽기 모델에서는 의도된 비용일 수 있습니다. 대신 어떤 이벤트가 어떤 필드를 갱신하는지 명확해야 합니다.

## 신선도 요구사항을 숫자로 정한다

읽기 모델은 대개 비동기로 갱신됩니다. 따라서 "최신이어야 한다"는 표현은 부족합니다. 1초 이내인지, 1분 이내인지, 하루 한 번이면 되는지 정해야 합니다.

신선도에 따라 설계가 달라집니다.

- 1초 이내: 동기 갱신 또는 강한 모니터링 필요
- 수십 초: 이벤트 스트림과 재처리 가능성이 중요
- 수분 이상: 배치 집계도 가능
- 하루 단위: 비용과 단순성이 더 중요

모든 읽기 모델을 실시간으로 만들면 운영 비용이 커집니다. 사용자가 실제로 필요로 하는 최신성을 기준으로 정해야 합니다.

## 재빌드 경로를 만든다

읽기 모델은 언젠가 틀어집니다. 이벤트 처리 버그, 누락된 메시지, 스키마 변경, 수동 데이터 수정이 원인이 될 수 있습니다. 그래서 재빌드 경로가 필요합니다.

좋은 재빌드 작업은 다음 속성을 가집니다.

- 특정 기간이나 특정 고객만 다시 만들 수 있다.
- 실행 중에도 기존 읽기 모델을 계속 제공할 수 있다.
- 진행률과 실패 원인을 기록한다.
- 새 모델과 기존 모델을 비교할 수 있다.
- 완료 후 안전하게 전환할 수 있다.

재빌드를 고려하지 않은 읽기 모델은 장애가 났을 때 손으로 고쳐야 하는 캐시가 됩니다.

## 체크리스트

- 읽기 모델이 답할 질문을 문장으로 쓴다.
- 조회 시점의 조인을 줄이기 위해 필요한 중복을 허용한다.
- 데이터 신선도 목표를 숫자로 정한다.
- 어떤 이벤트가 어떤 필드를 갱신하는지 문서화한다.
- 부분 재빌드와 전체 재빌드 경로를 준비한다.

읽기 모델은 쓰기 모델의 그림자가 아니라 별도의 사용자 경험을 지탱하는 모델입니다. 질문, 신선도, 재빌드 가능성을 먼저 정하면 나중에 성능과 일관성 문제를 훨씬 덜 겪습니다.
