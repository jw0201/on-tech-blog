AI에게 "이 코드 리뷰해줘"라고 말하면 대체로 긴 의견이 나옵니다. 하지만 팀에 필요한 것은 긴 의견이 아니라 놓치기 쉬운 위험을 반복해서 확인하는 것입니다. AI 코드 리뷰 프롬프트는 개인의 질문이 아니라 팀의 리뷰 규칙으로 다듬을수록 가치가 커집니다.

## 리뷰 목적을 좁힌다

한 번의 프롬프트에 모든 것을 맡기면 결과가 흐려집니다. 스타일, 보안, 테스트, 성능, 호환성은 서로 다른 관점입니다. PR마다 필요한 관점을 선택하거나, 기본 리뷰와 심화 리뷰를 나누는 편이 좋습니다.

```text
이 변경을 운영 리스크 관점에서 리뷰해.
특히 다음만 확인해:
- 기존 API 응답 호환성
- 권한 검사의 누락
- 실패 시 재시도 가능성
- 로그에 민감 정보가 남는지
```

AI에게 역할을 주는 것보다 확인할 증거를 알려주는 것이 더 중요합니다. "시니어처럼 봐줘"보다 "호환성이 깨지는 지점을 찾아줘"가 낫습니다.

## 코드베이스 규칙을 포함한다

AI는 일반론에 강하지만 로컬 규칙에는 약합니다. 팀이 쓰는 에러 포맷, 테스트 네이밍, 로깅 금지 항목, 의존성 추가 기준을 프롬프트에 넣어야 합니다.

예를 들어 다음 규칙은 리뷰 품질을 크게 높입니다.

- 새 public API는 기존 응답 필드를 삭제하지 않는다.
- 인증 실패는 `401`, 권한 부족은 `403`으로 구분한다.
- 로그에는 토큰, 이메일 전체, 결제 식별자를 남기지 않는다.
- 테스트는 성공 경로보다 실패 경로를 최소 하나 포함한다.
- 새 패키지는 대체 가능한 기존 유틸이 없을 때만 허용한다.

이 규칙은 문서로 관리하고 프롬프트에서 참조하게 만드는 것이 좋습니다. 매번 사람이 기억해서 붙여 넣으면 오래가지 않습니다.

## 출력 형식을 리뷰 가능하게 만든다

AI 리뷰가 장문의 설명으로 나오면 사람이 다시 요약해야 합니다. 발견 사항은 파일, 위치, 위험, 수정 제안이 분리되어야 합니다.

```text
출력 형식:
- 발견 사항만 적는다.
- 각 항목은 심각도, 파일, 이유, 제안으로 나눈다.
- 확실하지 않은 내용은 "확인 필요"로 표시한다.
- 문제가 없으면 "주요 이슈 없음"이라고 쓴다.
```

이 형식은 자동화에도 유리합니다. PR 코멘트로 옮기거나, 사람이 확인할 체크리스트로 쓰기 쉽습니다.

## AI 리뷰를 승인 근거로 쓰지 않는다

AI가 문제를 찾지 못했다는 사실은 안전하다는 증거가 아닙니다. AI 리뷰는 사람이 놓친 질문을 늘리는 도구이지 승인 권한자가 아닙니다. 특히 보안, 결제, 데이터 삭제, 권한 변경은 사람이 최종 판단해야 합니다.

유용한 운영 방식은 다음과 같습니다.

- 작은 PR에는 기본 체크만 돌린다.
- 위험한 파일 변경에는 보안 프롬프트를 추가한다.
- 데이터 마이그레이션에는 롤백과 백필 체크를 추가한다.
- AI가 낸 의견 중 실제 버그였던 항목을 프롬프트에 반영한다.

프롬프트도 코드처럼 개선 대상입니다. 틀린 지적이 반복되면 제거하고, 놓친 장애가 생기면 질문을 추가합니다.

## 체크리스트

- 리뷰 목적을 한 번에 하나씩 좁힌다.
- 팀의 로컬 규칙을 프롬프트에 포함한다.
- 출력 형식을 파일, 위험, 제안 중심으로 고정한다.
- 불확실한 지적은 확인 필요로 표시하게 한다.
- AI 리뷰 결과를 승인 근거로 쓰지 않는다.

AI 코드 리뷰의 장점은 지치지 않고 같은 질문을 반복한다는 점입니다. 그 반복을 팀의 규칙과 연결하면, 리뷰는 더 짧아지고 중요한 논의에 시간을 쓸 수 있습니다.
