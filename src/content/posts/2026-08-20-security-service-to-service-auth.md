서비스가 많아지면 내부 호출도 외부 API만큼 중요해집니다. 주문 서비스가 결제 서비스를 부르고, 알림 서비스가 사용자 서비스를 조회하고, 배치 작업이 관리자 API를 호출합니다. 이때 "내부망에서 온 요청이니까 믿는다"는 방식은 오래 버티기 어렵습니다.

내부망은 보안 경계가 아닙니다. 잘못된 배포, SSRF, 노출된 토큰, 침해된 워커 하나가 내부 API로 이어질 수 있습니다. 서비스 간 인증은 네트워크 위치가 아니라 호출 주체의 정체성과 권한을 기준으로 설계해야 합니다.

## 서비스 정체성을 명확히 한다

첫 단계는 호출자가 누구인지 아는 것입니다. 단순 공유 secret 하나를 모든 서비스가 쓰면 요청 출처를 구분할 수 없습니다. 토큰이 유출되어도 어떤 서비스에서 나갔는지 알기 어렵습니다.

서비스마다 별도 정체성을 가져야 합니다.

- `order-api`
- `payment-worker`
- `notification-scheduler`
- `admin-bff`

정체성은 인증서, workload identity, 서명된 JWT, mTLS 같은 방식으로 표현할 수 있습니다. 선택지는 인프라에 따라 다르지만 목표는 같습니다. 요청을 받은 서비스가 "이 호출자는 어떤 서비스인가"를 검증할 수 있어야 합니다.

## 권한 범위를 작게 나눈다

인증만으로는 부족합니다. `payment-worker`가 결제 승인 API를 호출할 수 있다고 해서 환불 API나 정산 API까지 호출할 수 있어야 하는 것은 아닙니다.

서비스 토큰에는 scope나 audience를 둡니다.

- `payments:authorize`
- `payments:refund`
- `users:read-basic`
- `notifications:send`

또한 토큰의 audience를 특정 서비스로 제한하면 토큰 재사용 위험을 줄일 수 있습니다. 사용자 서비스용 토큰이 결제 서비스에서 받아들여지면 안 됩니다.

## 사람 권한과 서비스 권한을 섞지 않는다

관리자 화면에서 버튼을 누르면 백엔드 서비스가 내부 API를 호출합니다. 이때 호출은 사람의 권한과 서비스의 권한을 함께 고려해야 합니다.

서비스 토큰만 보고 허용하면 사용자의 실제 권한을 건너뛰게 됩니다. 반대로 사용자 토큰만 내부 서비스에 그대로 넘기면 권한 모델과 개인정보 노출 범위가 복잡해집니다.

실무에서는 두 정보를 분리해 전달하는 방식이 안전합니다.

- 서비스 인증: 이 요청을 전달하는 백엔드가 신뢰 가능한 서비스인지 확인
- 사용자 컨텍스트: 어떤 사용자의 어떤 행동 때문에 호출됐는지 확인

민감한 작업은 두 조건을 모두 통과해야 합니다.

## 감사 로그에는 호출 체인을 남긴다

서비스 간 호출은 장애와 보안 조사의 핵심 단서입니다. 감사 로그에는 단순히 "환불됨"만 남기지 말고 누가, 어떤 서비스 경로로, 어떤 요청 ID에서 작업했는지 남겨야 합니다.

유용한 필드는 다음과 같습니다.

- 호출 서비스 ID
- 사용자 ID 또는 시스템 작업 ID
- 요청 ID와 trace ID
- 수행한 action
- 대상 리소스
- 허용 또는 거부 결과
- 사용된 scope

감사 로그에는 토큰 원문이나 민감한 페이로드를 남기면 안 됩니다. 필요한 것은 재구성 가능한 맥락이지 비밀값이 아닙니다.

## 토큰 수명과 회전을 운영한다

서비스 토큰은 한 번 만들고 잊기 쉽습니다. 하지만 오래 사는 토큰은 유출 시 피해가 큽니다. 가능하면 짧은 수명의 토큰을 자동 발급하고, 장기 secret은 secret manager와 회전 정책으로 관리해야 합니다.

토큰 회전은 문서가 아니라 실제 훈련이 필요합니다. 새 키를 추가하고, 양쪽 검증을 열어두고, 기존 키 사용률이 0이 되는지 확인하고, 오래된 키를 제거하는 순서를 반복해봐야 합니다.

서비스 간 인증은 내부 시스템을 불편하게 만들기 위한 장치가 아닙니다. 장애가 났을 때 원인을 찾고, 침해가 생겼을 때 확산을 막고, 권한이 필요한 만큼만 쓰이게 하는 운영 기반입니다. 내부망을 믿는 대신 서비스 정체성과 권한 범위를 검증해야 합니다.
