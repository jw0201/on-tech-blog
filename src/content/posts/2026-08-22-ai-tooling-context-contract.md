AI 코딩 도구는 코드를 빠르게 바꿀 수 있지만, 컨텍스트가 흐리면 빠르게 엉뚱한 방향으로 갑니다. "이 버그 고쳐줘"만으로는 충분하지 않습니다. 어떤 파일을 봐야 하는지, 어떤 동작은 유지해야 하는지, 어떤 테스트를 통과해야 하는지 알려주지 않으면 도구는 빈칸을 추측으로 채웁니다.

팀에서 반복적으로 AI 도구를 쓴다면 프롬프트보다 컨텍스트 계약이 중요합니다. 계약은 매번 붙여 넣는 긴 설명이 아니라, 작업을 시작하기 전에 합의해야 하는 작은 체크리스트입니다.

## 목표를 동작으로 쓴다

좋지 않은 목표는 구현 방법이나 감정으로 적힙니다.

- 코드 정리
- 성능 개선
- 로그인 버그 수정
- 타입 예쁘게 만들기

좋은 목표는 관찰 가능한 동작으로 적습니다.

- 만료된 세션으로 API를 호출하면 로그인 화면으로 이동한다
- 검색어 입력 후 300ms 안에 요청이 한 번만 나간다
- 권한 없는 사용자는 설정 저장 버튼을 볼 수 없다
- CSV 다운로드가 5만 행에서도 타임아웃 없이 작업 큐로 넘어간다

AI 도구는 이 차이를 크게 탑니다. 목표가 동작이면 테스트와 검증 방향을 잡기 쉽고, 목표가 추상적이면 리팩터링 범위가 불필요하게 커집니다.

## 작업 경계를 명시한다

컨텍스트 계약에는 하지 말아야 할 일도 들어가야 합니다. 예를 들어 버그 수정 작업에서 디자인 시스템 전체를 바꾸거나, 테스트 도구를 교체하거나, 의존성을 추가하는 것은 대부분 과한 변경입니다.

경계는 짧아도 됩니다.

- 공개 API 응답 형식은 바꾸지 않는다
- 데이터베이스 마이그레이션은 추가하지 않는다
- UI 문구는 기존 톤을 유지한다
- 새 라이브러리는 쓰지 않는다
- 실패한 테스트를 삭제하지 않는다

이런 제한은 도구를 약하게 만드는 것이 아니라 선택지를 줄여 정확도를 높입니다.

## 근거 파일을 지정한다

AI 도구가 저장소 전체를 훑을 수 있어도, 어떤 파일이 기준인지 알려주는 편이 좋습니다.

- 재현 테스트
- 관련 라우트
- 도메인 모델
- 기존 유사 구현
- 문서화된 정책
- 최근 장애 리포트

특히 "기존 유사 구현"은 효과가 큽니다. 팀마다 에러 처리, 로깅, 상태 관리, 테스트 스타일이 다르기 때문에 좋은 예시 파일 하나가 긴 설명보다 낫습니다.

## 검증 명령을 함께 넘긴다

작업의 완료 기준은 테스트 명령까지 포함해야 합니다.

```bash
npm run test -- auth-session
npm run lint
npm run build
```

검증 명령이 없으면 도구는 정적 추론으로 끝내기 쉽습니다. 반대로 명령이 명시되어 있으면 실패를 보고 다시 수정하는 루프를 만들 수 있습니다.

테스트가 느린 저장소라면 최소 검증과 전체 검증을 나눕니다.

- 변경 중 반복 실행할 빠른 테스트
- 커밋 전 한 번 실행할 전체 테스트
- 수동 확인이 필요한 화면 또는 시나리오

## 결과물 형식을 정한다

AI 도구의 마지막 응답도 계약에 포함할 수 있습니다. "무엇을 바꿨는지, 어떤 검증을 했는지, 남은 위험은 무엇인지"를 요구하면 코드 리뷰가 쉬워집니다.

예시는 간단합니다.

- 변경 요약
- 테스트 결과
- 의도적으로 건드리지 않은 범위
- 리뷰어가 집중해서 볼 파일

AI 코딩 도구의 품질은 모델 성능만으로 결정되지 않습니다. 좋은 작업 계약을 주면 도구는 팀의 맥락 안에서 움직이고, 나쁜 계약을 주면 저장소를 상대로 추측 게임을 합니다. 반복 작업일수록 프롬프트를 길게 쓰기보다 컨텍스트 계약을 작고 선명하게 만드는 편이 효과적입니다.
