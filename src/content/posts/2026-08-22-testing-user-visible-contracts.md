테스트가 많아도 리팩터링할 때마다 깨진다면 테스트가 구현 세부사항에 너무 가까이 붙어 있을 가능성이 큽니다. 반대로 테스트가 적어도 핵심 사용자 계약을 잘 잡고 있으면 변경에 대한 자신감이 생깁니다.

테스트 우선순위를 정할 때는 "사용자나 다른 시스템이 실제로 의존하는가"를 기준으로 삼는 편이 좋습니다. 이것을 사용자에게 보이는 계약이라고 부를 수 있습니다.

## 계약은 UI에만 있는 것이 아니다

사용자에게 보이는 계약은 브라우저 화면만 뜻하지 않습니다.

- 버튼을 눌렀을 때 일어나는 변화
- URL 쿼리 파라미터의 의미
- API 응답 필드와 에러 코드
- 이메일 제목과 핵심 링크
- 웹훅 payload 형식
- CSV 내보내기 컬럼 순서
- 권한 없는 사용자가 볼 수 없는 동작

이런 계약은 코드 구조가 바뀌어도 유지되어야 합니다. 그래서 테스트 가치가 높습니다.

## 구현 세부사항 테스트를 줄인다

컴포넌트 내부 state 이름, private 함수 호출 횟수, 특정 라이브러리 mock 구조를 테스트하면 리팩터링 비용이 커집니다. 사용자는 `isModalOpen`이 true인지 관심이 없습니다. 사용자는 모달이 열리고 필요한 정보가 보이는지 관심이 있습니다.

백엔드도 마찬가지입니다. 서비스 메서드가 repository를 몇 번 호출했는지보다, 같은 입력에서 어떤 응답과 부작용이 생기는지가 더 중요합니다.

물론 단위 테스트가 필요 없는 것은 아닙니다. 계산 규칙, 파서, 권한 판정처럼 순수 로직이 복잡한 곳은 단위 테스트가 가장 빠르고 정확합니다. 다만 사용자 계약과 무관한 내부 배선을 과하게 고정하지 않는 것이 중요합니다.

## 깨지면 사용자에게 보이는 것부터 고른다

테스트를 추가해야 할 때 다음 질문을 던집니다.

- 이 동작이 깨지면 사용자가 바로 알아차리는가
- 다른 서비스나 클라이언트가 이 형식에 의존하는가
- 과거에 장애나 회귀가 있었는가
- 코드 리뷰만으로 놓치기 쉬운가
- 테스트가 실패하면 원인을 빠르게 좁힐 수 있는가

이 질문에 많이 해당할수록 좋은 테스트 후보입니다.

예를 들어 결제 페이지에서는 버튼 스타일보다 결제 생성 요청, 중복 클릭 방지, 실패 메시지, 재시도 가능 여부가 우선입니다. 관리자 목록에서는 정렬 아이콘보다 필터 조건이 URL에 유지되는지가 더 중요할 수 있습니다.

## 테스트 이름에 계약을 드러낸다

테스트 이름은 구현 설명보다 계약 설명이 좋습니다.

```text
권한 없는 사용자는 멤버 초대 버튼을 볼 수 없다
만료된 쿠폰 코드는 409와 만료 사유를 반환한다
검색어를 지우면 page 쿼리도 함께 초기화된다
```

이름만 읽어도 제품 규칙이 보이면 테스트는 문서 역할도 합니다. 반대로 `renders correctly`, `calls handler`, `updates state` 같은 이름은 실패했을 때 중요도를 판단하기 어렵습니다.

## 계약 테스트와 세부 테스트를 섞지 않는다

한 테스트에서 UI 렌더링, API mock, 내부 함수 호출, CSS class까지 모두 검증하면 실패 원인이 흐려집니다. 계약 테스트는 계약에 집중해야 합니다.

예를 들어 "검색어 입력 후 결과가 갱신된다"는 테스트는 사용자가 볼 수 있는 결과와 요청 파라미터 정도만 확인하면 됩니다. 내부 debounce 구현이나 state 변수 이름은 고정하지 않아도 됩니다.

좋은 테스트 전략은 많은 테스트를 무작정 쌓는 것이 아닙니다. 바뀌어도 되는 코드와 바뀌면 안 되는 계약을 구분하는 일입니다. 사용자에게 보이는 계약부터 테스트하면, 테스트는 개발 속도를 막는 짐이 아니라 변경을 지탱하는 기준이 됩니다.
