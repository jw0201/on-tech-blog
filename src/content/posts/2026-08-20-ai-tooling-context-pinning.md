AI 코딩 도구를 쓰다 보면 모델 성능보다 컨텍스트 품질이 결과를 더 크게 좌우할 때가 많습니다. 같은 요청이라도 어떤 파일을 먼저 읽었는지, 어떤 규칙을 기억하고 있는지, 이전 실패 사례를 알고 있는지에 따라 결과가 달라집니다.

컨텍스트를 많이 넣는 것이 답은 아닙니다. 너무 많은 정보를 넣으면 핵심 규칙이 묻히고, 오래된 설명이 현재 코드보다 우선되는 문제가 생깁니다. 필요한 것은 컨텍스트 핀ning입니다. 자주 필요한 정보를 작고 안정적인 형태로 고정하는 방식입니다.

## 고정할 정보와 매번 읽을 정보를 구분한다

모든 문서가 고정 컨텍스트가 되어야 하는 것은 아닙니다. 자주 바뀌는 구현 파일은 매번 읽는 편이 낫고, 거의 바뀌지 않는 작업 원칙은 고정하는 편이 좋습니다.

고정하기 좋은 정보는 다음과 같습니다.

- 테스트 명령과 실행 조건
- 코드 스타일에서 자주 어긋나는 규칙
- 보안상 절대 하면 안 되는 일
- 배포나 마이그레이션 순서
- 리뷰에서 반복적으로 지적된 실수

반대로 상세 구현 설명, 오래된 설계 문서, 임시 디버깅 메모는 고정 컨텍스트에 넣지 않는 편이 좋습니다. 실제 코드와 어긋나는 순간 품질을 떨어뜨립니다.

## 규칙은 짧고 검증 가능해야 한다

AI 도구에 주는 규칙은 사람이 읽는 문서보다 더 작아야 합니다. "좋은 코드를 작성한다" 같은 문장은 행동을 바꾸지 못합니다. 대신 실행 가능한 제약으로 적어야 합니다.

좋은 예시는 다음과 같습니다.

- 파일 검색은 `rg`를 먼저 사용한다.
- 마이그레이션 파일은 생성 후 되돌림 절차를 함께 작성한다.
- 결제 관련 변경은 성공 테스트와 실패 테스트를 모두 추가한다.
- 기존 staged 변경은 사용자 작업으로 보고 되돌리지 않는다.

이런 규칙은 작업 중 바로 확인할 수 있습니다. 반대로 추상적인 원칙만 있으면 모델이 자기 방식대로 해석합니다.

## 실패 사례를 압축해서 남긴다

팀에서 AI 도구를 오래 쓰면 반복 실패 패턴이 보입니다. 예를 들어 생성된 코드가 테스트 fixture를 잘못 공유하거나, 권한 체크를 UI에만 넣거나, 날짜를 로컬 타임존 없이 처리하는 식입니다.

이런 사례는 길게 기록하지 말고 짧은 금지 규칙과 확인 방법으로 남깁니다.

- "권한은 라우터와 서비스 계층에서 검증한다. UI 체크만 추가하지 않는다."
- "날짜 비교는 서비스 타임존을 명시한다. 브라우저 기본 타임존에 의존하지 않는다."
- "fixture는 테스트마다 새로 만든다. 전역 fixture mutation을 피한다."

실패 사례는 감정적인 회고보다 재발 방지 체크리스트가 되어야 쓸모 있습니다.

## 컨텍스트 파일에도 소유자가 필요하다

컨텍스트 파일은 방치되면 쉽게 쓰레기장이 됩니다. 누구나 규칙을 추가하지만 아무도 지우지 않으면 AI 도구는 서로 충돌하는 지시를 받습니다.

그래서 고정 컨텍스트에는 소유자와 정리 주기가 필요합니다. 한 달에 한 번이라도 다음 질문으로 다듬는 것이 좋습니다.

- 아직 유효한 규칙인가?
- 실제 실패를 줄였는가?
- 더 짧게 쓸 수 있는가?
- 코드나 자동화로 대체할 수 있는가?

규칙이 자동화될 수 있다면 lint, test, CI gate로 옮기는 편이 더 낫습니다. AI에게 매번 기억시키는 것보다 도구가 강제하는 쪽이 안정적입니다.

## 작업 시작 루틴을 만든다

컨텍스트 핀ning은 파일을 만드는 것으로 끝나지 않습니다. AI 도구가 작업을 시작할 때 어떤 순서로 읽고 확인할지 루틴이 있어야 합니다.

예를 들어 다음 흐름을 둘 수 있습니다.

- 고정 작업 규칙을 먼저 확인한다.
- 관련 코드와 테스트를 검색한다.
- 변경 전 git 상태를 확인한다.
- 구현 후 지정된 테스트를 실행한다.
- 사용자 변경과 자신의 변경을 구분해 보고한다.

이 루틴은 모델이 바뀌어도 팀의 작업 방식이 유지되게 해줍니다.

AI 코딩 도구의 품질은 모델만으로 결정되지 않습니다. 잘 고른 컨텍스트, 짧은 규칙, 실제 실패에서 나온 체크리스트가 함께 있어야 안정적인 동료처럼 일합니다. 중요한 정보를 적게, 선명하게, 검증 가능하게 고정하는 것이 핵심입니다.
