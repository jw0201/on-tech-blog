블루그린 배포는 애플리케이션 롤백을 쉽게 만듭니다. 새 버전을 green 환경에 띄우고 트래픽을 넘긴 뒤 문제가 생기면 blue로 되돌리면 됩니다. 하지만 데이터베이스는 보통 하나입니다. 애플리케이션은 두 버전이 공존해도 데이터는 공유됩니다.

이 때문에 블루그린 배포에서 가장 위험한 부분은 서버 전환이 아니라 스키마와 데이터 변경입니다. 새 코드만 기준으로 마이그레이션을 작성하면 롤백 순간 이전 코드가 깨질 수 있습니다.

## 양쪽 버전이 읽을 수 있는 스키마를 만든다

배포 중에는 이전 버전과 새 버전이 동시에 데이터베이스를 읽고 쓸 수 있습니다. 따라서 마이그레이션은 양쪽 코드와 호환되어야 합니다.

안전한 순서는 대체로 다음과 같습니다.

- 새 nullable 컬럼이나 새 테이블을 먼저 추가한다.
- 이전 코드는 그대로 동작하게 둔다.
- 새 코드는 새 컬럼을 쓰되 기존 필드도 읽을 수 있게 한다.
- 백필을 별도 작업으로 실행한다.
- 모든 인스턴스가 새 코드로 전환된 뒤 오래된 컬럼을 제거한다.

컬럼 이름 변경이나 타입 변경을 한 번에 처리하면 위험합니다. 이름을 바꾸는 대신 새 컬럼을 추가하고, 읽기 경로를 양쪽에 열어두고, 충분히 관측한 뒤 제거하는 편이 안전합니다.

## 쓰기 경로를 먼저 안정화한다

읽기 호환성보다 더 까다로운 것은 쓰기입니다. 이전 버전은 예전 컬럼에 쓰고, 새 버전은 새 컬럼에 쓰면 데이터가 갈라질 수 있습니다.

전환 기간에는 dual write나 write adapter를 고려할 수 있습니다. 다만 dual write는 실패 지점이 늘어나므로 관측과 재시도 정책이 필요합니다. 두 쓰기 중 하나만 성공했을 때 어떤 상태가 정답인지 명확해야 합니다.

작게 시작하려면 새 코드가 기존 컬럼을 계속 쓰면서 새 컬럼을 부가적으로 채우게 만들 수 있습니다. 이후 백필과 검증을 통해 새 컬럼이 충분히 안정적이라고 판단되면 읽기 경로를 옮깁니다.

## 롤백 가능한 변경과 되돌릴 수 없는 변경을 구분한다

모든 변경이 같은 수준으로 롤백 가능한 것은 아닙니다. 애플리케이션 코드는 되돌릴 수 있어도 데이터 삭제, 컬럼 제거, 의미 변경은 쉽게 되돌릴 수 없습니다.

배포 계획에는 변경 유형을 표시하는 것이 좋습니다.

- 즉시 롤백 가능: 새 코드만 배포한 경우
- 조건부 롤백 가능: 새 컬럼에 쓰기 시작했지만 기존 경로도 유지한 경우
- 롤백 어려움: 데이터 변환이 완료되고 이전 의미를 잃은 경우

롤백 어려운 단계는 자동 배포 흐름에 섞지 말고 별도 승인과 백업 확인을 두는 편이 안전합니다.

## 백필은 배포와 분리한다

대량 백필을 애플리케이션 배포에 묶으면 장애 원인을 분리하기 어렵습니다. 새 코드 문제인지, 백필 부하인지, 인덱스 생성 문제인지 한꺼번에 터질 수 있습니다.

백필은 배포 후 관측 가능한 작업으로 분리합니다. 배치 크기, sleep 간격, 중단 조건, 재시작 위치를 명시해야 합니다. 진행률과 오류율을 볼 수 있는 지표도 필요합니다.

좋은 백필은 언제든 멈추고 다시 시작할 수 있습니다. 전체 트랜잭션 하나로 오래 잠그는 방식은 피해야 합니다.

## 전환 완료 조건을 숫자로 둔다

"문제 없어 보이면 이전 컬럼 제거"는 위험합니다. 전환 완료 조건은 숫자로 정합니다.

- 24시간 동안 이전 코드 인스턴스가 0개
- 새 컬럼 null 비율 0.01% 미만
- 읽기 경로의 fallback 사용률 0
- dual write mismatch 0건
- 롤백 시나리오 리허설 완료

이 조건이 있어야 제거 작업을 자신 있게 할 수 있습니다.

블루그린 배포는 서버를 빠르게 되돌리는 기술이지만, 데이터베이스 변경까지 자동으로 안전하게 만들어주지는 않습니다. 스키마 호환성, 쓰기 경로, 백필, 롤백 가능성을 별도로 설계해야 진짜로 안심하고 전환할 수 있습니다.
