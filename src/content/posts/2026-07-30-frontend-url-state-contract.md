목록 화면에서 필터를 바꾸고, 정렬을 적용하고, 페이지를 이동했는데 새로고침하면 상태가 사라지는 경우가 있습니다. 사용자는 같은 화면을 동료에게 공유할 수 없고, QA는 버그 재현 링크를 만들기 어렵습니다.

URL 상태는 단순한 구현 디테일이 아니라 제품 계약입니다. 링크 하나로 같은 화면을 다시 만들 수 있어야 합니다.

## URL에 담을 상태를 고른다

모든 UI 상태를 URL에 넣을 필요는 없습니다. 공유와 복원이 중요한 상태만 남기는 편이 유지보수하기 쉽습니다.

URL에 적합한 상태는 다음과 같습니다.

- 검색어
- 필터 값
- 정렬 기준
- 페이지 번호 또는 cursor
- 선택된 탭
- 기간 범위

반대로 모달 열림, 드롭다운 펼침, 임시 입력값처럼 순간적인 상태는 보통 URL에 넣지 않습니다. URL이 너무 많은 세부 상태를 갖게 되면 뒤로 가기 동작이 예측하기 어려워집니다.

## 기본값은 생략한다

`?page=1&sort=createdAt_desc&status=all`처럼 기본값을 모두 넣으면 URL이 길어지고 변경 비용이 커집니다. 기본값은 코드에서 선언하고 URL에는 사용자가 바꾼 값만 담는 편이 좋습니다.

예를 들어 `status=all`이 기본이면 URL에서 생략합니다.

```text
/issues?q=timeout
/issues?q=timeout&status=open
```

이렇게 하면 기본 정책을 바꿀 때도 기존 링크를 더 쉽게 해석할 수 있습니다.

## 파싱 실패를 제품적으로 처리한다

URL은 외부 입력입니다. 사용자가 직접 수정할 수도 있고, 오래된 링크가 남아 있을 수도 있습니다. 따라서 query string을 신뢰하면 안 됩니다.

프론트엔드에서 처리할 기준을 정해둡니다.

- 알 수 없는 필터 값은 무시한다.
- 숫자 범위를 벗어난 page는 1로 되돌린다.
- 지원 중단된 정렬 값은 새 기본값으로 매핑한다.
- 파싱할 수 없는 날짜는 기간 필터를 비운다.

실패를 에러 화면으로 보내기보다 가능한 범위에서 복원하는 편이 목록 화면에는 더 자연스럽습니다.

## 서버 API와 이름을 맞춘다

프론트엔드 URL 파라미터와 백엔드 API 파라미터가 서로 다르면 변환 코드가 늘어납니다. 화면의 표현과 API 계약이 완전히 같을 필요는 없지만, 이름과 enum은 가능한 한 맞추는 것이 좋습니다.

예를 들어 URL은 `status=open`, API는 `state=OPENED`라면 매핑 계층이 필요합니다. 이 매핑이 많아지면 필터가 추가될 때마다 누락이 생깁니다.

## 테스트는 링크 복원을 본다

URL 상태의 핵심 테스트는 "사용자가 만든 링크가 같은 화면을 다시 만드는가"입니다.

테스트에서는 다음 흐름을 확인합니다.

1. 필터와 정렬을 선택한다.
2. URL이 기대한 query string으로 바뀌는지 본다.
3. 해당 URL로 새로 진입한다.
4. UI 상태와 요청 파라미터가 동일한지 확인한다.

URL 상태를 제대로 다루면 목록 화면은 훨씬 덜 휘발적입니다. 공유, 재현, 북마크, 뒤로 가기가 모두 제품 경험의 일부가 됩니다.
