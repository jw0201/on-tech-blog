테스트가 가끔 느려지고 가끔 실패한다면 외부 네트워크 의존성을 의심해볼 만합니다. 로컬에서는 통과하지만 CI에서 실패하거나, 특정 시간대에만 깨지는 테스트는 실제 서비스, CDN, 인증 서버, 패키지 레지스트리를 몰래 호출하고 있을 수 있습니다.

Hermetic 테스트는 실행 환경 밖의 상태에 의존하지 않는 테스트입니다. 네트워크를 닫는 것은 그중 가장 효과적인 출발점입니다.

## 기본값은 차단이어야 한다

테스트에서 네트워크를 허용하는 방식은 편하지만 위험합니다. 새 코드가 외부 API를 호출해도 아무도 모른 채 통과할 수 있기 때문입니다. 반대로 기본값을 차단하면 의존성이 생기는 순간 테스트가 즉시 알려줍니다.

Node.js 환경에서는 HTTP 클라이언트를 mock 레이어로 감싸거나, 테스트 러너 시작 시 `fetch`, `http`, `https` 호출을 막을 수 있습니다. 브라우저 테스트라면 Playwright의 route 기능으로 예상하지 않은 요청을 실패 처리할 수 있습니다.

핵심은 허용 목록입니다.

- 로컬 테스트 서버
- 정적 fixture 파일
- 의도적으로 띄운 mock 서버
- 테스트 러너가 필요로 하는 내부 엔드포인트

이 외 요청은 실패해야 합니다.

## Mock은 프로토콜에 가깝게 둔다

네트워크를 닫으면 mock이 필요합니다. 이때 내부 함수 mock만 남발하면 실제 API 계약과 멀어집니다. 가능하면 HTTP 경계에서 요청과 응답을 흉내 내는 편이 좋습니다.

좋은 mock은 다음을 검증합니다.

- 요청 메서드와 경로
- 필수 헤더
- 요청 본문 구조
- 응답 상태 코드
- 오류 응답 형태

이렇게 하면 외부 서비스와의 계약을 테스트하면서도 실제 네트워크는 사용하지 않을 수 있습니다.

## 예외는 파일로 남긴다

모든 테스트에서 네트워크를 영원히 금지할 수는 없습니다. 통합 테스트나 계약 갱신 테스트처럼 실제 서비스를 호출해야 하는 경우가 있습니다. 다만 예외는 암묵적이면 안 됩니다.

예외 목록에는 다음 정보를 남깁니다.

- 호출 대상 도메인
- 필요한 테스트 이름
- 사용 이유
- 소유자
- 만료일 또는 재검토일

만료일이 없는 예외는 시간이 지나며 기본값이 됩니다. 테스트 안정성을 위해서는 예외도 부채처럼 관리해야 합니다.

## Fixture 갱신 경로를 만든다

외부 응답을 fixture로 고정하면 안정성은 좋아지지만 현실과 멀어질 수 있습니다. 그래서 fixture를 갱신하는 명령이 필요합니다. 이 명령은 일반 테스트와 분리되어야 하며, 네트워크 접근을 명시적으로 요구해야 합니다.

예를 들어 다음처럼 운영할 수 있습니다.

```bash
npm run test
npm run fixtures:refresh -- --service=billing
```

일반 테스트는 네트워크를 닫고, fixture 갱신 명령만 외부 호출을 허용합니다. 갱신된 fixture는 코드 리뷰에서 차이를 확인합니다.

## 실패 메시지는 친절해야 한다

네트워크 차단 테스트의 실패 메시지가 불친절하면 개발자는 차단 장치를 우회하고 싶어집니다. 실패 메시지에는 어떤 요청이 막혔고 어떻게 처리해야 하는지 나와야 합니다.

예시는 다음과 같습니다.

```text
Unexpected network request blocked: POST https://api.example.com/invoices
Use the billing mock server or add a documented exception.
```

테스트 경계는 개발자를 괴롭히기 위한 장치가 아니라 불안정한 의존성을 빨리 드러내는 장치입니다. 네트워크를 기본 차단으로 두면 CI는 더 예측 가능해지고, 테스트 실패는 실제 코드 변화에 가까워집니다.
