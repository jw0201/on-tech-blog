시크릿 유출은 대개 특별한 사고처럼 보이지만 원인은 평범합니다. 디버깅용 `.env` 파일을 커밋하거나, 테스트 토큰을 README에 붙여 넣거나, 로그 샘플에 실제 키가 섞입니다. 한 번 원격 저장소에 올라간 시크릿은 삭제 커밋만으로 안전해지지 않습니다. 그래서 시크릿 스캐닝은 배포 전 검사의 일부로 들어가야 합니다.

## 로컬과 CI를 함께 둔다

로컬 pre-commit 훅은 빠르게 알려준다는 장점이 있습니다. 하지만 모든 개발자가 훅을 설치한다고 보장할 수 없고, 우회도 쉽습니다. CI 검사는 느리지만 중앙에서 강제할 수 있습니다.

실무에서는 둘 다 필요합니다. 로컬 훅은 실수를 일찍 막고, CI는 최종 방어선 역할을 합니다. 특히 외부 기여자나 자동 생성 커밋이 있는 저장소라면 CI 검사는 선택이 아니라 기본값에 가깝습니다.

## 오탐을 관리할 구조가 필요하다

시크릿 스캐너를 켜면 오탐이 생깁니다. 예제용 문자열, 테스트 fixture, 해시 값이 토큰처럼 보일 수 있습니다. 오탐이 많으면 팀은 검사를 무시하기 시작합니다.

따라서 예외 처리 방식이 중요합니다. 좋은 예외는 세 가지를 남깁니다.

- 어떤 파일과 값이 예외인지
- 왜 실제 시크릿이 아닌지
- 누가 언제 승인했는지

단순히 검사 전체를 끄는 예외는 피해야 합니다. 가능하면 특정 줄, 특정 패턴, 테스트 디렉터리처럼 범위를 좁힙니다.

## 유출 발견 후 절차를 미리 정한다

스캐너가 실제 시크릿을 발견했을 때 가장 나쁜 반응은 "커밋을 지우면 되나?"를 그때부터 논의하는 것입니다. 유출 대응은 미리 정해져 있어야 합니다.

기본 절차는 단순합니다.

1. 해당 키를 즉시 폐기하거나 회전한다.
2. 키가 접근할 수 있었던 리소스를 확인한다.
3. 로그에서 사용 흔적을 찾는다.
4. 저장소 기록 정리는 보조 조치로 처리한다.
5. 같은 경로의 재발 방지 규칙을 추가한다.

중요한 순서는 폐기가 먼저라는 점입니다. Git 기록을 깨끗하게 만드는 일보다 실제 권한을 끊는 일이 더 급합니다.

## 테스트용 시크릿도 진짜처럼 다룬다

"개발용 키라 괜찮다"는 말은 위험합니다. 개발용 키가 실제 데이터에 접근하지 못하더라도, 공격자는 그 키를 발판으로 시스템 구조를 파악할 수 있습니다. 또 개발과 운영 경계가 흐린 작은 팀에서는 테스트 키가 생각보다 넓은 권한을 갖는 경우가 많습니다.

테스트에는 실제 토큰 모양을 흉내 낸 더미 값을 쓰고, 외부 서비스 연동 테스트가 필요하면 CI의 시크릿 저장소를 사용합니다. 문서에는 실제 키 대신 형식만 보여줍니다.

```text
PAYMENT_API_KEY=pay_test_xxxxxxxxxxxxx
```

이 값이 실제로 동작하지 않는다는 점이 중요합니다.

## 체크리스트

- 로컬 훅과 CI 검사를 함께 사용한다.
- 오탐 예외는 파일, 이유, 승인자를 남긴다.
- 실제 유출 시에는 Git 기록 정리보다 키 폐기를 먼저 한다.
- 테스트와 문서에는 동작하지 않는 더미 값을 쓴다.
- 스캐너 실패를 배포 차단 조건으로 둘지 명확히 정한다.

시크릿 스캐닝은 보안팀만의 도구가 아닙니다. 개발 흐름에 자연스럽게 붙어 있어야 실수를 초기에 잡습니다. 좋은 파이프라인은 사람을 의심하는 대신 실수가 멀리 가지 못하게 만듭니다.
