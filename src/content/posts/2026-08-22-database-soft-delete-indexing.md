소프트 삭제는 간단해 보입니다. 테이블에 `deleted_at` 컬럼을 추가하고 삭제 대신 시간을 기록하면 됩니다. 하지만 실제 운영에서는 조회 성능, 유니크 제약, 데이터 복구, 개인정보 보관 기간이 함께 얽힙니다.

소프트 삭제를 안전하게 쓰려면 "삭제된 행을 숨긴다"보다 조금 더 넓은 설계가 필요합니다.

## 모든 조회에 삭제 조건이 들어가야 한다

소프트 삭제 테이블의 기본 조회 조건은 보통 `deleted_at is null`입니다. 문제는 이 조건이 빠지기 쉽다는 점입니다. 특히 관리자 쿼리, 배치 작업, 통계 쿼리, 직접 작성한 SQL에서 실수가 생깁니다.

가능하면 ORM의 기본 scope나 repository 메서드에 삭제 조건을 넣고, 삭제된 행을 포함하는 조회는 이름으로 드러냅니다.

- `findActiveById`
- `findIncludingDeletedById`
- `listDeletedForRestore`

이름에 의도를 남기면 코드 리뷰에서 잘못된 조회를 잡기 쉽습니다.

## 인덱스는 active 행 기준으로 잡는다

삭제된 데이터가 계속 쌓이면 `deleted_at is null` 조건이 성능에 영향을 줍니다. 대부분의 일반 화면은 삭제되지 않은 행만 조회하므로 active 행을 기준으로 인덱스를 설계해야 합니다.

PostgreSQL에서는 partial index가 좋은 선택입니다.

```sql
create index users_active_email_idx
on users (email)
where deleted_at is null;
```

이렇게 하면 활성 사용자 조회가 삭제된 데이터 크기에 덜 영향을 받습니다. MySQL처럼 partial index가 제한적인 환경에서는 복합 인덱스에 `deleted_at`을 포함하거나 active 상태 컬럼을 별도로 둘 수 있습니다.

## 유니크 제약은 삭제 정책과 함께 정한다

소프트 삭제에서 가장 자주 만나는 문제가 유니크 제약입니다. 이메일이 유니크인 사용자 테이블에서 사용자를 삭제한 뒤 같은 이메일로 다시 가입할 수 있어야 할까요?

정답은 제품 정책입니다.

- 삭제 후 같은 값을 재사용할 수 있다
- 삭제된 계정도 같은 값을 영구 점유한다
- 일정 기간 후 재사용할 수 있다

정책에 따라 제약 조건도 달라집니다. 재사용을 허용한다면 active 행에만 유니크가 걸려야 합니다. 재사용을 막는다면 삭제된 행도 포함해 유니크를 유지합니다. 일정 기간 후 허용하려면 별도 정리 작업이나 보존 테이블이 필요합니다.

정책을 정하지 않은 채 `deleted_at`만 추가하면 가입, 복구, 중복 데이터 처리에서 충돌이 납니다.

## 복구 가능성을 테스트한다

소프트 삭제를 쓰는 이유 중 하나는 복구입니다. 그런데 실제로 복구해보면 연관 데이터가 이미 바뀌었거나, 유니크 값이 다른 행에 사용 중이거나, 외부 시스템 상태와 맞지 않을 수 있습니다.

복구가 제품 기능이라면 테스트 시나리오가 필요합니다.

- 삭제된 행을 다시 활성화할 수 있는가
- 연관된 자식 데이터도 함께 복구되는가
- 같은 유니크 값을 가진 새 행이 있을 때 어떻게 되는가
- 삭제 중 발생한 외부 작업을 되돌릴 수 있는가

복구가 필요 없다면 소프트 삭제가 정말 맞는지도 다시 봐야 합니다. 단순 감사 목적이면 변경 로그나 별도 archive 테이블이 더 나을 수 있습니다.

## 보관 기간과 하드 삭제를 분리한다

소프트 삭제는 영구 보관이 아닙니다. 개인정보나 비용이 큰 데이터는 일정 기간 후 하드 삭제해야 할 수 있습니다. 이 정책은 법무, 보안, 운영 요구사항과 연결됩니다.

좋은 설계는 삭제 상태를 단계로 나눕니다.

- active
- soft deleted
- pending purge
- purged

그리고 purge 작업은 별도 배치로 수행하며, 실행 로그와 실패 재시도 정책을 둡니다.

소프트 삭제는 편리하지만 공짜가 아닙니다. 조회 조건, 인덱스, 유니크 제약, 복구, 보관 기간까지 함께 설계해야 운영 중 예상치 못한 데이터 문제가 줄어듭니다.
