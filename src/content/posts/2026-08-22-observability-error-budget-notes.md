SLO와 에러 버짓은 도입할 때는 멋있지만, 숫자만 대시보드에 있으면 팀의 행동을 바꾸지 못합니다. 이번 달 예산을 얼마나 썼는지, 어떤 릴리스가 영향을 줬는지, 다음 주에 무엇을 조정할지 기록으로 남겨야 실제 운영 도구가 됩니다.

에러 버짓 노트는 복잡한 문서가 아니어도 됩니다. 매주 짧게 현재 상태와 결정만 남겨도 충분합니다.

## 숫자와 사건을 함께 적는다

에러 버짓은 비율만 보면 맥락이 부족합니다. 예산을 30% 썼다는 사실보다 중요한 것은 왜 썼는지입니다.

노트에는 다음 항목을 함께 둡니다.

- 대상 서비스와 SLO
- 현재 측정 기간
- 사용한 에러 버짓 비율
- 가장 큰 소모 원인
- 관련 배포 또는 장애
- 사용자 영향
- 다음 액션

예를 들어 "검색 API 가용성 SLO 99.9%, 이번 주 예산 45% 소모, 원인은 8월 20일 인덱스 변경 후 p95 지연 증가"처럼 쓰면 숫자가 바로 행동으로 연결됩니다.

## 릴리스 정책과 연결한다

에러 버짓이 빠르게 줄어들고 있다면 팀은 새로운 기능 배포보다 안정화에 집중해야 합니다. 이 원칙이 문서에만 있고 실제 릴리스 판단에 쓰이지 않으면 의미가 없습니다.

간단한 정책을 만들 수 있습니다.

- 예산 사용 50% 이하: 정상 배포
- 50~80%: 위험 변경은 점진 배포
- 80% 이상: 안정화 작업 우선, 대규모 변경 보류
- 예산 초과: 원인 분석과 재발 방지 전까지 기능 릴리스 제한

정책은 팀 문화에 맞게 조정해야 합니다. 중요한 것은 장애 이후에 감정으로 배포를 멈추는 것이 아니라, 미리 합의한 기준으로 속도를 조절하는 것입니다.

## 원인을 카테고리로 분류한다

에러 버짓 소모 원인을 계속 적다 보면 패턴이 보입니다.

- 배포 결함
- 외부 의존성 장애
- 용량 부족
- 데이터베이스 쿼리 성능
- 설정 실수
- 클라이언트 버그
- 관측 지표 오류

분류가 쌓이면 안정화 투자의 우선순위가 생깁니다. 장애마다 개별적으로 대응하는 대신 "최근 두 달 예산의 절반이 배포 결함에서 나왔으니 배포 스모크 테스트를 강화하자"처럼 말할 수 있습니다.

## 사용자 영향 언어로 번역한다

SLO 숫자는 엔지니어에게는 익숙하지만, 제품 팀이나 고객 지원 팀에는 추상적일 수 있습니다. 노트에는 사용자 영향도 같이 적어야 합니다.

- 로그인 실패 사용자가 약 320명 발생
- 관리자 CSV 다운로드가 평균 40초 지연
- 결제 생성 실패 7건, 모두 재시도 성공
- 알림 발송이 최대 18분 지연

이렇게 쓰면 안정성 논의가 기술 지표를 넘어 제품 우선순위로 이어집니다.

## 작은 회고를 반복한다

에러 버짓 노트의 목적은 책임 추궁이 아닙니다. 팀이 같은 실수를 덜 반복하도록 학습하는 것입니다. 매주 짧게라도 "이번 주에 배운 것"을 남기면 운영 지식이 쌓입니다.

좋은 액션은 구체적이어야 합니다.

- 느린 쿼리 알림 임계값을 2초에서 1초로 조정
- 결제 API 배포에 canary 10분 추가
- 외부 API timeout을 3초로 제한
- 장애 대시보드에 버전 라벨 추가

에러 버짓은 숫자만으로는 팀을 움직이지 못합니다. 노트로 맥락과 결정을 남길 때, 안정성은 대시보드가 아니라 운영 습관이 됩니다.
