스켈레톤 UI는 로딩을 덜 답답하게 보이게 만듭니다. 하지만 잘못 만들면 실제 콘텐츠보다 더 불안정한 화면이 됩니다. 로딩 중에는 높이가 달라지고, 데이터가 들어오면 카드가 밀리고, 실패하면 회색 박스만 남는 식입니다. 좋은 스켈레톤은 예쁜 placeholder가 아니라 화면의 구조를 미리 고정하는 장치입니다.

## 실제 레이아웃과 같은 크기를 가진다

스켈레톤은 실제 콘텐츠가 들어올 영역과 같은 폭, 높이, 간격을 가져야 합니다. 제목 한 줄, 설명 두 줄, 썸네일 비율이 정해져 있다면 로딩 상태도 같은 규칙을 써야 합니다.

```css
.article-card__image,
.article-card__imageSkeleton {
  aspect-ratio: 16 / 9;
}

.article-card__titleSkeleton {
  height: 1.4rem;
  width: 72%;
}
```

핵심은 데이터 도착 전후에 레이아웃이 움직이지 않는 것입니다. 로딩 화면을 따로 디자인하면 실제 화면과 어긋나기 쉽습니다. 가능하면 같은 컴포넌트 안에서 상태만 바꾸고, 크기 규칙은 공유합니다.

## 모든 지연에 스켈레톤을 쓰지 않는다

100ms 안에 끝나는 요청에 스켈레톤을 보여주면 화면이 깜빡입니다. 사용자는 로딩이 빨랐다고 느끼기보다 UI가 불안정하다고 느낍니다. 짧은 지연에는 아무것도 표시하지 않고, 일정 시간이 지나면 로딩 상태를 보여주는 편이 낫습니다.

실무에서는 다음 기준이 유용합니다.

- 0~150ms: 기존 화면 유지
- 150~500ms: 작은 로딩 표시 또는 비활성 상태
- 500ms 이상: 구조가 보이는 스켈레톤
- 3초 이상: 진행 상황, 재시도, 대체 경로 표시

이 기준은 절대값이 아니라 제품의 체감 속도에 맞춰 조정하면 됩니다. 중요한 것은 모든 요청을 같은 로딩 UI로 처리하지 않는 것입니다.

## 실패 상태를 함께 설계한다

스켈레톤만 만들고 에러 상태를 나중에 붙이면 화면이 어색해집니다. 요청 실패, 빈 결과, 권한 없음, 부분 성공은 서로 다른 상태입니다. 특히 목록 화면에서는 전체 실패와 일부 카드 실패를 구분해야 합니다.

```tsx
if (state === "loading") return <ArticleSkeletonList />;
if (state === "error") return <RetryPanel onRetry={refetch} />;
if (articles.length === 0) return <EmptyState />;

return <ArticleList articles={articles} />;
```

스켈레톤은 로딩 상태 하나만 해결합니다. 사용자가 다음 행동을 할 수 없는 실패 상태까지 스켈레톤으로 가리면 문제를 숨기는 UI가 됩니다.

## 애니메이션은 절제한다

반짝이는 shimmer 효과는 처음에는 좋아 보이지만, 화면 전체가 움직이면 피로감이 큽니다. 긴 목록이나 대시보드에서는 애니메이션을 약하게 두거나 정적인 placeholder를 쓰는 편이 낫습니다. `prefers-reduced-motion`도 반드시 고려합니다.

```css
@media (prefers-reduced-motion: reduce) {
  .skeleton {
    animation: none;
  }
}
```

로딩 UI는 주인공이 아닙니다. 콘텐츠가 나타나기 전까지 구조와 기대를 유지하는 보조 장치입니다.

## 체크리스트

- 실제 콘텐츠와 같은 레이아웃 규칙을 사용한다.
- 짧은 지연에는 스켈레톤을 늦게 표시한다.
- 실패, 빈 결과, 권한 없음 상태를 따로 둔다.
- 긴 목록에서는 과한 shimmer를 피한다.
- `prefers-reduced-motion`을 반영한다.

스켈레톤 로딩의 목표는 사용자를 속이는 것이 아니라 기다리는 동안 화면을 이해할 수 있게 만드는 것입니다. 구조가 안정적이면 로딩 시간은 조금 길어도 덜 불안하게 느껴집니다.
