AI 코딩 에이전트는 작은 수정, 테스트 보강, 반복적인 리팩터링에서 이미 충분히 유용합니다. 문제는 "얼마나 똑똑한가"보다 "어디까지 맡겨도 되는가"입니다. 에이전트가 빠르게 코드를 바꿀 수 있다는 사실은 장점이지만, 같은 이유로 잘못된 변경도 빠르게 퍼질 수 있습니다.

안전한 도입의 핵심은 작업 범위와 권한을 명시하는 것입니다. 사람에게도 신입 온보딩 때 권한을 나누듯, 에이전트에게도 가드레일이 필요합니다.

## 맡기기 좋은 작업

에이전트에게 적합한 작업은 목표가 작고 검증 방법이 분명한 일입니다.

- 실패하는 테스트를 보고 원인을 좁히기
- 타입 오류나 린트 오류 수정
- 기존 패턴을 따라 새 API 핸들러 추가
- 테스트 케이스 누락 보강
- 문서와 코드 예시 동기화
- 반복적인 마이그레이션 코드 작성

이런 작업은 변경 범위가 작고, 빌드나 테스트로 결과를 확인할 수 있습니다. 에이전트가 잘못 추론해도 리뷰 비용이 비교적 낮습니다.

## 조심해야 할 작업

반대로 제품 판단, 보안 정책, 데이터 삭제, 외부 발송이 걸린 작업은 사람이 주도해야 합니다.

- 결제, 인증, 권한 모델 변경
- 데이터 마이그레이션과 삭제
- 프로덕션 인프라 설정 변경
- 고객에게 발송되는 이메일 문구 수정
- 법무나 개인정보 정책이 얽힌 코드
- 모호한 요구사항을 임의로 해석해야 하는 기능

이 작업들을 절대 시키지 말자는 뜻은 아닙니다. 다만 에이전트는 초안을 만들고, 결정은 사람이 해야 합니다.

## 저장소 권한은 단계적으로 준다

처음부터 푸시 권한이나 배포 권한을 주면 사고 반경이 커집니다. 도입 초기에는 읽기 권한과 브랜치 작업으로 충분합니다. 이후 안정성이 확인되면 다음 순서로 넓힙니다.

1. 로컬 수정만 허용
2. 별도 브랜치 푸시 허용
3. PR 생성 허용
4. 특정 라벨이나 경로에 한해 자동 머지 허용

자동 머지는 마지막 단계입니다. 그 전에는 CI, 코드오너 리뷰, 보안 스캔이 모두 통과해야 합니다.

## 작업 지시에는 금지 조건을 포함한다

에이전트 프롬프트에는 해야 할 일뿐 아니라 하지 말아야 할 일을 넣어야 합니다.

```text
src/billing 아래 파일은 수정하지 않는다.
기존 public API 응답 형식은 바꾸지 않는다.
테스트가 실패하면 원인만 보고하고 우회하지 않는다.
빌드가 통과하면 변경 파일 목록과 검증 결과를 요약한다.
```

금지 조건이 구체적일수록 리뷰가 쉬워집니다. "안전하게 해줘"는 안전장치가 아닙니다. 수정 금지 경로, 호환성 조건, 검증 명령을 직접 적어야 합니다.

## 결과물은 코드보다 검증 로그를 먼저 본다

에이전트의 변경을 볼 때는 "그럴듯한 코드"보다 "무엇으로 검증했는가"를 먼저 봅니다. 최소한 다음 정보가 필요합니다.

- 실행한 테스트와 빌드 명령
- 실패한 명령과 실패 이유
- 수정한 파일 목록
- 의도적으로 건드리지 않은 영역
- 남은 리스크

검증 로그가 없는 자동 수정은 사람이 처음부터 다시 확인해야 합니다. 생산성을 얻으려면 에이전트가 코드뿐 아니라 검증 흔적까지 남기게 해야 합니다.

## 체크리스트

- 작고 검증 가능한 작업부터 맡긴다.
- 보안, 결제, 삭제, 외부 발송은 사람 승인 경로를 둔다.
- 권한은 로컬 수정에서 PR 생성까지 단계적으로 넓힌다.
- 프롬프트에 수정 금지 영역과 호환성 조건을 명시한다.
- 최종 리뷰에서는 검증 명령과 실패 로그를 먼저 확인한다.

AI 코딩 에이전트는 자율 개발자가 아니라 빠른 작업자에 가깝습니다. 일을 잘게 나누고 검증 가능한 경계 안에 두면, 팀의 속도를 올리면서도 운영 리스크를 관리할 수 있습니다.
