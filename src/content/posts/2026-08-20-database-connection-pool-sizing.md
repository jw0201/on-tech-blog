커넥션 풀 크기는 자주 기본값으로 방치됩니다. 개발 환경에서는 문제가 없고, 운영에서도 한동안 괜찮아 보입니다. 그러다 트래픽이 늘거나 인스턴스를 증설한 순간 데이터베이스 커넥션 한도를 넘기고 장애가 납니다.

커넥션 풀은 클수록 좋은 설정이 아닙니다. 너무 작으면 애플리케이션이 대기하고, 너무 크면 데이터베이스가 동시에 처리할 수 없는 일을 떠안습니다. 필요한 것은 전체 시스템 기준의 계산입니다.

## 인스턴스 수를 곱해서 본다

애플리케이션 한 대의 풀 크기만 보면 착각하기 쉽습니다. 풀 크기 20은 작아 보이지만 인스턴스가 30개면 최대 600개의 커넥션이 됩니다. 여기에 worker, 배치, 관리자 도구까지 더하면 데이터베이스 한도를 쉽게 넘습니다.

먼저 전체 최대치를 계산합니다.

```text
총 최대 커넥션 = 인스턴스 수 * 인스턴스당 풀 크기 + 기타 클라이언트
```

이 값은 데이터베이스의 `max_connections`보다 작아야 할 뿐 아니라, 실제로 처리 가능한 동시 쿼리 수보다도 작아야 합니다. 연결할 수 있다고 처리할 수 있는 것은 아닙니다.

## 평균이 아니라 대기 시간을 본다

풀 크기를 조정할 때 평균 쿼리 시간만 보면 부족합니다. 중요한 것은 요청이 커넥션을 얻기 위해 얼마나 기다리는지입니다.

관측해야 할 지표는 다음과 같습니다.

- pool checkout latency
- active connection 수
- idle connection 수
- timeout으로 커넥션 획득 실패한 횟수
- 쿼리 실행 시간 분포
- 데이터베이스 CPU와 lock wait

checkout latency가 높다면 풀을 늘릴 수도 있지만, 쿼리가 느려서 커넥션을 오래 잡고 있는 것일 수도 있습니다. 이 경우 풀을 늘리면 데이터베이스 부하만 키울 수 있습니다.

## 느린 쿼리를 먼저 줄인다

커넥션은 쿼리 실행 동안 점유됩니다. 같은 요청 수라도 쿼리 시간이 길면 필요한 커넥션 수가 늘어납니다. 그래서 풀 크기 문제처럼 보이는 장애가 실제로는 느린 쿼리 문제일 때가 많습니다.

예를 들어 초당 100개 요청이 들어오고 각 요청이 DB 커넥션을 50ms 사용하면 필요한 동시 커넥션은 대략 5개입니다. 그런데 쿼리가 500ms로 느려지면 50개가 필요합니다.

풀을 키우기 전에 느린 쿼리, 불필요한 트랜잭션, N+1 조회, 긴 lock 대기를 먼저 확인해야 합니다.

## 요청과 배치를 분리한다

웹 요청과 배치 작업이 같은 풀을 쓰면 배치가 커넥션을 점유해 사용자 요청이 밀릴 수 있습니다. 특히 대량 백필, 리포트 생성, 인덱싱 작업은 별도 풀이나 별도 워커로 분리하는 편이 안전합니다.

분리 기준은 다음과 같습니다.

- 사용자 요청은 낮은 대기 시간 우선
- 배치는 처리량과 재시도 우선
- 관리자 작업은 제한된 동시성
- 마이그레이션은 별도 실행 경로

풀을 분리하면 각 작업 유형에 맞는 timeout과 동시성 제한을 줄 수 있습니다.

## 풀 크기 변경은 배포 계획에 포함한다

오토스케일링과 풀 크기는 함께 움직입니다. 인스턴스가 두 배로 늘면 데이터베이스 커넥션 최대치도 두 배가 됩니다. 따라서 스케일링 정책에는 데이터베이스 연결 예산이 포함되어야 합니다.

새 서비스를 배포할 때도 마찬가지입니다. "인스턴스 10개, 풀 15개"는 데이터베이스에 최대 150개 연결을 추가한다는 뜻입니다. 배포 전 이 예산을 확인해야 합니다.

커넥션 풀 크기는 감으로 넣는 숫자가 아니라 데이터베이스 용량을 나누어 쓰는 계약입니다. 인스턴스 수, 쿼리 시간, 대기 시간, 작업 유형을 함께 보면 작은 풀로도 안정적인 처리량을 만들 수 있습니다.
