분산 추적에서 trace id는 요청의 경로를 이어줍니다. 하지만 때로는 경로뿐 아니라 요청의 속성도 함께 전달하고 싶어집니다. 예를 들어 테넌트 유형, 실험 그룹, 요청 우선순위 같은 값입니다. 이런 용도로 쓰이는 것이 baggage입니다.

baggage는 편리하지만 조심해야 합니다. 한 번 전파되면 여러 서비스와 로그, 메트릭, 외부 호출로 퍼질 수 있기 때문입니다.

## 전파할 값과 기록할 값을 구분한다

모든 관측 값이 전파되어야 하는 것은 아닙니다. 어떤 값은 현재 서비스의 span attribute로 충분합니다. baggage는 downstream 서비스가 실제로 의사결정이나 관측에 써야 할 때만 넣는 편이 좋습니다.

전파 후보는 다음처럼 제한할 수 있습니다.

- 요청 우선순위
- 테넌트 등급
- 실험 그룹
- 내부 트래픽 여부
- 샘플링 힌트

반대로 넣으면 안 되는 값도 분명합니다.

- 이메일, 전화번호 같은 개인정보
- access token이나 session id
- 원문 검색어
- 긴 자유 텍스트
- 고유 사용자 ID

baggage는 여러 경계를 지나기 때문에 민감 정보가 들어가면 제거하기 어렵습니다.

## 카디널리티 비용을 계산한다

baggage 값은 로그와 메트릭 라벨로 복사되기 쉽습니다. 이때 고유값이 많은 필드가 들어가면 저장 비용과 쿼리 비용이 급격히 늘어납니다.

예를 들어 `tenantId`를 그대로 전파하고 모든 메트릭 라벨에 붙이면 테넌트 수만큼 시계열이 늘어납니다. 문제 분석에는 도움이 될 수 있지만 기본 라벨로 쓰기에는 비쌀 수 있습니다.

대안은 등급화입니다.

- `tenant_tier=enterprise`
- `traffic_class=internal`
- `plan_group=paid`

고유 식별자가 필요할 때는 로그나 span attribute에 제한적으로 남기고, 메트릭 라벨로 승격하지 않는 규칙을 둡니다.

## 경계에서 정리한다

서비스 mesh, API gateway, edge worker처럼 요청 경계에 가까운 곳에서 baggage를 정리하는 정책이 필요합니다. 외부 클라이언트가 임의로 보낸 baggage를 내부 시스템이 그대로 믿으면 안 됩니다.

경계 정책은 다음을 포함합니다.

- 허용된 key만 통과시킨다.
- key와 value 길이를 제한한다.
- 외부 요청의 baggage는 기본적으로 제거한다.
- 내부에서 생성한 값만 신뢰한다.
- downstream으로 보낼 때 필요한 값만 남긴다.

baggage는 헤더로 전파되므로 크기 제한도 중요합니다. 너무 큰 baggage는 요청 실패나 프록시 문제를 만들 수 있습니다.

## 소유자와 용도를 문서화한다

baggage key는 한번 퍼지면 제거하기 어렵습니다. 그래서 추가할 때 소유자와 목적을 남겨야 합니다.

문서에는 다음을 적습니다.

- key 이름
- 값의 가능한 범위
- 생성 위치
- 소비하는 서비스
- 보존 기간
- 메트릭 라벨 사용 여부

소비하는 서비스가 사라졌다면 baggage key도 제거 대상입니다. 전파 컨텍스트는 방치되면 오래된 의존성을 숨깁니다.

## 샘플링과 함께 설계한다

baggage는 샘플링 결정을 돕는 데 유용합니다. 예를 들어 결제 흐름이나 enterprise 테넌트 요청을 더 높은 비율로 추적할 수 있습니다.

다만 샘플링에 쓰는 값은 조작 가능성을 고려해야 합니다. 외부 사용자가 값을 바꿀 수 있다면 추적 비용을 의도적으로 늘릴 수 있습니다. 경계에서 신뢰할 수 있는 값으로 다시 계산하는 편이 안전합니다.

baggage는 분산 시스템의 맥락을 풍부하게 해주지만, 무제한 메모장이 아닙니다. 적은 수의 낮은 카디널리티 값만 전파하고, 경계에서 정리하고, 소비자를 추적해야 오래 운영할 수 있습니다.
