비밀값 교체는 대부분 사고가 난 뒤에야 급하게 실행됩니다. 그때 처음 절차를 확인하면 권한, 배포 순서, 캐시, rollback 기준이 모두 동시에 문제가 됩니다.

Secret rotation은 문서만 있으면 충분하지 않습니다. 실제로 돌려본 훈련이어야 합니다.

## 소유자를 먼저 찾는다

교체할 비밀값이 무엇인지보다 중요한 질문은 누가 책임지는가입니다. 오래된 API key는 종종 여러 팀이 같이 쓰고, 정확한 사용처가 문서와 다를 수 있습니다.

각 secret에는 최소한 다음 정보가 있어야 합니다.

- 소유 팀
- 사용 서비스
- 발급 위치
- 배포 경로
- 만료일
- 긴급 폐기 절차

소유자가 없는 secret은 교체도 폐기도 어렵습니다. 목록 정리 자체가 보안 작업입니다.

## dual key를 지원한다

안전한 교체는 보통 새 key를 추가하고, 트래픽을 전환하고, 오래된 key를 폐기하는 순서로 진행됩니다. 시스템이 key 하나만 허용하면 무중단 교체가 어렵습니다.

가능하면 다음 구조를 지원합니다.

```text
current key: 새 요청에 사용
previous key: 검증 또는 rollback을 위해 임시 허용
```

서명 검증, webhook secret, 외부 API credential 모두 dual key 기간이 있으면 운영 부담이 줄어듭니다.

## 캐시와 런타임 반영을 확인한다

Secret manager 값을 바꿨다고 모든 프로세스가 즉시 새 값을 쓰는 것은 아닙니다. 애플리케이션이 시작 시점에만 환경 변수를 읽을 수도 있고, sidecar가 캐시할 수도 있습니다.

훈련에서는 다음을 확인해야 합니다.

- 새 secret 배포 후 어떤 프로세스를 재시작해야 하는가
- secret reload가 자동인지 수동인지
- 오래된 pod가 남아 있지 않은가
- queue worker와 batch job도 같은 값을 쓰는가
- rollback 시 이전 key가 아직 유효한가

웹 서버만 바꾸고 worker를 놓치면 일부 작업만 조용히 실패할 수 있습니다.

## 관측 지표를 준비한다

교체 중에는 성공 여부를 빠르게 판단할 지표가 필요합니다.

- 인증 실패율
- 외부 API 401 또는 403 응답
- webhook 검증 실패 수
- 배포된 버전별 요청 성공률
- secret reload 오류

이 지표가 없으면 교체가 끝난 뒤 사용자 문의로 실패를 알게 됩니다.

## 작은 secret부터 연습한다

처음 훈련은 영향이 작은 내부 webhook secret부터 시작하는 편이 좋습니다. 절차가 안정되면 결제, 인증, 배포 credential처럼 더 중요한 secret으로 넓힙니다.

각 훈련 후에는 실제 소요 시간과 막힌 지점을 기록합니다. 다음 교체는 그 기록을 기준으로 더 짧고 안전해져야 합니다.

Secret rotation의 목표는 완벽한 문서가 아니라 당황하지 않는 팀입니다. 정기적으로 돌려본 절차는 사고가 났을 때 훨씬 강합니다.
