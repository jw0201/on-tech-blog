큰 PR은 리뷰를 느리게 만들고, 리뷰가 느리면 변경은 더 커집니다. 결국 모두가 부담스러운 상태에서 대충 승인하거나, 며칠 동안 충돌을 고치게 됩니다.

PR을 작게 만드는 일은 코드를 덜 쓰는 것이 아니라 변경의 순서를 설계하는 일입니다.

## 행동 변화와 구조 변화를 분리한다

가장 먼저 볼 것은 리팩터링과 기능 변경이 섞였는지입니다. 파일 이동, 이름 변경, 계층 분리는 행동 변화가 없어도 diff를 크게 만듭니다.

가능하면 다음 순서로 나눕니다.

1. 테스트 또는 관측 추가
2. 행동 변화 없는 구조 정리
3. 새 기능 추가
4. 이전 경로 제거

리뷰어는 각 PR에서 봐야 할 질문이 달라집니다. 구조 정리 PR에서는 동작이 그대로인지 보고, 기능 PR에서는 제품 동작을 봅니다.

## 호환 계층을 임시로 둔다

한 번에 모든 호출자를 바꾸려 하면 PR이 커집니다. 새 API나 모듈을 도입할 때는 잠깐의 호환 계층이 도움이 됩니다.

예를 들어 새 함수로 옮기면서 기존 함수는 내부에서 새 함수를 호출하게 만들 수 있습니다.

```ts
export function oldCalculatePrice(input: OldInput) {
  return calculatePrice(adaptOldInput(input));
}
```

그 다음 호출자를 여러 PR로 옮기고, 마지막에 old path를 제거합니다. 임시 코드는 반드시 제거 계획이 있어야 합니다.

## 리뷰 기준을 PR 설명에 적는다

작은 PR이라도 리뷰어가 맥락을 모르면 오래 걸립니다. 설명에는 구현 내용을 길게 쓰기보다 리뷰 기준을 적는 편이 좋습니다.

유용한 항목은 다음과 같습니다.

- 이번 PR에서 바뀌는 사용자 동작
- 의도적으로 바꾸지 않은 것
- 다음 PR에서 이어질 작업
- 집중해서 봐야 할 위험 영역
- 테스트 방법

리뷰어가 "이 PR에서 무엇을 승인하는가"를 알면 리뷰 속도가 빨라집니다.

## 데이터 변경은 더 작게 나눈다

DB migration이 포함된 PR은 특히 조심해야 합니다. 코드와 schema를 한 번에 바꾸면 rollback이 어렵습니다.

일반적인 순서는 다음과 같습니다.

1. 새 컬럼이나 테이블 추가
2. 양쪽 write 또는 backfill
3. read path 전환
4. 오래된 컬럼 제거

각 단계는 배포 가능한 상태여야 합니다. 중간 상태가 운영에서 안전해야 큰 변경도 작게 배포할 수 있습니다.

## 완료 기준을 작게 잡는다

PR이 작아도 독립적으로 의미가 있어야 합니다. "컴파일만 된다"가 아니라 다음 단계로 가기 위한 확실한 기반을 만들어야 합니다.

예를 들어 observability 추가 PR은 기능이 바뀌지 않아도 배포 후 지표를 볼 수 있으면 의미가 있습니다. 호환 계층 PR은 호출자 이전을 시작할 수 있으면 의미가 있습니다.

리뷰 가능한 PR은 팀의 집중력을 아끼는 설계입니다. 작은 diff보다 중요한 것은 리뷰어가 정확한 질문을 할 수 있는 변경 단위입니다.
