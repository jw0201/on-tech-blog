쿼리는 테스트 데이터에서 빠르게 보이다가 운영 데이터에서 갑자기 느려질 수 있습니다. 로컬에는 행이 적고, 분포가 단순하고, 캐시도 따뜻하기 때문입니다.

중요한 조회가 추가될 때는 코드 리뷰와 함께 query plan 리뷰가 필요합니다.

## 실제 조건에 가까운 파라미터를 쓴다

`EXPLAIN`을 볼 때 아무 값이나 넣으면 의미가 약해집니다. 데이터 분포에 따라 DB가 선택하는 계획이 달라질 수 있습니다.

대표 파라미터를 최소 세 종류로 봅니다.

- 결과가 거의 없는 조건
- 평균적인 결과 수를 만드는 조건
- 특정 tenant나 카테고리에 데이터가 몰린 조건

특히 멀티테넌트 시스템에서는 큰 tenant와 작은 tenant의 계획이 다를 수 있습니다.

## 읽는 행과 반환하는 행을 비교한다

쿼리가 느린 이유는 대개 반환 행보다 훨씬 많은 행을 읽기 때문입니다. 실행 계획에서는 실제로 스캔한 행 수와 최종 반환 행 수를 함께 봐야 합니다.

확인할 신호는 다음과 같습니다.

- sequential scan이 예상보다 큰 테이블에 발생하는가
- filter에서 대부분의 행이 버려지는가
- 정렬이 메모리를 넘어서 디스크를 쓰는가
- nested loop가 큰 입력에 반복되는가
- index가 있어도 조건 순서 때문에 활용되지 않는가

단순히 "index를 탄다"만으로는 부족합니다. 얼마나 읽고 버리는지가 중요합니다.

## ORDER BY와 pagination을 같이 본다

목록 API에서 필터는 괜찮아 보여도 정렬과 페이지네이션 때문에 느려지는 경우가 많습니다. `ORDER BY created_at DESC LIMIT 50`은 흔하지만, 조건에 맞는 index가 없으면 큰 정렬이 발생할 수 있습니다.

cursor pagination을 쓴다면 cursor 조건과 정렬 기준이 같은 index를 사용할 수 있는지 봐야 합니다.

```sql
where tenant_id = ?
  and created_at < ?
order by created_at desc
limit 50
```

이 쿼리에는 보통 `(tenant_id, created_at)` 형태의 index가 필요합니다.

## 통계와 vacuum 상태도 확인한다

쿼리 플랜은 DB 통계에 의존합니다. 통계가 낡으면 DB는 행 수를 잘못 추정하고 나쁜 계획을 고를 수 있습니다.

운영에서 갑자기 느려진 쿼리는 index만 볼 것이 아니라 다음도 확인해야 합니다.

- table과 index bloat
- 통계 갱신 시점
- autovacuum 지연
- 특정 값에 데이터가 몰린 skew
- 최근 대량 insert 또는 delete

성능 문제는 SQL 한 줄보다 데이터 생명주기와 연결되어 있을 때가 많습니다.

## 리뷰 결과를 남긴다

중요한 쿼리라면 PR에 실행 계획 요약을 남깁니다.

- 사용한 파라미터
- 예상 반환 행 수
- 주요 index
- 가장 비싼 단계
- 데이터 증가 시 위험

쿼리 플랜 리뷰는 모든 SQL에 필요한 의식은 아닙니다. 하지만 자주 호출되는 목록, 배치 작업, 대량 tenant 대상 쿼리는 배포 전에 한 번 보는 것만으로도 큰 장애를 줄일 수 있습니다.
