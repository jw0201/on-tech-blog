트래픽이 늘면 로그 비용은 빠르게 커집니다. 그래서 샘플링을 고민하게 됩니다. 하지만 단순히 모든 로그를 10%만 남기면 장애 조사에 필요한 정보까지 사라질 수 있습니다.

로그 샘플링의 목표는 적게 저장하는 것이 아니라 같은 판단을 더 낮은 비용으로 할 수 있게 만드는 것입니다.

## 에러 로그는 기본적으로 보존한다

가장 먼저 정할 원칙은 에러와 보안 관련 로그를 샘플링 대상에서 제외하는 것입니다.

보존해야 할 로그는 다음과 같습니다.

- 5xx 응답
- 인증과 권한 실패
- 결제와 주문 실패
- 데이터 변경 감사 로그
- rate limit 차단
- panic 또는 unhandled exception

이 로그들은 양이 적더라도 조사 가치가 큽니다. 비용 절감을 위해 먼저 줄일 대상은 반복적인 성공 로그입니다.

## 요청 단위로 샘플링한다

로그 라인 단위로 샘플링하면 한 요청의 일부 로그만 남아서 흐름을 이해하기 어렵습니다. 가능하면 request ID 또는 trace ID 기준으로 샘플링합니다.

한 요청이 샘플링 대상으로 선택되면 그 요청의 주요 로그는 함께 남깁니다.

```text
request_id=abc start
request_id=abc db_query
request_id=abc response
```

이렇게 해야 성공 요청의 대표 샘플을 분석할 수 있습니다.

## 동적 샘플링을 둔다

평상시에는 성공 로그를 낮은 비율로 남기고, 장애가 의심되면 특정 서비스나 endpoint의 샘플링 비율을 올릴 수 있어야 합니다.

유용한 조정 기준은 다음과 같습니다.

- endpoint
- tenant
- HTTP status
- latency bucket
- feature flag
- 배포 버전

예를 들어 새 릴리스 직후에는 해당 버전의 로그를 더 많이 남기고, 안정화되면 다시 낮출 수 있습니다.

## 샘플링 비율을 로그에 남긴다

샘플링된 로그를 지표처럼 사용할 때는 비율을 알아야 합니다. 10% 샘플에서 100건이 보인다면 실제로는 약 1,000건일 수 있습니다.

로그에는 다음 필드를 넣는 것이 좋습니다.

- `sampled=true`
- `sample_rate=0.1`
- `sampling_rule=success_request_default`

이 정보가 있어야 집계와 비용 분석을 해석할 수 있습니다.

## 감사 로그와 섞지 않는다

운영 디버깅 로그와 감사 로그는 목적이 다릅니다. 감사 로그는 누가 어떤 데이터를 바꿨는지 증명해야 하므로 샘플링하면 안 됩니다.

로그 비용을 줄이려면 감사 로그를 별도 저장소와 보존 정책으로 분리하는 편이 낫습니다. 디버깅 로그의 샘플링 정책이 감사 요구사항을 침범하지 않게 해야 합니다.

로그 샘플링은 관측성을 포기하는 작업이 아닙니다. 어떤 신호가 판단에 필요한지 먼저 정하면 비용은 줄이면서도 장애 대응 능력은 유지할 수 있습니다.
